# 五大模板深度审计与优化方案

> 日期：2026-05-29
> 审计范围：cf-shop / cf-api / cf-tools / cf-static / cf-form-kit
> 审计维度：结构一致性、业务目标对齐、行业最佳实践、部署可靠性

## 一、审计总结

### 1.1 整体评价

| 模板 | 文件数 | 状态 | 与 cf-core 集成 | 部署模式 | 评价 |
|------|--------|------|-----------------|---------|------|
| **cf-shop** | 39 | ⚠️ 基本就绪 | ✅ 完全集成 | workers | 缺少 `.deploy-mode`，有冗余脚本 |
| **cf-api** | 35 | ⚠️ 基本就绪 | ✅ 完全集成 | workers | 缺少 `.deploy-mode`，有冗余脚本 |
| **cf-tools** | 37 | ⚠️ 基本就绪 | ✅ 完全集成 | workers | 缺少 `.deploy-mode`，有冗余脚本 |
| **cf-static** | 29 | 🔴 有阻塞性问题 | ❌ 不集成（纯静态） | pages | 工具 JS 文件缺失，页面功能不可用 |
| **cf-form-kit** | 38 | 🟡 独立体系 | ❌ 完全独立（D1） | workers (D1) | 未迁移到 cf-core，是最早的模板 |

### 1.2 关键发现

**发现 1：五个模板分为三个"代际"**

| 代际 | 模板 | 特征 |
|------|------|------|
| **第一代** | cf-form-kit | 独立自包含，D1 数据库，无 cf-core 集成，自有部署脚本 |
| **第二代** | cf-shop / cf-api / cf-tools | cf-core 集成，Turso，.deploy/ 统一部署体系 |
| **第三代** | cf-static | Pages 模式，无后端，SEO 工具链 |

**发现 2：三个共性阻塞问题**

| # | 严重度 | 问题 | 影响模板 |
|---|--------|------|---------|
| 1 | 🔴 严重 | cf-static 工具页面引用了不存在的 JS 文件 | cf-static |
| 2 | 🟡 中等 | cf-shop/cf-api/cf-tools 缺少 `.deploy-mode` 文件 | 3 个模板 |
| 3 | 🟡 中等 | `scripts/deploy.sh` 与 `.deploy/` 体系功能重叠 | cf-shop/cf-api/cf-tools |

**发现 3：cf-form-kit 是"孤岛"**

cf-form-kit 是唯一没有集成 cf-core 的模板。它有自己的：
- `src/lib/http.ts` — 与 cf-core/http.ts 功能重复
- `src/lib/security.ts` — 与 cf-core/security.ts 功能重复
- `src/lib/rate-limit.ts` — 与 cf-core/rate-limit.ts 功能重复
- `src/lib/idempotency.ts` — 与 cf-core/idempotency.ts 功能重复
- `src/db/client.ts` — D1 专用，与 cf-core/db 不同
- `scripts/deploy-full.mjs` — 与 `.deploy/` 体系不同

## 四、优化方案

### 4.1 立即修复（P0 — 阻塞性问题）

#### 修复 1：cf-static 工具 JS 文件

创建 `public/js/` 下的 3 个工具 JS 文件，使工具页面功能可用。

#### 修复 2：三个模板的 `.deploy-mode` 文件

为 cf-shop / cf-api / cf-tools 创建 `.deploy-mode` 文件，写入 `workers`。

#### 修复 3：删除冗余 `scripts/deploy.sh`

删除 cf-shop / cf-api / cf-tools 中的 `scripts/deploy.sh`，统一使用 `.deploy/` 体系。

#### 修复 4：cf-static `generate:sitemap` 脚本

删除 `package.json` 中的 `generate:sitemap` 脚本（`generate-seo-pages.mjs` 已包含 sitemap 生成）。

### 4.2 cf-form-kit 迁移方案（P1 — 重要决策）

**选项 A：迁移到 cf-core + Turso（推荐）**

将 cf-form-kit 迁移到 cf-core 体系：
- 删除重复的 `src/lib/` 文件，改用 `@eforge/cf-core/*`
- 将 D1 迁移到 Turso（与整体技术路线一致）
- 添加 `.deploy/` 目录（从 `.deploy/` 模板复制）
- 添加 `.deploy-mode` 文件（`workers`）

**优点**：
- 与整体技术路线一致
- 减少重复代码（4 个 lib 文件 → cf-core）
- 统一部署体验（one-click.sh）

**缺点**：
- D1 → Turso 需要迁移数据
- 需要修改所有路由文件（从 `c.env.DB.prepare()` 改为 Drizzle ORM）

**选项 B：保持独立，标记为"遗留模板"**

将 cf-form-kit 标记为"遗留模板"，不再维护新功能：
- 保留现有代码不变
- 在 README 中添加"遗留模板"标记
- 新项目建议使用 cf-tools 或 cf-api 替代

**优点**：
- 无迁移风险
- 不影响现有项目

**缺点**：
- 技术债务积累
- 新项目无法使用统一的一键部署

**选项 C：迁移到 cf-core + 保留 D1**

将 cf-form-kit 迁移到 cf-core，但保留 D1 数据库：
- 删除重复的 `src/lib/` 文件
- 保留 D1（适合极轻量场景）
- 添加 `.deploy/` 目录
- 修改 `01-setup-turso.sh` 为可选（如果 `.deploy-mode` 为 `workers-d1`）

**优点**：
- 减少重复代码
- 保留 D1 的轻量优势

**缺点**：
- 需要维护两套数据库逻辑（D1 + Turso）

### 4.3 我的建议

**推荐选项 A：迁移 cf-form-kit 到 cf-core + Turso**

理由：
1. **技术一致性**：所有模板使用相同的技术栈，降低维护成本
2. **统一部署体验**：所有模板使用 one-click.sh，用户无需学习不同的部署方式
3. **减少重复代码**：4 个 lib 文件 → cf-core，减少约 400 行重复代码
4. **Turso 优势**：Free 套餐 9GB 存储，比 D1 的 500MB 更宽裕
5. **长期维护**：维护一套代码比维护两套更容易

**迁移步骤**：
1. 删除 `src/lib/` 目录（4 个文件）
2. 修改所有路由文件，从 `c.env.DB.prepare()` 改为 Drizzle ORM
3. 修改 `src/db/client.ts`，从 D1 改为 Turso
4. 添加 `.deploy/` 目录（从 `.deploy/` 模板复制）
5. 添加 `.deploy-mode` 文件（`workers`）
6. 修改 `package.json`，添加 `@eforge/cf-core` 依赖
7. 修改 `tsconfig.json`，添加 `@eforge/cf-core/*` paths
8. 测试部署

- ✅ 五个模板全部使用统一的技术栈（cf-core + Turso）
