# 踩坑记录：Hugo → 11ty 迁移全过程

> 项目：cf-static（在线开发工具站）
> 时间：2026-05-29 ~ 2026-05-31
> 目标：从 Hugo 迁移到 Eleventy (11ty) v3，部署到 Cloudflare Pages

---

## 一、架构决策坑

### 坑 1：Hugo vs 11ty 的本质差异

**问题**：Hugo 是"二进制 + 配置驱动"，11ty 是"Node.js + 代码驱动"。

**表现**：
- Hugo 用 `hugo new` 脚手架命令生成内容文件
- 11ty 用普通文件 + frontmatter，没有脚手架
- Hugo 的 `layouts/` 目录结构是固定的，11ty 的目录结构完全自由

**教训**：迁移时不要试图"1:1 对应"，要按 11ty 的方式重新设计。

### 坑 2：11ty v3 的 `site` 是保留字（🔴 最严重的坑）

**问题**：在 11ty v3 中，`site` 是内置全局变量（SiteMap 对象），**不能**用作数据文件名。

**表现**：
```
# site.json 作为数据文件 → site 关键字被覆盖
# 模板中 {{ site.siteName }} → 输出字面量 "{{ site.siteName }}"
# 因为 site 变成了 SiteMap 对象，没有 .siteName 属性
```

**影响范围**：
- 首页 title/description 渲染为字面量 `{{ site.siteName }}`
- OG 标签、Twitter Card 全部失效
- robots.txt 中 `{{ site.url }}` 解析为空

**修复方案**：
```
# 方案 A：重命名数据文件
site.json → config.json
# 模板中改为 {{ config.siteName }}

# 方案 B：在 .eleventy.js 中通过 addGlobalData 注入
eleventyConfig.addGlobalData("mySite", () => require("./src/_data/site.json"));
```

**推荐方案 A**，简单直接。

### 坑 3：Nunjucks 模板引擎 vs Liquid 语法

**问题**：11ty 支持多种模板引擎（Nunjucks、Liquid、MJML、Handlebars），但语法不互通。

**踩坑记录**：
```njk
{# Liquid 语法（❌ Nunjucks 不支持） #}
{% if tool.keywords contains "json" %}

{# Nunjucks 语法（✅ 正确） #}
{% if tool.keywords and tool.keywords | contains("json") %}
```

**其他差异**：
| 功能 | Liquid | Nunjucks |
|------|--------|----------|
| 数组包含 | `array contains "x"` | `array | contains("x")` |
| 安全输出 | `{{ var \| safe }}` | `{{ var \| safe }}`（相同） |
| 默认值 | `{% assign x = y \| default: "z" %}` | `{{ y \| default("z") }}` |
| 条件 | `{% if x %}` | `{% if x %}`（相同） |
| 循环 | `{% for i in arr %}` | `{% for i in arr %}`（相同） |

## 二、目录结构坑

### 坑 4：`{% include %}` 只搜索 `_includes/` 目录

**问题**：Nunjucks 的 `{% include %}` 标签只在 `includes` 目录中搜索模板文件。

**错误做法**：
```
src/
  tools/
    social-insurance-calculator.njk  ← 放在这里
```
```njk
{# tools.njk 中 #}
{% include tool.slug ~ '.njk' %}
{# → Error: template not found: social-insurance-calculator.njk #}
```

**正确做法**：
```
src/
  _includes/
    social-insurance-calculator.njk  ← 必须放在 _includes/ 下
```

**修复**：
```bash
mv src/tools/*.njk src/_includes/
rmdir src/tools/
```

### 坑 5：`addPassthroughCopy` 在 v3 中的路径解析变化

**问题**：11ty v3 中，`addPassthroughCopy` 的路径解析行为有变化。

**错误做法**：
```js
// v2 风格：直接复制整个目录
eleventyConfig.addPassthroughCopy("public");
// → 在 v3 中会把 public/ 整体复制到 _site/public/，路径不对
```

**正确做法**：
```js
// v3 风格：逐个文件复制
eleventyConfig.addPassthroughCopy("favicon.svg");
eleventyConfig.addPassthroughCopy("_headers");
eleventyConfig.addPassthroughCopy("assets");  // 目录可以，但要在 input 目录下
```

**关键**：`addPassthroughCopy` 的路径是相对于 `input` 目录的。如果 `assets/` 在 `src/` 外，需要放对位置。

### 坑 6：`assets/` 目录应该在 `src/` 内还是外？

**最终方案**：放在 `src/` 外，与 `.eleventy.js` 同级。

```
cf-static/
  .eleventy.js
  assets/          ← 静态资源（JS/CSS/图片）
  favicon.svg
  _headers
  src/
    _data/
    _includes/
    _layouts/
    index.njk
    tools.njk
```

**原因**：`addPassthroughCopy("assets")` 会原样复制到输出目录，不需要经过模板引擎。放在 `src/` 外更清晰。

## 三、模板与数据坑

### 坑 7：`templateFormats` 不包含 `"js"` 导致 JS 模板不被识别

**问题**：最初尝试用 `sitemap.js` 作为 11ty 数据模板（JavaScript data template），但 `templateFormats` 默认不包含 `"js"`。

**错误**：
```js
// .eleventy.js
return {
  templateFormats: ["njk", "md"],  // ❌ 缺少 "js"
};
```

**修复**：
```js
return {
  templateFormats: ["njk", "md", "js"],  // ✅
};
```

**后续**：最终放弃了 sitemap.js 方案，因为 Nunjucks 模板引擎会尝试解析 XML 声明 `<?xml`，改用 `npx eleventy --dryrun` 后手动生成 sitemap。

### 坑 8：Nunjucks 把 `<?xml` 当作模板标签

**问题**：Nunjucks 模板引擎会解析 `{%` 和 `{{`，但 `<?xml version="1.0"?>` 中的 `<?` 也会被某些解析器误识别。

**表现**：
```
TemplateContentRenderError: template not found: ?xml version="1.0"?>
```

**修复方案**：不要用 Nunjucks 模板生成 XML 文件。改用：
1. 静态文件直接 passthrough
2. 或者用 JS data template 生成

### 坑 9：分页（Pagination）生成的页面数据作用域

**问题**：使用 11ty 分页功能时，`eleventyComputed` 中的数据引用。

```njk
---
pagination:
  data: tools
  size: 1
  alias: tool
eleventyComputed:
  title: "{{ tool.title }}"
  description: "{{ tool.description }}"
---
```

**注意**：
- `alias` 定义的变量（如 `tool`）在模板正文中可用
- `eleventyComputed` 中的值会传递给 layout，所以 `base.njk` 中可以用 `{{ title }}`
- 但 `eleventyComputed` 中的模板字符串**不会**在 frontmatter 外部再次求值

### 坑 10：FAQ 数据格式标准化

**问题**：原始 JSON 数据中 FAQ 字段名不统一（`q`/`a` vs `question`/`answer`）。

**修复**：统一为 `question`/`answer`：
```json
"faq": [
  {
    "question": "什么是 JSON 格式化工具？",
    "answer": "JSON 格式化工具是一款免费的在线工具..."
  }
]
```

**教训**：数据驱动站点必须在迁移前统一数据格式，否则模板中需要大量条件判断。

## 四、SEO 相关坑

### 坑 11：Canonical URL 需要手动设置

**问题**：11ty 不会自动生成 canonical URL，需要在每个页面中手动设置。

**方案**：在分页模板中使用 `eleventyComputed`：
```njk
---
eleventyComputed:
  canonical: "{{ site.url }}{{ page.url }}"
---
```

**注意**：`page.url` 是 11ty 内置的全局变量，包含当前页面的 URL 路径。

### 坑 12：`robots.txt` 需要模板引擎处理

**问题**：`robots.txt` 中的 `Sitemap:` 行需要动态插入站点 URL。

**方案**：
```js
// .eleventy.js
eleventyConfig.addPassthroughCopy("src/robots.txt", { filter: "njk" });
```

这样 `robots.txt` 会经过 Nunjucks 模板引擎处理，可以引用数据变量。

### 坑 13：OG 标签缺少 `og:site_name` 和 `og:locale`

**问题**：base layout 中这些标签是条件渲染的，但条件变量未设置。

**修复**：在 base layout 中直接使用数据文件中的值：
```njk
<meta property="og:site_name" content="{{ config.siteName }}">
<meta property="og:locale" content="{{ config.locale }}">
```

## 五、JS/CSS 相关坑

### 坑 14：计算器表单模板与 JS 的 DOM 依赖

**问题**：计算器的 JS 代码依赖特定的 DOM 元素 ID，如果模板中缺少这些元素，JS 会静默失败。

**排查方法**：
1. 列出 JS 中所有 `document.getElementById('xxx')` 调用
2. 检查模板中是否有对应 ID 的元素
3. 确保表单结构匹配 JS 期望

**income-tax-calculator.js 的特殊问题**：
```js
// JS 期望 childrenCountGroup 是一个直接变量
const childrenCountGroup = document.getElementById('childrenCount').parentElement;
// 但模板中 childrenCount 的父元素是 <div class="children-count-group">
// 需要确保 JS 正确引用
```

### 坑 15：CSS 缺少计算器表单样式

**问题**：`styles.css` 中没有 `.calculator-form`、`.form-group`、`.form-fieldset` 等样式。

**修复**：添加计算器专用样式：
```css
.calculator-form { ... }
.form-group { ... }
.form-fieldset { ... }
.calculator-result { ... }
```

## 六、部署相关坑

### 坑 16：Cloudflare Pages 的构建配置

**问题**：Cloudflare Pages 默认查找 `src/` 作为输入目录，但 11ty 的 `input` 目录也是 `src/`，输出到 `_site/`。

**Cloudflare Pages 设置**：
- 构建命令：`npx @11ty/eleventy`
- 输出目录：`_site`
- 根目录：`templates/cf-static`（如果项目在子目录）

### 坑 17：`_headers` 文件位置

**问题**：Cloudflare Pages 的 `_headers` 文件必须在输出目录的**根目录**。

**正确做法**：
```js
eleventyConfig.addPassthroughCopy("_headers");
```
这样 `_headers` 会被复制到 `_site/_headers`，Cloudflare Pages 能正确识别。

## 七、数据文件合并坑

### 坑 18：从多个 JSON 文件合并为单一 `tools.json`

**原始状态**：每个工具一个 JSON 文件（`json-formatter.json`、`base64-decode.json` 等）
**迁移后**：合并为单一 `tools.json` 数组

**原因**：
- 11ty 的数据级联机制：单个 JSON 文件作为数据文件时，其数据会注入到同名模板
- 但我们需要分页（pagination）遍历所有工具，单一数组更方便
- 减少文件数量，简化维护

**教训**：数据驱动站点中，**聚合数据**比**分散数据**更容易维护。

## 八、版本兼容性坑

### 坑 19：11ty v3 vs v2 的 Breaking Changes

| 特性 | v2 | v3 |
|------|----|-----|
| `site` 全局变量 | 可用作数据名 | 保留字（SiteMap） |
| `addPassthroughCopy` 路径 | 相对项目根 | 相对 input 目录 |
| 默认模板格式 | `["html", "liquid", "md"]` | `["njk", "md"]` |
| `EleventyHtmlBasePlugin` | 不存在 | 新增 |
| 数据模板格式 | JS CommonJS | JS ESM |

### 坑 20：ESM vs CommonJS

**问题**：项目 `package.json` 设置了 `"type": "module"`，但 11ty 数据模板默认用 CommonJS。

**修复**：`.eleventy.js` 本身用 ESM（`import/export`），数据模板用 JSON（无此问题）。

## 九补充、SEO/GEO 深度加固采坑记录（2026-05-31 审计新增）

> 以下坑点来自 SEO/GEO 全面加固审计，涉及 Nunjucks 隐式 Bug、JSON-LD 规范、11ty v3 行为变化等深层问题。

### 坑 21：Nunjucks `not in` 对中文字符串完全失效（🔴 最隐蔽的坑）

**问题**：Nunjucks 的 `not in` 运算符对中文字符串做**字符级拆分比较**，而非整串比较。

**复现**：
```njk
{# 意图：从 tools 中提取不重复的 category #}
{% set _categories = [] %}
{% for t in tools %}
{% if t.category and t.category not in _categories %}
{# 当 t.category = "格式化" 时：
   "格式化" not in ["格式化"] → Nunjucks 返回 true！
   因为它把 "格式化" 拆成 ["格", "式", "化"] 逐个比较 #}
{% set _categories = _categories + [t.category] %}
{% endif %}
{% endfor %}
```

**表现**：首页分类索引把 "格式化" 拆成了三个 `<h2>`：`<h2>格</h2>`、`<h2>式</h2>`、`<h2>化</h2>`。

**根因**：Nunjucks 底层用 JavaScript `indexOf()` 做 `in` 比较，但对模板中的数组+字符串组合，会触发字符迭代而非对象比较。这是 Nunjucks 的已知行为缺陷。

**修复方案**：
```njk
{# ✅ 使用 .eleventy.js 中自定义的 JS filter #}
{% set categories = tools | map("category") | unique %}
{% for cat in categories %}
{% if cat %}
  <h2>{{ cat }}</h2>
{% endif %}
{% endfor %}
```

```js
// .eleventy.js 中必须定义这两个 filter
eleventyConfig.addFilter("unique", (array) => [...new Set(array)]);
eleventyConfig.addFilter("map", (array, prop) => array.map(item => item[prop]));
```

**教训**：
- ❌ **永远不要用 Nunjucks 模板语法做中文字符串的去重/成员检查**
- ✅ **必须用 JS filter（在 `.eleventy.js` 中实现）**，因为 JS 的 `Set` 和 `===` 对中文完全正确
- 这个 bug 在英文环境下**不会暴露**（单字母分类名碰巧能工作），只在中文内容中出现

### 坑 22：`page.url.endswith()` 是 Python 语法，Nunjucks 不支持

**问题**：想判断当前页面是否为首页或 index 页，本能地写了 Python 风格代码。

**错误写法**：
```njk
{% if page.url != '/' and not page.url.endswith('/index.html') %}
```

**报错**：
```
Template render error: (base.njk) [Line 51, Column 43]
  error - TypeError: page.url.endswith is not a function
```

**修复方案**：Nunjucks/JavaScript 中字符串没有 `endswith()`，用 `indexOf()` + 位置判断：
```njk
{% if page.url != '/' and (page.url | indexOf('/index.html')) != -1 %}
```

或者更清晰的写法——用 JS filter：
```js
// .eleventy.js
eleventyConfig.addFilter("endsWith", (str, suffix) => str.endsWith(suffix));
```
```njk
{% if page.url != '/' and not (page.url | endsWith('/index.html')) %}
```

**教训**：
- ❌ Nunjucks 运行在 JavaScript 环境，**不是 Python**
- ✅ 字符串操作必须用 JS API：`indexOf()`, `startsWith()`, `endsWith()`, `slice()`
- ✅ 复杂字符串操作建议封装为自定义 filter

### 坑 23：11ty v3 `addPassthroughCopy` 的 `filter: "njk"` 对 sitemap.xml 不生效

**问题**：想让 `sitemap.xml` 经过 Nunjucks 模板引擎处理（替换 `{{ config.url }}`），但 `filter: "njk"` 在 v3 中的行为与预期不同。

**错误做法**：
```js
// .eleventy.js
eleventyConfig.addPassthroughCopy("sitemap.xml", { filter: "njk" });
```
结果：sitemap.xml 被原样复制，`{{ config.url }}` 未被替换。

**正确做法**：
1. 将文件重命名为 `sitemap.njk`（放在 `src/` 目录下）
2. 添加 frontmatter 指定输出路径：
```njk
---
permalink: /sitemap.xml
---
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  {% for tool in tools %}
  <url>
    <loc>{{ config.url }}/tools/{{ tool.slug }}/index.html</loc>
  </url>
  {% endfor %}
</urlset>
```
3. 从 `.eleventy.js` 中移除 sitemap 的 passthroughCopy

**教训**：
- ❌ `addPassthroughCopy` 的 `filter` 选项在 v3 中行为不确定
- ✅ 需要模板处理的非 HTML 文件，**直接命名为 `.njk` + frontmatter `permalink`**
- ✅ 这是 11ty 处理任意格式模板输出的标准方式

### 坑 24：JSON-LD Schema 在子页面重复输出（Organization Schema）

**问题**：`base.njk` 是无条件输出 Organization Schema，导致每个子页面都有重复的 Organization JSON-LD。

**错误写法**：
```njk
{# base.njk — 无条件输出 #}
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "name": "{{ config.siteName }}",
  ...
}
</script>
```

**正确写法**：
```njk
{# base.njk — 仅首页输出 #}
{% if page.url == '/' %}
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Organization",
  ...
}
</script>
{% endif %}
```

**教训**：
- ❌ Organization Schema 应该**只在首页**出现
- ✅ 每个子页面应该有自己对应的 Schema（WebPage、SoftwareApplication 等）
- ✅ 用 `page.url` 条件控制不同 Schema 的输出范围

---

### 坑 25：首页不应渲染面包屑导航

**问题**：面包屑导航在 `base.njk` 中渲染，但首页 (`page.url == '/'`) 也渲染了一个无意义的面包屑：`<nav class="breadcrumb"><a href="/">首页</a></nav>`。

**修复**：
```njk
{% if page.url != '/' and (page.url | indexOf('/index.html')) == -1 %}
<nav aria-label="Breadcrumb" class="breadcrumb">
  <a href="/">首页</a>
  {% if tool %} › <span>{{ tool.title }}</span>{% endif %}
</nav>
{% endif %}
```

**教训**：面包屑导航对首页和各列表页（/tools/index.html 等）都无意义，必须排除。

---

### 坑 26：SearchAction JSON-LD target 必须用 EntryPoint 对象

**问题**：SearchAction 的 `target` 字段直接用字符串 URL，不符合 Schema.org 规范。

**错误写法**：
```json
"target": "{{ config.url }}/tools/?q={search_term_string}"
```

**正确写法**：
```json
"target": {
  "@type": "EntryPoint",
  "urlTemplate": "{{ config.url }}/tools/?q={search_term_string}"
},
"query-input": "required name=search_term_string"
```

**教训**：Google 结构化数据文档明确要求 SearchAction 使用 `EntryPoint` 对象格式。

---

### 坑 27：JSON-LD 中空数组字段无意义（sameAs: []）

**问题**：`sameAs: []` 空数组对搜索引擎毫无价值，反而可能被视为低质量标记。

**修复**：直接移除空数组字段。如果有实际社交媒体链接，再填入。

---

### 坑 28：JSON-LD 中 trailing comma 导致无效 JSON

**问题**：
```json
"offers": {
  "@type": "Offer",
  "price": "0",
  "priceCurrency": "CNY"   ← 这里多了一个逗号
}
```

**表现**：Google Rich Results Test 报错 "JSON parse error"。

**修复**：移除最后一个属性后的逗号。

**教训**：JSON-LD 是严格的 JSON，不允许 trailing comma。手写 JSON 时特别注意。

### 坑 29：config.json 有 `ogImage` 字段但模板未引用

**问题**：`config.json` 中定义了 `ogImage` 字段，但 `base.njk` 的 `<head>` 中没有对应的 `<meta property="og:image">` 标签。

**修复**：
```njk
{% if config.ogImage %}
<meta property="og:image" content="{{ config.ogImage }}">
{% endif %}
```

**教训**：数据字段和模板引用必须同步维护，否则字段变成"死代码"。
