# 数据库容量分析 — CF Guardian

## 一、Cloudflare D1 Free Tier 限制

| 指标 | Free Tier |
|------|-----------|
| 数据库大小 | **5 MB** |
| 每日读取 | 5,000,000 行/天 |
| 每日写入 | 100,000 行/天 |
| 数据库数量 | 200 |

## 二、Turso (LibSQL) Free Tier 限制

| 指标 | Free Tier |
|------|-----------|
| 存储空间 | **8 GB** |
| 读取 | 1,000,000 行/小时 |
| 写入 | 30,000 行/小时 |
| 位置 | 3 个边缘位置 |
| 有效期 | 永久免费 |

## 三、数据量推算

### 场景：商业产品对标（多用户 SaaS）

假设上线后有：
- **Free 用户**: 100 人 × 1 站 = 100 站
- **Starter 用户**: 30 人 × 3 站 = 90 站
- **Pro 用户**: 10 人 × 10 站 = 100 站
- **Agency 用户**: 2 人 × 30 站 = 60 站
- **总计**: ~350 个监控站点

### 每日数据产生量（按每日 1 次扫描）

| 表 | 每站每次扫描新增行数 | 每日总行数 (350站) | 每行估算大小 | 每日增量 |
|----|---------------------|-------------------|-------------|---------|
| scans | 1 | 350 | ~2 KB (含 issues_json) | ~700 KB |
| alerts | ~8 (平均每站8个问题) | 2,800 | ~500 B | ~1.4 MB |
| geo_checks | ~15 (15项GEO检查) | 5,250 | ~300 B | ~1.6 MB |
| api_usage | ~5 | 1,750 | ~150 B | ~262 KB |
| **每日合计** | | **10,150 行** | | **~4 MB/天** |

### 月度数据量

| 指标 | 数值 |
|------|------|
| 每月新增行数 | ~300,000 行 |
| 每月新增空间 | ~120 MB |
| **D1 Free 5MB 能撑多久** | **~1 天** ❌ |
| **Turso Free 8GB 能撑多久** | **~66 天（2个月）** ✅ |

### 即使只有 10 个付费用户（30站）

| 指标 | 数值 |
|------|------|
| 每月新增行数 | ~9,000 行 |
| 每月新增空间 | ~3.6 MB |
| **D1 Free 5MB 能撑多久** | **~1.5 天** ❌ |
| **Turso Free 8GB 能撑多久** | **~222 个月（18年）** ✅ |

## 四、结论

### D1 Free Tier 完全不够用

**5 MB 的数据库大小限制意味着：**
- 即使只有 1 个用户、1 个站点，运行 3-5 天就会爆满
- alerts 表和 geo_checks 表是主要占用者
- 无法做商业产品

### Turso (LibSQL) 是正确选择

**8 GB 免费空间：**
- 350 站点规模可以跑 2 个月
- 配合数据清理策略（保留 90 天），可以长期运行
- 30k 写入/小时足够应对扫描队列
- Cloudflare Workers 有官方 SDK (`@libsql/client`)

### 推荐架构

```
Cloudflare Workers (Free)
  ├── Turso LibSQL (Free, 8GB)  ← 主数据库
  ├── Cloudflare Queues (Free)   ← 异步扫描队列
  ├── Cloudflare Cron (Free)     ← 每日定时扫描
  └── Cloudflare KV (Free)       ← 缓存/会话 (可选)
```

### 需要迁移的内容

1. `wrangler.jsonc` — 移除 D1 binding，添加 Turso 环境变量
2. `src/db/schema.ts` — 从 D1 驱动改为 Turso `@libsql/client`
3. 所有 `env.DB.prepare()` 调用 — 改为 Turso async API
4. 添加数据清理 cron（保留最近 90 天扫描数据）
