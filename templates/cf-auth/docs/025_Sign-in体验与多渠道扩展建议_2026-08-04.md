# 025 Sign-in 体验与多渠道扩展建议

> 日期：2026-08-04  
> 范围：`/sign-in`（协议页）+ `/admin/login`（Admin 门禁）  
> 样本深链：`/sign-in?callbackURL=%2Fadmin%2Fblocklist`

## 1. 现状（实现事实）

| 层 | 路径 | 职责 |
|----|------|------|
| 协议登录 | `GET /sign-in`（`src/routes/pages.ts`） | 邮箱 + 动态社交；OAuth 回流与 Admin `callbackURL` 分流 |
| Admin 门禁 | `/admin/login`（Vue） | 探测 session / 引导去 sign-in / credential 折叠 |
| 社交注册表 | `src/lib/social-providers.ts` | google/github/microsoft/apple/discord/gitlab；密钥齐全才启用 |
| 回跳安全 | `safePath` | 仅同 origin 相对路径，防 open redirect |

深链流（已实现）：

1. 未登录访问 `/admin/blocklist` → 守卫 → `/admin/login?redirect=/admin/blocklist`
2. 点社交 → `/sign-in?callbackURL=/admin/blocklist`
3. 登录成功 → `postLogin = /admin/blocklist`（**不是**拼进 authorize）

## 2. 产品定位（建议长期遵守）

- **`/sign-in` = 全站身份枢纽**（RP OAuth 回流、Admin、将来 passkey/magic link 都挂这里）
- **`/admin/login` = 运维门禁说明页**（白名单提示、会话复用、次要 credential），**不要**在 Admin 内再嵌一套完整社交 OAuth 表单
- 会话 Cookie **仅 auth 域**；业务 RP 永远授权码 + PKCE（已有架构，勿为「便利」共享 Cookie）

## 3. 易用性 / 便利性（已部分落地 +  backlog）

**本轮已落地：**

- Admin 深链场景化标题/徽章/目的地展示
- 社交主路径；Admin 下邮箱折叠且隐藏「注册」
- 加载态、更可读错误（429/封禁/密码）
- 硬删除确认须键入 `DELETE`（Admin 表，防灾难）

**建议 backlog（未实现，勿当已有）：**

| 优先级 | 项 | 理由 |
|--------|----|------|
| P1 | 登录成功后若已有 Admin session，sign-in 可短页「继续进入 {dest}」 | 少一次无意义点击 |
| P1 | 社交按钮官方字形/图标 + 稳定视觉顺序 | 降低「这是不是钓鱼」感 |
| P2 | Passkey / WebAuthn 作为管理员首选 | 运维无密码、抗钓鱼 |
| P2 | Magic link 仅白名单邮箱 | 无密码恢复路径 |
| P3 | 记住上次成功的 provider（localStorage） | 单管理员场景提速 |
| P3 | 中英 locale 与 brand 槽位 | 多产品共用 IdP |

## 4. 扩展更多社交渠道（最佳实践）

现有注册表扩展成本低：**加 `SOCIAL_PROVIDER_REGISTRY` 一项 + 配 env**，登录页自动出按钮。

建议顺序（平台 IdP，非 C 端 App 内嵌）：

1. **已开**：Google、GitHub（开发者 / 运维友好）
2. **企业**：Microsoft Entra（`MICROSOFT_*`；注意 tenant 单/多租户配置）
3. **消费/社区**：Apple（密钥轮换重）、Discord（社区产品）
4. **自建**：GitLab.com vs self-hosted 需 `issuer` 扩展点

原则：

- **密钥双齐才启用**（已实现）— 禁止半开按钮
- **`ENABLED_SOCIAL_PROVIDERS` 白名单**控制面，避免一次堆 6 个按钮
- **account linking**：已启用 `trustedProviders` + 同邮箱；扩展 IdP 时同步进 trusted，并保持 `allowDifferentEmails: false`
- **回调 URL 文档化**：每个 IdP 控制台填 `{BETTER_AUTH_URL}/api/auth/callback/{id}`
- **不要**把「微信/支付宝」当第一波：需公众号/开放平台资质与移动端 SDK，和当前 Web IdP 路径不同，应单独立项

## 5. 与 Admin 深链相关的体验红线

- `callbackURL` 必须继续走 `safePath`（禁止 `//evil` / 外域）
- Admin 与 OAuth 回流互斥判断：`response_type`+`client_id` 才进 authorize
- 登录页 **不要**对 Admin 深链开放无限制 sign-up（本轮 Admin 场景已隐藏注册）
- 真正权限永远在服务端 `ADMIN_*`，前端 flag 只是 UX

### 文案分层（避免混为一谈）

| 用户看到的 | 实际由什么决定 | 不是什么 |
|------------|----------------|----------|
| 「管理后台登录」场景、不提供注册 | URL：`callbackURL`（或 `redirect_uri`）指向 `/admin`… → `isAdminReturn` | **不是** `ADMIN_EMAILS` 开关文案 |
| 登录成功后能否进 `/admin` API | 服务端 `ADMIN_EMAILS` / `ADMIN_USER_IDS`（或 `ADMIN_API_KEY`） | **不是**「在登录页注册过」 |
| 邮箱密码表单是否出现 | `EMAIL_PASSWORD_ENABLED` + meta | 与是否 Admin 深链独立 |

**对外措辞建议（已部分落地）：** 用户面少写「白名单 / RP / IdP / Phase A」；权限层称「管理员名单」并点名 `ADMIN_EMAILS`；自动化称「请求头 API Key」，避免与登录密码混淆。
