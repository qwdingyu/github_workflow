## 1. 架构定位（必须先钉死）

### 1.1 双系统不要串

| 系统 | 域名（生产） | Admin 含义 | 登录态 |
|------|--------------|------------|--------|
| **cf-auth 平台 Admin** | `auth.eforge.xyz` | 管 OAuth client、IdP 用户/会话、审计 | Better Auth **HttpOnly cookie** + `ADMIN_*` 白名单 |
| cf-lottery 业务/租户 Admin | `lucky.eforge.xyz` 等 | 管活动、奖品、参与、兑换码等 | 业务 JWT / OAuth 换票后的业务会话 |

**【文档】** `019` §0 已写明同一边界。  
**【架构】** cf-auth 是**平台级 IdP**；业务租户 RBAC 在各 RP（`013` §「明确不做」）。

### 1.2 本后台目标用户与数据规模假设

| 项 | 代码/文档依据 | 含义 |
|----|---------------|------|
| 目标用户 | `013` §5.1：平台维护者，非每个租户管理员 | 管理员人数预期很少 |
| 鉴权模型 | `admin-auth.ts`：env 白名单，不做 lottery L2/L3 | 保持简单是有意设计 |
| Client 治理 | `oauthClient` 全表 Admin 列表 | RP 数量通常远小于活动/卡密行数 |
| 用户表 | 仅 BA `user`，无业务档案 | 用户增长来自各 RP 登录，但**处置能力**仍很薄 |

**【建议】** 批量与黑名单设计必须按「少管理员、高危误操作、IdP 全局影响」建模，而不是按 lottery「多运营、多行表」建模。

## 2. 现状能力清单（仅陈述已实现）

### 2.1 后端 API（`src/routes/admin.ts`）

全部挂在 `/api/admin`，且 `r.use("*", requirePlatformAdmin(auth))`。

| 方法 | 路径 | 行为摘要 |
|------|------|----------|
| GET | `/health` | 服务名 + users/clients/sessions **COUNT** |
| GET | `/clients` | 分页 + `q` 搜 name/clientId；DTO 脱敏 |
| GET | `/clients/:clientId` | 单条脱敏 |

| PATCH | `/clients/:clientId` | name / redirect_uris / skip_consent / require_pkce / disabled |

## 3. 安全审查（攻击面与已控项）

### 3.1 已落实且有代码/测试支撑的控制

| 控制 | 位置 | 证据 |
|------|------|------|
| 管理面默认关闭 | 未配 ADMIN_* → 503 | `requirePlatformAdmin`；测试 |
| 管理员 ≠ 任意登录用户 | 白名单 | `isWhitelisted` |
| 开放 create-client 收口 | 中间件 | `blockOpenClientRegistration`；测试 |
| Secret 不进列表/详情 | DTO | `toAdminClientDto` 无 secret，仅 `hasSecret` |
| API Key 比较抗时序 | `timingSafeEqual` | `admin-auth.ts` |
| 搜索通配转义 | `likeContains` + ESCAPE | `016`、`search.ts`、测试 `q=%` |
| SPA 不抢协议页 | 仅 `/admin*` 静态 | `016` |
| 写操作审计（client/session） | `writeAdminAudit` | create/patch/rotate/revoke |
| 会话列表不回传 token | select 显式列 | `admin.ts` sessions GET |
| 账号关联限制 | `allowDifferentEmails: false` 等 | `auth.ts` |
| 动态注册关闭 | `allowDynamicClientRegistration: false` | `auth.ts` |

### 3.2 真实风险（按「本架构下可利用/可误伤」排序）

#### R1 — 会话吊销不完整（运营止血缺口）**【代码】**

`DELETE /api/admin/users/:userId/sessions` 实现为：

```ts
await db.delete(session).where(eq(session.userId, userId));
```

同文件**不**更新 `oauthRefreshToken` / `oauthAccessToken`。

**【测试】** `admin-api.test.ts` 只断言吊销后 **session 列表长度为 0**，不断言 refresh。

**影响（逻辑推论，非已复现 PoC）：**  
在 OAuth 2.1 模型下，RP 持有的 refresh 与 IdP 浏览器 session 是不同凭证。仅删 session 满足「踢掉 auth 域 Cookie 会话」，**不自动等于**「该用户在所有 RP 上无法续期」。  
是否仍能用 refresh 换 token，取决于 Better Auth oauth-provider 在校验 refresh 时是否强依赖未删 session / `revoked` 字段——**本仓库未写回归测试，不得假装已验证**。

**【建议】** 将「强制下线」定义为显式多步事务（实施时补测）：

1. 删或失效 `session`  
2. 将该 `userId` 的 `oauthRefreshToken` 置 `revoked` 或删除  
3. 可选清理未过期 `oauthAccessToken`  
4. audit meta 记录各表影响行数  

在补测前，UI 文案不宜写「已从所有应用退出」。

#### R2 — 无用户封禁 / 登录黑名单**【代码】**

- `user` 表字段：id/name/email/emailVerified/image/timestamps — **无** banned  
- 无 `blocklist` / `auth_blocklist` 表  
- 登录与 authorize 路径（`app.ts` 限流后进 `auth.handler`）**无**平台级拒绝钩子  

因此：即使用户 session 被删，**只要仍能通过 Google/邮箱再次登录**，即可回到 IdP（若仍在 `ADMIN_EMAILS` 则连 Admin 也能回）。  
对普通用户滥用/盗号，管理员**没有**持久拒绝手段。

`audit` 中的 `user.disable` **不能**当作已有功能。

#### R3 — `ADMIN_API_KEY` 全权且审计主体为空**【代码】**

- Key 通过即 `AdminActor.userId/email = null`  
- 与 session 管理员**同一套** client 写、session 删权限  
- 无 key 指纹写入 audit  

泄露 Key ≈ 脚本级全管理面。这是显式设计（CI/运维），不是实现 bug，但是**最高价值机密**之一（与 `BETTER_AUTH_SECRET` 同级运维纪律，见 `019`）。

**【建议】** 轮换纪律；audit meta 记 key 指纹；长期减少「长期万能 Key」、改短期会话或独立只读/只写范围（若做范围，需新产品设计，当前无 RBAC 字段）。

#### R4 — `skip_consent` 无第一方约束**【代码】**

`POST/PATCH /clients` 接受任意 `skip_consent: true`，只校验 redirect 为合法 URL 数组（`new URL`），**不**校验是否第一方域名。  
误配会导致该 client 授权时跳过同意页（产品风险 + 钓鱼 RP 风险，取决于谁能改 client——仅管理员）。

#### R5 — `redirect_uris` 校验偏弱**【代码】**

`parseRedirectUris`：非空数组 + 每项 `new URL` 成功。  
**不**强制 https、**不**禁内网以外的任意主机、**不**做组织域名 allowlist。  
管理员手滑加恶意回调即生效——属**特权误操作**面，不是匿名攻击面。

#### R6 — Admin 写限流不覆盖会话 DELETE**【代码】**

create/patch/rotate 有 `adminWrite` 桶；`DELETE .../sessions` 与 `DELETE /sessions/:id` **无**限流。  
在已窃取管理员 session 的前提下，可快速批量点杀会话（前端尚无批量，但 API 可被直接打）。优先级低于 R1/R2，但是加固点。

#### R7 — `rate_limit_log` 清理未挂载**【代码】**

`cleanExpiredRateLimits` 存在，**无** cron/启动调用。  
长期：表增大 → 限流子查询变慢或存储上涨。属可靠性/运维，不是直接 RCE。

#### R8 — 前端 flag 可伪造**【代码】【文档】**

已知可接受：只影响 SPA 路由是否先渲染，API 仍 401。不必当漏洞修，但**禁止**未来改成「前端存 Admin 权限 token」。

### 3.3 匿名攻击者视角（摘要）

在 **ADMIN_* 已配置、create-client 已收口、限流开启** 的前提下：

| 路径 | 匿名可行性（基于代码逻辑） |
|------|----------------------------|
| 直接调 `/api/admin/*` | 无 Key/白名单 session → 401 |
| 注册普通用户再 create-client | 403 |
| 未配 ADMIN 时撞管理面 | 503（且不能当管理员用） |
| 撞 sign-up/sign-in/authorize/token | 有 IP 限流，可被拖慢不能根治 bot |
| 打穿的主路径 | 盗用白名单管理员 IdP 账号、泄露 API Key、或社会工程改 env |

**结论：** 当前更大风险是 **特权凭证与运维误操作 + 止血链不全**，不是「Admin 未鉴权裸奔」。

## 4. 运营视角：流程是否闭环

| 运营场景 | 今天能否完成 | 缺口 |
|----------|--------------|------|
| 接入新 RP | ✅ 后台建 client，复制一次 secret | 无 env 片段导出；TRUSTED_ORIGINS 仍要改 env（`013` P1-7） |
| 临时下线 RP | ✅ `disabled=true` | 禁用后已发 refresh 行为未在本仓库测清；无批量 |
| 密钥轮换 | ✅ rotate-secret（硬轮换） | 需与 RP 发版窗口对齐；禁止「顺手批量轮换」 |
| 用户盗号应急 | ⚠️ 可删 session | 无封禁；refresh/access 未在 Admin 处理；文案易过度承诺 |
| 垃圾用户/滥用 | ❌ | 无 blocklist |
| 追责 | ⚠️ audit 可按 action 滤 | 无时间范围/target 搜索/导出；API Key 操作者为空 |
| 多 client 日常治理 | ⚠️ 单行操作 | 无多选；client 少时仍可接受 |

Dashboard 三计数对「要不要扩容/是否被刷」帮助有限——属体验债，不是安全漏洞。

## 5. 「黑名单」：为何不能照搬 lottery

### 5.1 lottery 事实（对照仓库）

| 项 | 位置 | 行为 |
|----|------|------|
| 表 | `cf-lottery` `lottery_blacklist`：`tenantId + identityValue` 唯一 | 租户级 |
| API | `admin-lottery-tenant-ops.ts`：GET/POST/DELETE `/blacklist` | 校验邮箱；写租户审计 |
| 前端 | `AdminBlacklistView.vue` | 单条添加/删除，**无** `useTableSelection` |
| 运行时 | `participation.ts` 等在**参与**路径查黑名单 | 拦的是活动参与，不是 IdP 登录 |

### 5.2 cf-auth 若「抄表不抄挂载点」会发生什么

| 错误做法 | 后果 |
|----------|------|
| 只做 Admin CRUD，登录/authorize 不查 | **假功能**，运营以为封了 |
| 按 `tenantId` 建表 | cf-auth **无**租户模型，字段无意义 |
| 与 lottery 共用一套「邮箱黑名单」服务 | 跨产品耦合，权限与数据边界破坏（`013` 禁止 Admin 做进 lottery） |

### 5.3 【建议】平台级 Blocklist 目标语义（未实现）

**名称建议：** `auth_blocklist`（或 `platform_blocklist`），业务自管表，**不**进入 `authSchema`（与 `admin_audit_log` 同一分层）。

| 字段（建议） | 说明 |
|--------------|------|
| id | 主键 |
| type | `email` \| `user_id` \|（可选）`email_domain` |
| value | 规范化（email 小写） |
| reason | 运营备注 |
| created_by_user_id / email | 可空（API Key） |
| created_at | |
| expires_at | 可选 |

**强制挂钩点（缺一不可）：**

1. Admin API 增删查 + audit（`blocklist.add/remove`）  
2. 在 **签发新 session / 完成社交登录回调 / oauth authorize 同意后发码** 之前查询（具体挂 BA hook 还是 `app.ts` 中间件，实施时选一处，避免双源）  
3. 封禁时**级联**执行与「强制下线」同一套会话+令牌处理  
4. 对外错误文案固定、不暴露「黑名单」细节；对内 audit 可记  

**明确不优先：** 批量物理删除 `user` 行（破坏 `sub` 稳定与 RP 映射、审计完整性）。封禁优于删除。

**与 `user.disable` 类型名：** 落地时可映射为 blocklist 写入，或真正加列；需在实施记录里二选一，避免两套真理。

|------|------|------------|
| `useTableSelection` | `cf-lottery/frontend/src/composables/useTableSelection.ts` | 当前页可选 id；`isSelectable`；翻页 watch 过滤不可见选中；全选当前页；shift 范围选 |
| 批量删活动 | `AdminLotteryView.vue` `batchDeleteDraws` | 确认文案含数量；`batchOperating` 锁；**for 循环调单条 API**；success/failed 计数；`clearSelection` + reload |
| bulk-bar | `AdminLogsView.vue` 等 | 仅 `selectedCount > 0` 显示；复制/导出与危险删除分离 |
| 确认框 | 两边皆有 `ConfirmDialog` + `useConfirmDialog` | cf-auth clients/sessions 已用 |

**【代码】** cf-auth **尚未**拷贝 `useTableSelection`。

### 6.2 lottery 中**不应**当 IdP 真理的部分

| 项 | 说明 |
|----|------|
| `AdminLogsView` 的 `batchDeleteAdminLogs` | 前端直接 `throw new Error('当前后端暂未开放...')`——说明**批量删审计在 lottery 也未当真开放** |
| 活动/卡密/兑换码 batch | 业务表批量写入，与 oauth client 治理无关 |
| 租户黑名单 UI | 无多选；且语义是参与拦截 |

### 6.3 【建议】cf-auth 批量能力矩阵（防灾难）

| 页面 | 建议多选 | 允许的批量动作 | 禁止 |
|------|----------|----------------|------|
| Clients | 是 | 批量 **禁用/启用**（串行 PATCH，上限建议 ≤20） | 批量删 client；批量轮换 secret；批量改 redirect |
| Users | 是 | 批量 **封禁**（依赖 §5）；批量 **下线**（依赖 R1 完整语义） | 批量删用户 |
| Sessions | 是 | 批量下线当前页选中 session | 「一键全站所有用户下线」无二次确认 |
| Audit | 可选 | **仅**复制/CSV 导出选中行 | **任何删除** |
| Blocklist（若做） | 是 | 批量移除；导入预览后小批量添加 | 无预览的超大导入 |

### 6.4 批量实现铁律（与 lottery 对齐且更严）

1. **前端选择范围 = 当前页可见且 selectable**（`useTableSelection` 默认行为）；不做跨页隐形全选。  
2. **后端初期优先串行调用已有单条 API**（与 `batchDeleteDraws` 相同），保证每条 audit、失败可计数。  
3. 若未来提供 `POST /api/admin/.../batch`：必须 `ids.length` 上限、逐条鉴权结果、**禁止**无 where 的整表更新。  
4. 所有危险批量：`ConfirmDialog` 文案包含 **数量 + 不可逆/影响面**（禁用 client 要写明「新授权失败」；不要写未验证的「RP 立即全下线」除非 R1 已测）。  
5. `batchOperating` 期间禁用选择与按钮，防重复提交。  
6. **审计日志禁止删除 API**（与 `audit.ts` 注释「只追加、不提供删除 API」一致——**【代码】** 当前确实无删除路由，必须保持）。

## 7. 最佳实践（结合本仓库约束）

### 7.1 继续保持的架构选择

| 实践 | 依据 |
|------|------|
| 平台 Admin 留在 cf-auth，不进 lottery | `013` |
| UI  primitives 继续拷贝 lottery（css/组件），业务页自写 | `015` |
| 管理员 = env 白名单，不上完整 RBAC | `admin-auth.ts`、`013` §5.4 |
| Secret 只展示一次；DTO 永不回传 | `oauth-client-dto.ts`、create/rotate 响应 |
| 动态注册关闭 + create-client 收口 | `auth.ts`、`016` |
| 文档与事故知识进 docs，不靠聊天 | `018`/`019` |

### 7.2 运维纪律（无代码也可执行）

1. `ADMIN_EMAILS` 仅个人工作账号，IdP 侧开 2FA。  
2. `ADMIN_API_KEY` 不进前端、不进聊天、不进 RP 仓库；与人类登录密码分离（`019`）。  
3. `skip_consent` 仅第一方 RP；变更看 audit。  
4. 轮换 client secret / `BETTER_AUTH_SECRET` 走窗口与清单（`019` JWKS 教训）。  
5. 生产变更 client 前确认 `redirect_uris` 与 RP 配置一致。  

### 7.3 推荐实施阶段（仍为【建议】，非已排期承诺）

| 阶段 | 内容 | 依赖/验收 |
|------|------|-----------|
| **P0 止血** | 完整下线（session + refresh±access）+ 平台 blocklist + 登录/authorize 拒绝 + 单测 | 无 blocklist 不宣称「封禁」；有测才改 UI 文案 |
| **P1 批量（安全动作）** | 拷贝 `useTableSelection`；clients 批量启停；users 批量下线/封禁；串行+上限+确认 | 建立在 P0 语义上 |
| **P2 运营体验** | audit 导出与时间/target 过滤；dashboard 有意义计数；redirect/https 与 skip_consent 服务端约束；rate_limit 清理挂载 | 不引入删审计、不引入删用户 |
| **明确不做** | 公网 DCR；Admin 进 lottery；企业 IAM；无确认 bulk 删 client；审计可删 | `013` + 本文 §6.3 |

## 9. 结论（一句话）

**cf-auth 平台 Admin 在鉴权收口、client 治理、审计与限流上已达到「可登录运维的 L0」；尚未达到「安全事件可封禁、可令牌级止血、可安全批量」的 L1。**  
黑名单必须做成 **IdP 级 blocklist + 运行时强制执行**，禁止假装 lottery 参与黑名单可用。  
批量必须 **只借 lottery 的选择与确认骨架**，动作白名单化，串行、限量、可审计，禁止批量删 client/用户/审计。
