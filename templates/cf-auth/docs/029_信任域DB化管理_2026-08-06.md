# 029 信任域 DB 化管理（trusted_origin）

## 1. 目标与验收

**目标**：信任域由「env 静态配置」升级为「env 部署锚 + DB 运营扩展」双源合并，DB 部分可在 Admin 页面热增删，无需 redeploy。

**验收定义**（全部满足才算完成）：

- [x] 新增 `trusted_origin` 表（幂等迁移，已有库可平滑升级）——`src/db/schema.ts` + `src/db/migrate.ts`；`scripts/migrate.mjs` 实测建表（14 表 + 索引）
- [x] CORS 与 Admin CSRF 均按 `env ∪ DB(enabled)` 解析，热生效（写后立即生效）——`app.ts` CORS async 回调 + `admin.ts` `assertAdminWriteOrigin`；无缓存，写后即时生效
- [x] Admin 页面 `/admin/trusted-origins` 可增删/启停信任域，全程审计——`AdminTrustedOriginsView.vue` + 路由 + 菜单；审计 `trusted_origin.create/update/delete`

## 2. 信任域模型（冻结）

```
┌─ 业务信任域（purpose=cors）──────────────────────────────────┐
│  ① env TRUSTED_ORIGINS        —— 部署锚（改 env + redeploy）│
│  ② DB trusted_origin(cors)    —— 运营态（Admin 热增删）     │
│  ③ baseURL origin             —— 强制并入（BA 需要）        │
│  用途：CORS 响应头、Better Auth trustedOrigins              │
├─ 管理信任域（purpose=admin）─────────────────────────────────┤
│  ① env ADMIN_TRUSTED_ORIGINS  —— 部署锚                     │
│  ② DB trusted_origin(admin)   —— 运营态                     │
│  ③ 同源 = baseURL origin      —— 运行时放行（不依赖列表）   │
│  用途：Admin 写请求 CSRF Origin 校验                        │
└───────────────────────────────────────────────────────────────┘
```

- **env 是部署锚**：永远生效，DB 无法删除/覆盖；保证任一环境即使 DB 为空也能工作。
- **DB 是运营扩展**：加新 RP 的信任域不再改 env，Admin 页面操作即热生效。
- **同源保护**：`baseURL` origin 在解析层强制并入，防止误删导致管理面自锁。
- 两个 purpose 完全隔离：业务 RP 域**不会**自动获得管理写权限（延续上一轮 CSRF 解耦设计）。

## 3. 数据模型

```sql
CREATE TABLE IF NOT EXISTS "trusted_origin" (
  id TEXT PRIMARY KEY NOT NULL,
  origin TEXT NOT NULL,            -- 规范化：scheme://host[:port]，小写，无尾斜杠/路径/query
  purpose TEXT NOT NULL,           -- 'cors' | 'admin'
  enabled INTEGER NOT NULL,        -- 1=生效 0=停用（软下线，不删行）
  created_by_email TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS trusted_origin_purpose_origin_uniq
  ON "trusted_origin" (purpose, origin);   -- 同 purpose 下 origin 唯一
CREATE INDEX IF NOT EXISTS trusted_origin_enabled_idx
  ON "trusted_origin" (enabled);
```

- 列命名沿用平台运维表（`admin_audit_log` / `auth_blocklist`）的 snake_case 风格。
- 不进 Better Auth adapter（`authSchema` 不含本表）。
- `enabled=0` 保留行（可恢复），而非删行——信任域历史可审计。

## 4. origin 校验与规范化（安全关键）

`normalizeOrigin(raw)` 规则（`src/lib/trusted-origin.ts`）：

- 仅接受 `https://` 与 `http://localhost` / `http://127.0.0.1`（http 仅限本机回环，防明文信任域被中间人利用）
- 无用户名/密码（拒绝 `https://user:pass@host`）
- 无路径、query、hash（信任域是 origin 级，不是 URL 级）
- 规范化输出用 `URL.origin`：host 小写、省略默认端口、去尾斜杠

```text
合法：https://lucky.eforge.xyz        → https://lucky.eforge.xyz
      http://localhost:8787            → http://localhost:8787
      HTTPS://AUTH.EFORGE.XYZ/         → https://auth.eforge.xyz
非法：https://lucky.eforge.xyz/path    （含路径）
      http://shop.eforge.xyz           （非回环 http）
      https://user:pass@x.com          （含凭据）
      https://x.com?a=1                （含 query）
```

## 5. API 契约（/api/admin/trusted-origins）

均需平台管理员 + 写操作限流 + CSRF（admin 路由统一中间件已覆盖）。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/trusted-origins` | 列表；`purpose` 筛选；`limit/offset`；env 部署锚只读展示（`envTrusted`/`envAdminTrusted` 字段，不可改） |
| POST | `/api/admin/trusted-origins` | 创建 `{ origin, purpose }`；校验+规范化；重复→409 语义（400 带原因）；写审计 `trusted_origin.create` |
| PATCH | `/api/admin/trusted-origins/:id` | 仅 `enabled`（软启停）；origin 不可改（改=删+建，防绕过审计）；审计 `trusted_origin.update` |
| DELETE | `/api/admin/trusted-origins/:id` | 硬删行；审计 `trusted_origin.delete`；删除后该 origin 立即失去信任 |

错误语义：`invalid_origin` / `duplicate` / `not_found` / `invalid_purpose`，统一 `fail(c, msg, 400|404)`。

## 6. 解析规则（env ∪ DB 合并，写后立即生效）

```text
resolveTrustedOrigins(db, purpose, envList) =
    normalize(envList) ∪ { origin | trusted_origin WHERE purpose AND enabled } ∪ { baseURL origin }
```

- 每次请求解析（小表，无缓存）——与 rate_limit 每写请求读 DB 的先例一致；正确性优先。
- 写操作（POST/PATCH/DELETE）成功即影响下一次解析，无需失效缓存（无缓存）。
- 读取优化：CORS 中间件仅在**有 Origin 头**时读 DB（同源/无 Origin 请求零额外开销）；Admin CSRF 仅**非 baseURL 的 Origin** 才查 DB 白名单。

## 7. 安全设计

- 写路径：Admin 鉴权（requirePlatformAdmin）+ CSRF（assertAdminWriteOrigin）+ 写限流（enforceAdminWriteLimit）+ 审计（writeAdminAudit）——与 clients/blocklist 同纪律。
- 读取路径：信任列表仅服务端使用，不向非管理员暴露明文（`/api/admin/health` 只暴露 `firstPartyRedirectHosts`，不含 trusted origins）。
- 防自锁：解析层强制并入 baseURL origin；CSRF 同源判断不依赖 DB。
- 防绕过：origin 不可编辑（防把 `lucky.eforge.xyz` 改写成 `evil.example.com` 不留痕）；删除是硬删 + 审计，UI 需确认。
- DB 值本身是信任边界：可被管理权限写入者篡改——由 ADMIN_* 白名单 + 审计兜底（同现有表）。

## 11. 明确不做（防过度设计）

- 不做 trusted origin 的分页交互优化（当前小表 limit/offset 即可）
- 不做 TTL 缓存/失效（每请求读小表，量级可忽略；有性能证据再优化）
- 不做 origin 通配符/子域匹配（`*.eforge.xyz`）——通配信任域违背最小权限，如确有需要单独评估
- 不把业务 RP 的 redirect_uri 校验移入本表（redirect 属于 OAuth client 的精确登记，见 oauthClient.redirectUris）
