# 013 多项目接入能力评估与 Admin 增强路线

> 日期：2026-08-03  
> 项目：cf-auth（`https://auth.eforge.xyz`）  
> 性质：**分析 + 决策 + 实施路线**（本文件不写业务代码）  
> 原则：不造轮子；Admin UI/组件/样式 **照抄 cf-lottery**；协议层继续用 Better Auth 官方能力

---

## 一、结论摘要（先读）

| 问题 | 结论 |
|------|------|
| 程序核心（IdP + Code+PKCE）是否可用？ | **是**。本地闭环 + 生产 smoke 已通过（docs/012）。Google 浏览器同意页卡顿优先查控制台 URI / 网络，非 Worker 崩溃。 |
| 是否已满足「多个项目」auth 接入？ | **协议层基本满足；运维与产品层不足。** 可同时服务多个 RP，但 client 生命周期靠脚本/手操，缺统一管理面。 |
| 是否还需要优化？ | **需要。** 优先：RP 接入规范、client 治理、限流/审计、TRUSTED_ORIGINS 运维、第一方 RP 模板。 |
| 是否需要简单 Admin 后台？ | **需要（轻量 L0–L1）。** 不做企业 IAM 控制台；做「OAuth client + 用户只读 + 会话/令牌运维」三块。 |
| Admin 技术选型 | **全部复用 cf-lottery 已有方案**：Vue3 + `AdminLayout` / `AdminModal` / `ToastContainer` / `admin.css` / `useAdminAuth` 模式；后端 Hono + Drizzle + 中文注释；**禁止**另起 UI 体系或自研 OAuth 协议。 |

**一句话：**  
cf-auth 已是可用的多 RP 身份中心；下一步不是再造认证协议，而是 **把「接第二、第三个项目」变成可复制、可审计、可在后台点几下完成的流程**。

## 二、当前能力盘点（已核实）

### 2.1 已具备（可作为多项目底座）

| 能力 | 现状 | 证据 / 位置 |
|------|------|-------------|
| 独立 IdP 域名 | 生产 `auth.eforge.xyz` + Turso | docs/011、012 |
| Outbound OAuth 2.1 | 授权码 + PKCE + refresh；动态注册关闭 | `src/lib/auth.ts` oauthProvider |
| Inbound 多社交 | 注册表驱动 google/github/… | `src/lib/social-providers.ts` |
| 发现文档 | AS / OIDC well-known | `src/app.ts` |
| 健康与 meta | health + 社交公开元数据 | `/api/health`、`/api/auth-meta/social` |
| 账号关联策略 | trustedProviders、禁异邮箱强合 | `createAuth` accountLinking |
| 数据边界 | auth 库只存身份与 OAuth；业务不直连 | schema 注释、docs/001 |
| 回归手段 | `npm run verify` + `npm run smoke:prod` | docs/012 |
| RP 参考实现 | lottery：`cf-auth-oauth.ts` + `useCfAuthLogin` + `idp-user-provision` | cf-lottery 源码 |

### 2.2 明确不具备 / 薄弱（影响多项目规模化）

| 缺口 | 影响 | 严重度 |
|------|------|--------|
| **无正式 Admin 面** | 创建/禁用 client、看 redirect、轮换 secret 靠脚本与 cookie | **高** |
| **无平台管理员模型** | 任意已登录用户可调 create-client（插件默认路径）→ 权限边界模糊 | **高** |
| **无 RP 接入标准包** | 第二项目只能抄 lottery 源码，易漏 PKCE/映射/env | **高** |
| **无审计日志** | 谁建了 client、谁禁用、谁吊销 token 不可追溯 | **中高** |
| **无限流 / bot 防护** | 邮箱注册、authorize、token 在公网暴露面偏裸 | **中高** |
| **TRUSTED_ORIGINS 手工** | 每加一个 RP 要改 secret/env 并 redeploy | **中** |
| **无 client 清单 API（受管）** | 运维不知道线上有哪些 RP | **中** |
| **SLO / 全局登出** | 多 RP 登出不同步（docs 已声明非目标） | **低（可延后）** |
| **邮件验证 / 找回密码** | 邮箱路径偏「开发便利」 | **中（若生产开 email）** |
| **workers.dev 与自定义域混用** | social callback 绑 baseURL，备用域易踩坑 | **低（文档已说明）** |

### 2.3 与「多项目接入」对照的验收定义

满足「多个项目 auth 接入」的**工程定义**（本仓库采用）：

1. **每个业务项目**是独立 OAuth Client（自己的 `client_id` / secret / redirect_uris）。  
2. **协议统一**：Authorization Code + PKCE；业务自签本地 session/JWT；**不**共享 cf-auth Cookie。  
3. **身份主键**：业务侧绑定 `(provider=cf-auth, sub)`，参考 lottery `idp-user-provision`。  
4. **信任边界**：`TRUSTED_ORIGINS` 含各 RP origin；redirect_uri 精确登记。  
5. **可运维**：能列出/禁用 client、轮换 secret、查用户与会话，有最小审计。  

| 定义项 | 今日状态 |
|--------|----------|
| 1 多 client 数据模型 | **已支持**（`oauthClient` 表 + 插件 API） |
| 2 协议统一 | **已支持** |
| 3 身份映射范式 | **lottery 有；未抽成跨项目模板** |
| 4 信任边界 | **机制有；运维靠手改 env** |
| 5 可运维 | **未满足**（脚本级） |

→ **结论：协议上已是多项目 IdP；产品与运维上仍是「单人运维 + 脚本」阶段。**

## 三、多项目接入：最佳实践契约（冻结）

### 3.1 双层 OAuth（不可混）

```text
用户 ──Inbound──▶ Google/GitHub/… ──▶ cf-auth session（仅 auth 域 Cookie）
业务站 ──Outbound──▶ cf-auth authorize/token/userinfo ──▶ 业务本地 JWT/session
```

禁止：

- 业务前端直接读 cf-auth session cookie 当登录态  
- 业务服务直连 Turso auth 库  
- 多个业务共用同一个 `client_id`（审计与吊销粒度会坏）

### 3.2 每个 RP 最小配置清单

| 项 | 说明 |
|----|------|
| `client_id` / `client_secret` | 仅服务端；secret 只展示一次 |
| `redirect_uris[]` | 精确 URL；含本地与生产 |
| `skip_consent` | **仅第一方** RP 可 true |
| `require_pkce` | 默认 true（公网浏览器客户端） |
| 业务 env | `CF_AUTH_ISSUER` / `CLIENT_ID` / `SECRET` / `REDIRECT_URI` / `ENABLED` |
| 业务建档 | `sub` → 本地 users + identities；email 链接仅当已验证 |

### 3.3 标准接入步骤（第二、第三个项目照抄）

```text
① 在 cf-auth 注册 OAuth client（Admin 或受控脚本）
② 业务 env 写入 issuer + client + redirect
③ 前端：authorize + PKCE + state（参考 useCfAuthLogin）
④ 后端：code → token → userinfo → 本地 provision → 发业务 JWT
⑤ TRUSTED_ORIGINS 增加业务 origin；redeploy cf-auth（或后续配置中心）
⑥ 跑业务侧 smoke：authorize → callback → session
```

### 3.4 推荐从 lottery 复用的模块（不要重写）

| lottery 路径 | 用途 |
|--------------|------|
| `src/lib/cf-auth-oauth.ts` | PKCE、authorize URL、换 token、meta |
| `src/services/idp-user-provision.ts` | 防接管建档 |
| `frontend/.../useCfAuthLogin.ts` + `cf-auth-session.ts` | 浏览器侧状态 |
| `frontend/.../AuthCallbackView.vue` | 回调页范式 |

长期：抽 **「cf-auth RP SDK / 模板仓库」**（薄封装，仍走 HTTP），避免每个项目复制粘贴漂移。  
短期：文档 + 示例 env 即可，**不**先做大而全 monorepo 包。

## 四、优化项优先级（不含 Admin 大块时的纯增强）

### P0 — 上线后仍应尽快做（安全 / 正确性）

| ID | 项 | 做法 | 验收 |
|----|-----|------|------|
| P0-1 | **Client 创建权限收口** | 仅平台管理员或 `ADMIN_API_KEY` 可 create/update；禁止「任意登录用户注册 client」成为生产常态 | 未授权 → 401/403；单测 |
| P0-2 | **Authorize / token / sign-up 限流** | 参考 lottery `rate-limit`；Workers 可用 KV 或内存+IP；Node 同逻辑 | 超限 429；单测 |
| P0-3 | **生产邮箱策略** | 参与端若只走社交：`EMAIL_PASSWORD_ENABLED=false`；若保留邮箱：补验证邮件与密码强度 | 配置文档 + health 反映 |
| P0-4 | **RP 接入 runbook** | 独立短文档或本节 3.3 外发为 `docs/01x_RP接入手册` | 新人按手册接通 demo |
| P0-5 | **Secret 轮换说明** | Google/GitHub 曾在聊天暴露风险；文档固定轮换步骤 | docs 已有提醒，运维执行 |

### P1 — 多项目体验（强烈建议与 Admin 同期）

| ID | 项 | 做法 |
|----|-----|------|
| P1-1 | Client 列表 / 详情 API（管理端） | 只读 + 脱敏；secret 永不回传 |
| P1-2 | 禁用 / 启用 client | `disabled=true` 立即拒绝新授权 |
| P1-3 | 轮换 client_secret | 生成新 secret、旧 secret 宽限期可选（先做硬轮换） |
| P1-4 | 用户只读检索 | email / id 查询；关联 account.provider |
| P1-5 | 吊销用户 session / refresh | 安全事件响应 |
| P1-6 | 管理审计表 | actor、action、target、ip、at |
| P1-7 | `TRUSTED_ORIGINS` 运维清单 | 文档化「加 RP 必改」；中期可配置表 + 热加载（慎） |

### P2 — 体验与生态

| ID | 项 |
|----|-----|
| P2-1 | 登录页 / consent 页视觉与无障碍（仍保持最小 HTML 亦可） |
| P2-2 | 官方 RP 模板（Node/Hono 或 Vue）独立小目录 `examples/rp-minimal` |
| P2-3 | 结构化日志 + 错误码字典（`invalid_client` 等对运维友好） |
| P2-4 | JWKS 轮换演练 |
| P2-5 | 可选：Microsoft 等注册表已列 IdP 的真实联调 |
| P2-6 | 跨 RP 登出（SLO）评估——**默认不做**，直到有明确产品需求 |

### 明确不做（防过度设计）

- 不做 Keycloak/authentik 级 IAM  
- 不做多租户「每个 SaaS 客户一个 IdP realm」（cf-auth 是**平台级** IdP；业务租户在各 RP）  
- 不做业务权限 / RBAC（那是 lottery 的 L2/L3）  
- 不开放公网 Dynamic Client Registration  
- Admin **不**重新设计组件库、**不**引入另一套 CSS 框架

## 五、Admin 后台：要不要做？做成什么样？

### 5.1 决策

| 选项 | 含义 | 裁决 |
|------|------|------|
| A. 不做，永久脚本 | 多项目后必然踩权限与审计坑 | **否** |
| B. 轻量 Admin（推荐） | client + 用户只读 + 会话/令牌 + 审计 | **是 → 采用** |
| C. 大而全 IdP 控制台 | 同意屏编辑器、品牌、组织、SCIM… | **否（超出瑞士军刀）** |

**采用 B。** 目标用户是 **平台维护者（你 / 运维）**，不是每个业务租户的管理员。

### 5.2 功能范围（MVP 必须 vs 可延后）

#### MVP（L0，建议 1 个小迭代内可交付）

| 模块 | 能力 | 备注 |
|------|------|------|
| 登录 | 仅平台管理员可进 `/admin` | 见 5.4 鉴权 |
| Dashboard | 用户数、client 数、近 24h 登录/发码粗计数 | 只读 SQL 聚合 |
| OAuth Clients | 列表、创建、编辑 redirect/name、禁用、skip_consent（第一方）、**显示一次** secret | 核心 |
| Users | 按 email/id 搜索、看 providers、禁用用户（可选） | 只读为主 |
| Sessions | 按用户列出 session、强制下线 | 安全运维 |
| Audit | 管理操作流水 | 最小表 |

#### L1（紧随）

- Refresh token 吊销  
- client secret 轮换向导  
- 导出 client 配置片段（给 RP 的 env 模板，无 secret 或仅 id）  

#### L2（有需求再做）

- 品牌化登录页配置  
- 组织 / 多管理员邀请  
- Webhook 通知（client 被禁等）

**Admin 信息架构（建议菜单，中文）：**

| 路由 | 页 | 对标 lottery 习惯 |
|------|-----|-------------------|
| `/admin/login` | 登录 | AdminLoginView |
| `/admin` | 总览 | AdminDashboardView 精简 |
| `/admin/clients` | OAuth 应用 | 表格 + 工具栏 + Modal 表单 |

- 使用既有 class：`admin-page` / `toolbar` / `filters` / `btn` / `data-table` / `modal-*`  
- **禁止**在页面 scoped 再复制一套按钮/表格皮肤  
- 暗色、圆角、工具栏高度 34px 等约束直接继承 lottery 规约精神  

**实现形态建议：**

| 方案 | 说明 | 推荐 |
|------|------|------|
| cf-auth 内 `frontend/` workspace | 与 lottery 同构（Vite + Vue3 + vue-router + vue-i18n 可选） | **推荐** |
| 纯服务端 HTML Admin | 快但不复用组件 | 不推荐 |
| 把 Admin 做进 lottery 平台后台 | 耦合错误：auth 是独立基础设施 | **禁止** |

i18n：MVP 可先中文写死或只拷 `zh-CN` 必要 key；不必一次上全量 lottery 文案。

### 5.4 后端鉴权模型（最佳实践）

**问题：** Better Auth 的「登录用户」≠「平台管理员」。  
若任何人 register 后都能 `create-client`，多项目场景会变成「任意用户发 client」。

**推荐模型（简单、够用）：**

```text
① 环境变量 ADMIN_USER_IDS=id1,id2
   或 ADMIN_EMAILS=you@eforge.xyz
② 管理 API 中间件：requireAuthSession + email/id ∈ 白名单
③ 可选：ADMIN_API_KEY 仅用于 CI/脚本（Header），不进浏览器
④ 所有写操作写 audit_logs
```

补充：

- **不**把 lottery 的 `platform_members` / 租户模型搬进 cf-auth（那是业务多租户）。  
- cf-auth Admin = **平台级** 运维身份，一张白名单足够到数十个 RP。  
- 若未来管理员变多，再加 `auth_admin_users` 表；MVP 用 env 白名单可上线。

**管理 API 建议前缀：**

```text
/api/admin/health
/api/admin/clients          GET/POST
/api/admin/clients/:id      GET/PATCH（禁用、redirect、name、skip_consent）
/api/admin/clients/:id/rotate-secret  POST
/api/admin/users            GET
/api/admin/users/:id/sessions  GET + DELETE
/api/admin/audit            GET
```

实现要点：

- 优先调用 **Better Auth `auth.api.*`**（`createOAuthClient` / `adminUpdateOAuthClient` 等），避免手写破坏插件不变量。  
- 列表类只读可用 Drizzle 查 `oauthClient` / `user` / `session`（ORM，禁拼接 SQL）。  
- 响应 envelope 可对齐 lottery：`{ ok, data, error }`（拷 `lib/http` 思想，薄封装）。  
- **永远**不在 GET 列表返回 `client_secret`。

### 5.5 数据：是否新表？

| 表 | MVP |
|----|-----|
| 已有 `user` / `session` / `oauthClient` / tokens / consent | 复用 |
| `admin_audit_log`（id, actorUserId, action, targetType, targetId, meta JSON, ip, createdAt） | **建议新增** |
| `auth_admin_users` | L1 可选；MVP 用 env |

### 5.6 安全清单（Admin 专项）

- [ ] Admin 路由全部 HTTPS  
- [ ] CSRF：cookie 会话 + SameSite；写操作校验 Origin ∈ TRUSTED_ORIGINS 或 Admin 专用 origin  
- [ ] 率限制：登录与 rotate-secret  
- [ ] 审计不可被普通用户读取  
- [ ] 前端构建产物不含任何 secret  
- [ ] 生产关闭「开放注册后自动成管理员」路径

## 八、对你三个问题的直接回答

### Q1：还有没有别的优化地方？

有。优先序：**client 权限收口 → 限流 → RP 手册 → Admin → 审计/吊销 → 体验与更多 IdP**。  
协议与部署主路径已够用；短板在 **治理与可运营性**。

### Q2：是否满足多个项目的 auth 接入？

| 层面 | 满足？ |
|------|--------|
| OAuth/OIDC 协议、多 client 表、独立域名、PKCE | **是** |
| 标准化第二项目一周内接入、可审计、可自助关停恶意 client | **尚未** |

因此可表述为：

> **技术上已是多项目 IdP；工程上仍差「受管接入 + Admin」。**

### Q3：要不要简单 Admin？要的话怎么做？

**要。** 做成平台运维向的轻量后台；  
**前端与交互全部照抄 cf-lottery** 的 Admin 组件、布局、`admin.css`、Toast/Modal/分页范式；  
**后端** 继续 Hono + Drizzle + Better Auth 官方 client API；  
**不做** 业务 RBAC、不做公网动态注册、不做新 UI 体系。
