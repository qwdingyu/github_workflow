| 可说 | 不可说 |
|------|--------|
| 「官方 1.5 博文声称支持 D1」 | 「我们已证明 1.6.25 在本账号 D1 上生产可用」 |

**实施策略：**

1. **M1–M3 主路径：libSQL file SQLite**（已验证范式）。  
2. **M4 分支 A：** wrangler dev + D1 binding 跑同一套 smoke。  
3. **M4 分支 B（兜底）：** Workers 继续用远程 Turso/libSQL HTTP（lottery 生产同款）。  
4. 只有 A 稳定后，才把生产默认切 D1。

## 四、架构级坑（专业建议固化）

1. **共享 Cookie 多项目 SSO** → 禁止作为核心方案。  
2. **业务直连 auth DB** → 禁止。  
3. **Auth session ≠ 业务 session** → 文档与代码命名分开。  
4. **Dynamic Client Registration 对公网默认关闭** → 防客户端滥注。  
5. **redirect_uri 必须白名单** → 每个 RP 单独配置。  
6. **登出同步** → 第一阶段只做 RP 本地登出。  
7. **baseURL / trustedOrigins / HTTPS** → Cloudflare 自定义域名场景最易配错。  
8. **Workers CPU** → 023：避免登录路径超重 KDF。  
9. **OAuth access token 与 session 绑定** → 插件类型注释要求 introspection 校验 session；RP 勿假设 token 在用户登出后仍长期有效而不查。  
10. **npm peer** → CI 锁定 lockfile。

## 五、OAuth Provider 成熟度策略

```text
不要：验证 email 登录成功 → 立刻删 Logto、全站切 Better Auth
而要：
  本地 OAuth 闭环
  → 预发/生产 auth 域名
  → 真实 Google
  → 单一 RP（lottery 参与端）灰度
  → 第二 RP
  → 再评估删 Logto
```

插件能力（博文/类型）包括：authorization_code、refresh_token、client_credentials、OIDC openid、JWT/JWKS、consent、introspection/revocation、动态注册等。  
**全部默认开启等于扩大攻击面**——MVP 只开授权码+PKCE+必要 scope。

## 八、结论

**可以做，且值得做。**  
**路线必须是 OAuth/OIDC Provider，而不是跨域共享 Cookie。**  
**Cloudflare Workers 是优先部署面；Node + SQLite 是开发与兜底。**  
**D1 是优先候选存储，但必须以 1.6.25 实测为准，libSQL 是已验证兜底。**  
**cf-lottery 是第一个 RP 候选人，不是 auth 数据库的共库方。**
