## 一、先回答三个「是什么」

| 角色 | 是什么 | 不是什么 |
|------|--------|----------|
| **上游 Social IdP** | Google / GitHub / Microsoft / … | 业务项目不直接对接它们 |
| **cf-auth** | 你们的 **统一身份中心 + OAuth/OIDC Provider** | 不是业务库、不是跨域 Cookie 中枢 |
| **业务 RP**（lottery / shop / …） | 信任 cf-auth 发的 code/token 的应用 | 不直连 auth DB、不读 auth session cookie |

```text
  用户浏览器
       │
       │ ① 在 auth 域用 Google/GitHub 等登录
       v
 ┌─────────────────────────────────────────┐
 │  上游 IdP（Google / GitHub / …）         │  ← 联邦身份源（Inbound Federation）
 └──────────────────┬──────────────────────┘
                    │ OAuth 回调 → auth session（仅 auth.eforge.xyz Cookie）
                    v
 ┌─────────────────────────────────────────┐
 │  cf-auth  (auth.eforge.xyz)              │
 │  · user / session / account              │
 │  · socialProviders（多源）               │
 │  · oauth-provider + jwt                  │  ← 对内是「登录服务」，对外是「IdP」
 └──────────────────┬──────────────────────┘
                    │ ② Authorization Code + PKCE
                    v
 ┌─────────────────────────────────────────┐
 │  RP：lucky.eforge.xyz / 其他业务         │  ← Outbound OAuth Client
 │  · 本地业务 JWT / session                │
 │  · identity = issuer:sub                 │
 └─────────────────────────────────────────┘
```

**铁律：** 两层 OAuth 不能混谈。

1. **Inbound**：用户 → 上游 IdP → cf-auth（建立 **Auth session**）  
2. **Outbound**：RP → cf-auth（拿 **业务身份**，不共享 Cookie）

只接 Google 时架构也一样；多 IdP 只是 **Inbound 源变多**，Outbound 协议不变。

## 二、为什么要从 monorepo 拆成独立 GitHub 仓库

| 维度 | monorepo 子目录 | 独立仓库（推荐） |
|------|-----------------|------------------|
| 发布节奏 | 被 lottery 业务提交拖累 | auth 可独立 version / tag |
| 权限 | 业务开发者易摸到 secrets / schema | 最小权限、仅 auth 维护者 |
| 依赖 | 易被根 workspace 钩子/arch 规则误伤 | 独立 `package-lock`、独立 CI |
| 心智 | 「又一个 templates 文件夹」 | 明确 **平台基础设施** |
| 复用 | 难被 shop 等直接 submodule/引用 | 标准 git clone / 私有包 |

**结论：** cf-auth 是 **平台级 IdP**，应独立仓库；本 monorepo 可保留工作副本或 git subtree，但 **权威源 = 独立 GitHub repo**。

**禁止：** 业务项目 `import` cf-auth 源码当库；唯一契约是 **HTTP OAuth/OIDC**。

## 三、配置架构（最佳实践）

### 3.1 配置分层（由外到内）

```text
① 基础设施 secrets（平台）
   BETTER_AUTH_SECRET / BETTER_AUTH_URL / DATABASE_URL / TURSO_TOKEN
        │
② 信任边界
   TRUSTED_ORIGINS（自身 + 各 RP origin）
        │
③ 上游 Social 凭证（成对）
   {PROVIDER}_CLIENT_ID + {PROVIDER}_CLIENT_SECRET
        │
④ 策略开关
   ENABLED_SOCIAL_PROVIDERS=google,github   # 可选白名单
   EMAIL_PASSWORD_ENABLED=true|false
        │
⑤ 代码注册表（非密钥）
   SOCIAL_PROVIDER_REGISTRY  →  id / label / env 名 / 文档 notes
        │
⑥ 运行时解析
   resolveSocialProviders(env) → socialProviders + enabledIds + enabledMeta
        │
⑦ betterAuth({ socialProviders, account.accountLinking })
```

### 3.2 注册表驱动（Open/Closed）

**文件：** `src/lib/social-providers.ts`

| 原则 | 做法 |
|------|------|
| 扩展开 | 新 IdP = 注册表加一项 + 配 env |
| 修改闭 | **不**在 `createAuth` 里写 `if (google) … else if (github)` |
| 半开禁止 | 缺 ID 或 SECRET 任一 → **整 provider 不启用** |
| 密钥零入库 | 只出现在 `.env` / wrangler secret / CI secrets |
| 回调约定 | `{BETTER_AUTH_URL}/api/auth/callback/{id}`（Better Auth 标准） |

当前注册表（有序 = 登录按钮顺序）：

`google` → `github` → `microsoft` → `apple` → `discord` → `gitlab`

### 3.3 环境变量契约

| 变量 | 必填 | 说明 |
|------|------|------|
| `BETTER_AUTH_SECRET` | 是 | ≥32 字符 |
| `BETTER_AUTH_URL` | 是 | 生产 `https://auth.eforge.xyz` |
| `DATABASE_URL` / `TURSO_*` | 是 | 本地 file / 远程 libSQL |
| `TRUSTED_ORIGINS` | 强烈建议 | 逗号分隔；含 auth 自身与 RP |
| `GOOGLE_CLIENT_ID/SECRET` 等 | 按需 | 成对；不成对不启用 |
| `ENABLED_SOCIAL_PROVIDERS` | 否 | 空 = 凡密钥齐全即开 |
| `EMAIL_PASSWORD_ENABLED` | 否 | 默认 true；生产参与端可 false |

**运维心智模型：**

- **配密钥** = 具备启用能力  
- **白名单** = 显式裁剪生产面（灰度、合规、临时关某源）  
- **登录页** = 只渲染 `enabledMeta`，用户看不见未配置源  

### 3.4 账号关联（Account Linking）策略

| 配置 | 值 | 为什么 |
|------|-----|--------|
| `accountLinking.enabled` | `true` | 同一人多源登录应落到同一 `user` |
| `trustedProviders` | **仅**当前 `enabledIds` +（可选）`email-password` | 未配置源不进信任面 |
| `allowDifferentEmails` | `false` | 防邮箱不同时的错误合并 / 接管 |
| `requireLocalEmailVerified` | `true` | 降低「未验证邮箱抢注后被社交隐式合并」 |

> 生产上线前须用 **真实 Google + GitHub 双源** 测：同邮箱是否合并、异邮箱是否拒绝。

### 3.5 配置与部署矩阵

| 环境 | 社交 | 邮箱密码 | DB |
|------|------|----------|-----|
| 本地开发 | 可全空（仅 email）或 mock 密钥测 URL | true | `file:./data/local.db` |
| 预发 | google + github | 视需要 | 远程 libSQL / D1（M4） |
| 生产 auth.eforge.xyz | 白名单 + 真实密钥 | 可 false（仅社交） | 生产库 + secret |

Workers / Node **共用**同一 `resolveAuthConfig` + `createAuth`；差异仅入口（`index.ts` / `server.ts`）与绑定注入。

## 四、端到端流程（配置视角）

### 4.1 用户首次用 GitHub 登录并授权 lottery（完整闭环）

```text
[RP lottery]  ──authorize(client_id, redirect_uri, code_challenge)──►  [cf-auth]
[cf-auth]     无 session ──redirect──► /sign-in?...oauth params...
[浏览器]      GET /api/auth-meta/social  →  { providers:[{id:github,...}], ... }
[用户]        点「GitHub」
[浏览器]      POST /api/auth/sign-in/social { provider:"github", callbackURL }
[cf-auth]     302 → github.com/login/oauth/authorize
[GitHub]      用户同意 → redirect →
              https://auth.eforge.xyz/api/auth/callback/github?code=...
[cf-auth]     换 token、写 user/account、设 Auth Cookie
              → callbackURL（通常回到 authorize 或 /sign-in 续 OAuth）
[cf-auth]     已登录 → consent（若需）→ 发 authorization code 回 lottery
[lottery]     code + code_verifier → POST /api/auth/oauth2/token
[lottery]     得 access_token / id_token → userinfo 或验 JWT
[lottery]     写 identity_type=auth_user, identity_value=issuer:sub
              本域发业务 session —— 与 auth Cookie 无关
```

### 4.2 仅配置变更、无发版场景

1. 在 GitHub OAuth App 填回调：`https://auth.eforge.xyz/api/auth/callback/github`  
2. `wrangler secret put GITHUB_CLIENT_ID` / `SECRET`（或 `.env`）  
3. 可选：`ENABLED_SOCIAL_PROVIDERS=google,github`  
4. 重启 / 重新部署 → health 的 `socialProviders` 含 `github`  
5. 登录页自动出现按钮 —— **无需改业务 RP 代码**

### 4.3 关键某源（生产止血）

- 从 `ENABLED_SOCIAL_PROVIDERS` 去掉该 id，或撤掉 secret 并重启  
- 已绑定 `account` 行仍在；用户可改用其他 trusted 源（策略需产品确认）

## 五、模块边界（代码地图）

```text
src/
  lib/social-providers.ts   # 注册表 + resolve（纯函数，易单测）
  lib/env.ts                # Bindings → AuthRuntimeConfig
  lib/auth.ts               # betterAuth 工厂（social + linking + plugins）
  lib/platform.ts           # 双运行时 getEnv 等
  bindings.ts               # 类型契约（含各 *_CLIENT_*）
  app.ts                    # Hono：health / auth-meta / handler / well-known
  routes/pages.ts           # 登录/consent；按钮数据来自 meta API
  index.ts | server.ts      # Workers | Node 入口
```

**依赖方向（允许）：**

`pages` → meta API → `env` → `social-providers`  
`auth` → `env` → `social-providers`  
`app` → `auth` + `env`

**禁止：** pages 直接读 secret；RP 包依赖本仓库内部模块。

## 六、安全与合规清单

1. **密钥**：永不进 git；生产用 secret store；轮换有 runbook。  
2. **redirect_uri**：OAuth **client** 侧白名单（RP 回调）；社交侧在 Google/GitHub 控制台白名单（auth 回调）。  
3. **PKCE**：所有公网 RP 强制；SPA 用 public client。  
4. **Dynamic Client Registration**：保持关闭。  
5. **CORS / trustedOrigins**：显式列表，禁止 `*` + credentials。  
6. **Cookie**：仅 auth 域；`Secure` + 合适 SameSite（生产 HTTPS）。  
7. **账号接管**：`allowDifferentEmails: false` + email verified 策略；敏感操作可再 step-up。  
8. **日志**：禁止打印 client_secret / authorization code / refresh_token。  
9. **Workers CPU**：优先社交；邮箱密码 KDF 在 Free 计划需评估（见 lottery 023）。  
10. **多租户业务**：身份在 auth 统一；**租户/RBAC 仍在各 RP**，不把业务权限塞进 IdP。

## 七、与「只接 Google」方案的对比

| 项 | 单 Google | 多 IdP 注册表（本方案） |
|----|-----------|------------------------|
| 配置 | 两个 env | N 对 env + 可选白名单 |
| 代码分支 | 易写死 google | 注册表循环，无分支膨胀 |
| 登录 UI | 写死按钮 | meta API 驱动 |
| 账号模型 | 单 account provider | 多 account 行 + linking |
| 运维 | 简单 | 略增；换源/关源不改代码 |
| 协议对外 | 相同 | **相同**（RP 无感） |

**结论：** 多 IdP 的复杂度应收敛在 **Inbound 配置层**；Outbound 对 RP 保持单一 issuer。

## 八、反模式（审查时明确禁止）

| 反模式 | 后果 |
|--------|------|
| 业务共享 Better Auth session cookie | 跨域 Cookie / CSRF / 无法独立升级 |
| 业务直连 auth SQLite/D1 | 耦合、权限灾难、无法多 RP |
| 自研 OAuth AS | 安全与合规成本爆炸 |
| 登录页写死 Google 按钮 | 加 GitHub 要发版改前端 |
| 密钥写进 wrangler.jsonc / 文档正文 | 泄露 |
| 未配 SECRET 仍启用 provider | 半开导致难排查 500 |
| 把所有 better-auth 内置社交一次全开 | 未运营按钮、攻击面、支持成本 |
| monorepo 强绑 arch 规则要求 auth 表进 lottery schema | 错误边界（已用 SCHEMA 豁免应对；独立仓更干净） |

## 十一、决策记录（本轮）

| 决策 | 选择 | 理由 |
|------|------|------|
| 多社交接入方式 | 注册表 + env 成对启用 | OCP；运维可配；测试可注入 |
| 登录 UI | meta API 动态渲染 | 配置驱动，零硬编码按钮 |
| 账号合并 | 官方 accountLinking + 紧信任面 | 不自研合并算法 |
| 仓库形态 | **独立 GitHub 仓库** | 平台边界、权限、发布节奏 |
| 对外协议 | 仍仅 Code + PKCE | 与 001 一致；多 IdP 不改变 RP 契约 |
| 默认启用集 | 注册表含 6 源，**实际启用看密钥** | 避免空按钮；文档一次写清回调 |

## 十二、一句话总结

> **cf-auth 是双层身份枢纽：对上联邦多个社交 IdP（配置注册表驱动），对下用标准 OAuth/OIDC 服务多个业务 RP；会话不过域、库不共享、密钥不进仓、扩展不改核心分支。**
