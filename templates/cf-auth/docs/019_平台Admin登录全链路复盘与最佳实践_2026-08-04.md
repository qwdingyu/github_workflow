## 1. 设计意图：三条进 Admin 的路径

平台管理员 ≠「在 cf-auth 登录过的任意用户」。  
实现见 `src/lib/admin-auth.ts`。

### 1.1 路径 A — 浏览器主路径（本次事故主线）

```text
用户 → /sign-in（Google/GitHub）
     → Better Auth 写 session 表 + Set-Cookie（signed session_token）
     → 回到 /admin 或 /admin/login?redirect=...
     → 前端 credentials: 'include' 调 /api/admin/health
     → 服务端 auth.api.getSession(cookie) + ADMIN_EMAILS/IDS 白名单
     → 200 → 写 localStorage flag → 进仪表盘
```

要点：

- **权威在服务端 cookie + 白名单**，不在 `localStorage`。
- `localStorage.cf_auth_admin_ok` 只是路由守卫的**缓存 flag**，可被清、可被伪造；真正权限每次 API 仍校验。
- 社交登录是给**人**用的；管理员账号往往是 Google-only（无 password 哈希）。

### 1.2 路径 B — 邮箱密码（次路径）

```text
POST /api/auth/sign-in/email { email, password }
  → 仅当 account 表有 credential 密码哈希时成功
  → 再 probe /api/admin/health（仍要过白名单）
```

要点：

- **`ADMIN_API_KEY` 不是登录密码**，不能填进密码框。
- 纯 Google 用户任意密码 → `INVALID_EMAIL_OR_PASSWORD`（**预期**，不是平台坏了）。
- UI 已把邮箱密码收到 `<details>` 折叠区，避免误导主路径。

### 1.3 路径 C — 脚本 / CI（Header）

```text
X-Admin-Api-Key: <ADMIN_API_KEY>
或 Authorization: Bearer <ADMIN_API_KEY>
  → resolveAdminActor.via = "api_key"
  → 不依赖浏览器 cookie
```

要点：

- 只给自动化；**禁止**放进前端、禁止当人类密码。
- `GET /api/admin/health` + API Key 是部署后最干净的「管理面是否活着」探针。

### 1.4 三层概念不要混

| 概念 | 含义 | 失败表现 |
|------|------|----------|
| **已登录用户** | Better Auth session 有效 | get-session 200 + user；或 200 null |
| **平台管理员** | session 用户 ∈ `ADMIN_EMAILS`/`ADMIN_USER_IDS`，或 API Key | admin/* 200；否则 401 |
| **管理面已配置** | 至少配了一种 ADMIN_* | `health.adminConfigured`；未配则 admin 503 |

```text
已登录 ⊄ 管理员
管理员 ⊂ （已登录 ∩ 白名单） ∪ API Key
```

## 2. 前端状态机（Admin SPA）

相关文件：

- `frontend/src/router/index.ts` — 守卫
- `frontend/src/views/AdminLoginView.vue` — 登录/复用 session
- `frontend/src/composables/useAdminAuth.ts` — flag 读写
- `frontend/src/composables/useAdminRequest.ts` — 带 credentials 的 API

### 2.1 路由守卫

```text
访问 /admin/*
  → meta.public？放行（仅 /admin/login）
  → 有 localStorage flag？放行（仍依赖后续 API 鉴权）
  → 否则 fetch GET /api/admin/health (credentials: include)
       → 200 + ok → 写 flag，放行
       → 否则 → redirect /admin/login?redirect=<原路径>
```

### 2.2 登录页 onMounted

```text
checking = true
1) probeAdminSession() → GET /api/admin/health
   → 200 → markLoggedIn + replace(redirect)  // 静默进入
2) 否则 loadSessionHint() → GET /api/auth/get-session
   → 有 user.email → 展示「已检测到登录：…」+「使用当前会话进入」
   → 无 → 只展示「去 /sign-in」
checking = false
```

### 2.3 社交入口

```text
/sign-in?callbackURL=<encode(/admin 或 redirect)>
```

登录成功后 Better Auth 应把用户带回 Admin 域路径；再走守卫 / onMounted 探测。

### 2.4 为何「看起来像没登录」

| 前端现象 | 实际可能 |
|----------|----------|
| 一直停在 login | health 非 200（401/503/网络） |
| 无「已检测到登录」提示 | get-session 200 null **或 500**（500 时 catch 后 hint 为空） |
| 邮箱密码红字 | Google-only 或密码错（旁路） |
| 旧 UI（只有邮箱框） | 缓存旧 chunk（本次已用 content-hash 排除） |

**关键 UX 缺口（知识）**：`get-session` 若 **500**，`loadSessionHint` 的 `catch` 静默吞掉，用户看不到「会话接口炸了」，只看到空白登录卡——容易误判成「没登录成功」。

## 3. 服务端鉴权与 get-session 内部

### 3.1 `/api/admin/*`

```text
requirePlatformAdmin
  → 未配置 ADMIN_* → 503
  → resolveAdminActor
       ① API Key 常量时间比较
       ② auth.api.getSession(headers) 
            → 无 user → null → 401
            → 有 user 但不在白名单 → null → 401
            → 白名单命中 → adminActor
       ③ getSession **抛错** → catch → null → 401   ← 本次把 500 压成 401
```

**诊断含义**：admin/health **401 不能单独证明「没 cookie」**；也可能是 getSession 内部异常被吞。必须同时看 **get-session 状态码与 body**。

### 3.2 `/api/auth/get-session`（Better Auth）

简化（`better-auth` `session.mjs` + `jwt` 插件）：

```text
GET/POST /api/auth/get-session
  1. 读 signed cookie（HTTPS 下常为 __Secure-better-auth.session_token）
  2. 无 token → 200 null（正常）
  3. 可选 cookieCache（session_data）
  4. internalAdapter.findSession(token)  // 查 Turso session + user
  5. 过期则删 cookie / 可选删行 → 200 null
  6. 可能 refresh expiresAt
  7. 返回 { session, user }
  8. 【jwt 插件 after hook】若存在 session：
       getJwtToken → 读 jwks 表最新私钥
       → 用 BETTER_AUTH_SECRET 对称解密 privateKey
       → 签 JWT，写入响应头 set-auth-jwt
       → 解密失败 → BetterAuthError → 整请求 500 FAILED_TO_GET_SESSION
```

**核心洞见**：

> get-session 在「会话已合法」之后，仍可能因 **JWT 插件副作用** 失败。  
> 失败模式是：**有 cookie + 库里有 session 行 → 500**；**无 cookie → 200 null**。  
> 用「无 cookie 探针 200」**证明不了**「有 cookie 也正常」。

### 3.3 Cookie 形态（生产）

| 项 | 值 |
|----|-----|
| 逻辑名 | `better-auth.session_token` |
| HTTPS 前缀 | 常为 `__Secure-better-auth.session_token` |
| 值 | `token.signature`（HMAC，signature base64 长 44 且以 `=` 结尾） |
| 库内 token | 约 32 字符，**无**点号；点号只在 cookie 签名分隔 |
| HttpOnly / Secure | 是（浏览器 JS 读不到明文，Network 面板可见 Cookie 头） |

本地伪造探测时必须：

1. 用与生产一致的 `BETTER_AUTH_SECRET` 对 **库内 token** 做 `signCookieValue`；  
2. Cookie 名带上生产实际前缀（`__Secure-`）；  
3. `credentials` / 手动 Header 不要二次错误编码。

### 3.4 时间戳与 schema

- `session.expiresAt` 等为 SQLite `INTEGER` + Drizzle `mode: "timestamp"`（**秒**存库，读出为 `Date`）。  
- 本次事故中日期合法、未过期；**不是** timestamp 模式搞错导致 500。  
- 仍建议：改 schema/migrate 后做「注册→登录→get-session」闭环单测（已有 `auth-core.test.ts`）。

## 4. 一次真实失败的端到端时间线

### 4.1 用户操作

1. 打开 `https://auth.eforge.xyz/admin`（或 login）。  
2. 被引到 `/sign-in`，选 Google。  
3. Google 同意后回到 Admin。  
4. 仍停在登录相关页，无法进仪表盘。  
5. 曾尝试邮箱 +（疑似 API Key/随意密码）→ Invalid email or password（旁路噪音）。

### 4.2 Network 面板（完整链路，按业务语义）

| # | 请求 | 状态 | 解读 |
|---|------|------|------|
| 1 | 社交 sign-in | 200 | 开始 OAuth |
| 2 | 账户选择 / Google | 200/302 | IdP 正常 |
| 3 | Google 授权回调 | 302 | 授权码回到 cf-auth |
| 4 | `GET /admin/` | 200 | SPA HTML |
| 5 | `index-*.js` / `AdminLoginView-*.js` | 200/304 | **新包已部署**（hash 文件名） |
| 6 | `GET /api/admin/health`（守卫） | **401** | 无 adminActor |
| 7 | `GET /api/admin/health`（login probe） | **401** | 同上 |
| 8 | `GET /api/auth/get-session` | **500** | **根因暴露点** |

### 4.3 服务端与数据侧事实（排查时核实）

| 检查 | 结果 |
|------|------|
| `GET /api/health` | `ok`，`db: true`，`adminConfigured: true`，social google/github |
| 无 cookie `get-session` | **200 `null`** |
| 无 cookie `admin/health` | **401**「需要平台管理员身份」 |
| `ADMIN_EMAILS` | 含 `xthinkai@gmail.com` |
| `user` 表 | 该邮箱存在，`emailVerified=1`，仅 Google account |
| `session` 表 | 多条未过期 session，token 长度正常 |
| `jwks` 表 | 1 行；`privateKey` 为加密信封 |
| 本地用**当前** secret + 真实 token 签 cookie 调 get-session | **500** + `Failed to decrypt private key...` |
| `DELETE FROM jwks` 后同样 cookie | get-session **200**，admin/health **200** |

### 4.4 因果链（最终版）

```text
历史某次 BETTER_AUTH_SECRET 变更或环境分叉
  → jwks.privateKey 仍用旧 secret 加密
  → 当前 Worker secret 不同

用户 Google 登录成功
  → session 行写入，Set-Cookie 成功（签名用的是【当前】secret）✅
  → 浏览器进入 /admin，带上 cookie ✅

路由守卫 / 登录页
  → GET /api/admin/health
      → resolveAdminActor → getSession
          → 验 cookie ✅ → findSession ✅
          → jwt after-hook 解密 jwks ❌
          → 抛错 →（api 路径）失败
      → catch → null → 401「需要平台管理员身份」

  → GET /api/auth/get-session（handler 路径）
      → 同上解密失败 → HTTP 500

前端
  → health 401 → 不进仪表盘
  → get-session 500 被 catch → 无 sessionHint
  → 用户以为「登录没成功」或「白名单没配」
```

一句话：

> **身份登录成功了；管理面读会话时，JWT 插件的密钥材料坏了。**

## 5. 排查方法论（以后照做）

### 5.1 分层探针（由外到内，每层只证一件事）

| 层 | 探针 | 期望 | 若失败说明 |
|----|------|------|------------|
| L0 部署/包 | 看 HTML 引用的 `index-XXXX.js` 是否与本次 build 一致 | hash 一致 | 缓存/错 Worker/Assets |
| L1 活着 | `GET /api/health` | ok、db、adminConfigured | 库/绑定/配置 |
| L2 管理面配置 | health.`adminConfigured`；无 cookie admin/health | true；401 或 503 | 503=没配 ADMIN；401=已配但无身份 |
| L3 脚本管理面 | admin/health + `X-Admin-Api-Key` | 200 | API Key/绑定错误 |
| L4 匿名会话 | get-session 无 cookie | 200 null | BA handler 全坏（少见） |
| L5 **有会话** | get-session **带真实 session cookie** | 200 + user | **本次断在此（500）** |
| L6 白名单 | 同 cookie admin/health | 200 | 401=非白名单或 L5 仍失败 |
| L7 数据 | user/account/session/jwks SQL | 形状合理 | 无用户/无 session/jwks 异常 |

**铁律**：L4 通过 ≠ L5 通过。必须用「登录后的 cookie」或「库 token + 当前 secret 重签」做 L5。

### 5.2 状态码对照表（Admin 专用）

| get-session | admin/health | 优先怀疑 |
|-------------|--------------|----------|
| 200 null | 401 | 未登录 / cookie 域或 Secure 前缀不对 |
| 200 + user | 401 | 白名单邮箱/ID 不匹配（大小写、多空格已做 lower+trim） |
| 200 + user | 200 | 正常；若 UI 仍拦，查 flag/路由/前端 bug |
| **500** | **401** | **JWKS/secret、BA 内部、钩子副作用**（先查日志 decrypt） |
| 任意 | 503 | 未配置 ADMIN_* |
| 200 null | 200 | 几乎只能是 API Key 被带上了（异常） |

### 5.3 反幻觉清单（本次踩过的坑）

1. **不要**只因为「新 JS 304」就说前端有 bug——304 往往表示缓存命中且文件正确。  
2. **不要**把 email 登录失败当成主因——先看主路径 social + get-session。  
3. **不要**用 lottery 文档解释 auth Admin cookie。  
4. **不要**信任 `wrangler deployments list` 的旧「Secret Change」行 alone；用 URL 上的 chunk hash + health 字段交叉验证。  
5. **不要**在 resolveAdminActor 的静默 catch 下只报 401 就结案——对一下 get-session。  
6. **不要**在日志/文档里打印 secret 或完整 session token。  
7. **不要**假设「换 secret 只影响新登录」——**jwks 私钥加密绑定旧 secret**，旧 jwks 行会毒死所有「已登录 get-session」。

### 5.4 推荐复现脚本思路（正式沉淀，勿一次性丢弃）

目标：不依赖浏览器 DevTools 也能 L5。

1. 从 Turso 读目标用户最新 `session.token`（勿提交 token 到 git）。  
2. 用与 Worker 相同的 `BETTER_AUTH_SECRET`，调用 better-call 的 `signCookieValue`。  
3. 请求：  
   - `Cookie: __Secure-better-auth.session_token=<signed>`  
   - `Origin: https://auth.eforge.xyz`  
4. 打本地 `createAuth`/`createApp` 与生产 URL 各一次，对比状态码。  
5. 若本地 500 且日志含 decrypt private key → 查 jwks；清 jwks 后应 200。  
6. 脚本放 `scripts/` 或 docs 附录命令；**默认 dry-run**，生产写操作需显式确认。

## 6. 处置与验证（本次）

### 6.1 生产处置

```sql
-- Turso cf-auth-db
DELETE FROM jwks;
```

效应：

- 下次签 JWT 时 BA 用**当前** secret 生成新密钥对并写入 jwks。  
- 已用**旧 kid** 签出的 access/id token 可能校验失败 → RP 需重新走授权码（通常可接受）。  
- **session cookie 本身不依赖 jwks**；清 jwks 后旧 session 行一般仍可 get-session。

### 6.2 验证矩阵（处置后）

| 检查 | 期望 |
|------|------|
| 无 cookie get-session | 200 null |
| 有合法 cookie get-session | 200 + email |
| 白名单用户 cookie → admin/health | 200 + counts |
| API Key → admin/health | 200 |
| 浏览器硬刷新 `/admin` | 进仪表盘或显示「已检测到登录」后一键进入 |
| Google-only 邮箱密码 | 仍应失败（预期） |

### 6.3 用户侧恢复步骤

1. 打开 `https://auth.eforge.xyz/admin`（建议硬刷新）。  
2. 若仍在 login：点「去 /sign-in 用 Google / GitHub 登录」。  
3. 回到 Admin 后应自动进或显示会话提示。  
4. **不要**把 `ADMIN_API_KEY` 填进密码框。

## 7. 最佳实践（运维 & 研发）

### 7.1 Secret 生命周期

| 动作 | 必须同时做 |
|------|------------|
| 初次设置 `BETTER_AUTH_SECRET` | 空库或允许 BA 创建 jwks |
| **轮换** `BETTER_AUTH_SECRET` | ① 新 secret 写入 CF + `.env` ② **`DELETE FROM jwks`**（或迁移策略）③ 通知 RP 可能需重新登录/授权 ④ 跑 L3–L6 探针 |
| 多环境共享同一 Turso | **禁止**各环境不同 secret 共库；一库一 secret |
| local-deploy 同步 secret | 意识到「同步成功」可能制造与旧 jwks 的不一致 → deploy 检查清单含 jwks |

### 7.2 部署检查清单（扩展 docs/017）

每次 `bash local-deploy.sh` / 改 secrets 后：

- [ ] `GET /api/health` → ok、db、**adminConfigured**  
- [ ] `GET /api/admin/health` 无凭证 → 401（或未配时 503）  
- [ ] `GET /api/admin/health` + API Key → 200  
- [ ] `GET /api/auth/get-session` 无 cookie → 200 null  
- [ ] **有会话** get-session（浏览器登录后或脚本）→ **200 而非 500**  
- [ ] 若本轮改了 `BETTER_AUTH_SECRET` → 已执行 jwks 处置并记录  
- [ ] Admin SPA：`/admin`、`/admin/login` 200，协议页 `/sign-in` 仍是服务端页而非 SPA 误抢  

### 7.3 配置原则

1. **ADMIN_EMAILS** 用管理员真实 Google/GitHub 邮箱；小写存储比较已做，配置时仍避免隐藏字符。  
2. **ADMIN_API_KEY** 仅 CI/脚本；长度足够；不进前端 bundle。  
3. **BETTER_AUTH_URL / APP_ORIGIN / TRUSTED_ORIGINS** 生产走 `wrangler.jsonc` vars，**禁止**把 localhost URL 当 secret 上传（docs/017）。  
4. 社交与邮箱密码可并行；**Admin UX 主推社交**。  
5. create-client 仅管理员（docs/016）；人类走 `/admin/clients`。

### 7.4 可观测性（建议后续做，未完成则记债）

| 项 | 价值 |
|----|------|
| health 增加 `jwksDecryptOk`（尝试解密最新 jwks，失败只报 boolean） | 部署后 30 秒发现 secret 漂移 |
| resolveAdminActor catch 时 `console.error` 分类（decrypt vs 其它） | 401 与 500 根因可关联 |
| 前端 get-session 非 2xx 时展示「会话服务异常，请联系运维」 | 避免静默成「未登录」 |
| prod-smoke 增加「可选 SESSION_COOKIE 环境变量做 L5」 | 自动化回归有会话路径 |
| 审计：secret 轮换 runbook 链接到本文件 §7.1 | 降低二次事故 |

### 7.5 安全注意

- 清 jwks = 密钥材料轮换；记审计（谁、何时、为何）。  
- 不要 `disablePrivateKeyEncryption: true` 除非威胁模型接受「私钥明文在 DB」（一般不推荐）。  
- 复现时用的 session token / 签名 cookie 用完即弃，不写进 git、不贴公共 issue。  
- Worker 日志可能含 error 文案；避免 log 完整 Authorization/Cookie。

### 7.6 产品/UX 原则（Admin）

1. 主 CTA = 社交登录；邮箱密码折叠 + 文案写清「API Key 不是密码」。  
2. 有 session 且白名单 → 尽量自动进，少一次点击。  
3. 有 session 非白名单 → 明确「当前账号不是平台管理员」，不要只 401 无文案。  
4. get-session 5xx → 明确「认证服务异常」，引导重试/联系运维，而不是假装没登录。

## 8. 误判案例库（知识压缩）

## 12. 结论

1. **平台 Admin 主路径**是：社交登录 → Better Auth cookie → 白名单 → `/api/admin/*`。  
2. **本次故障**不是 Google 失败、不是 SPA 未部署、不是白名单漏配，而是 **`jwt` 插件在 get-session 后解密 jwks 失败**（secret 与库内加密私钥不一致），表现为 **get-session 500 + admin/health 401**。  
3. **修复**是清 jwks 让密钥与当前 secret 对齐；**预防**是 secret 轮换清单 + 有会话探针 + 可观测性。  
4. **知识上最值钱的两句话**：  
   - 「无 cookie 200」证明不了「有 cookie 也 200」。  
   - 「admin 401」在 catch 设计下可能等于「getSession 抛错」，不等于「用户没登录」。
