## 0. 已核实事实（反幻觉）

| 项 | 事实 |
|----|------|
| Node 入口 | **已有** `src/server.ts`：`@hono/node-server` + `createApp` + `dotenv` |
| Workers 入口 | `src/index.ts` + `wrangler deploy`（与 Node **二选一作为生产流量** 更安全） |
| 本地命令 | `npm run dev:local` → `tsx src/server.ts`；现增加 `npm start` 同入口 |
| Admin SPA | `frontend` Vite `outDir: '../public'` → 仓库根 **`public/`**（**不是** lottery 的 `frontend/dist`） |
| 协议页 | `/`、`/sign-in`、`/consent` 由 `src/routes/pages.ts` 提供；Node **不得** `serveStatic(/*)` 抢走 |
| 平台适配 | `src/lib/platform.ts`：`getEnv` / `getClientIp`（`TRUST_PROXY_HEADERS=true` 时信 XFF） |
| 数据库 | `DATABASE_URL` 或 `TURSO_URL`；默认 `file:./data/local.db`；migrate：`npm run db:migrate` |
| 生产 CF 现状 | 当前公开生产是 **Cloudflare Workers + Turso**（`auth.eforge.xyz`）。本文件描述的是 **另一条可运行路径**，不是「已自动切流」 |
| 未实现 | 本仓库**原先没有** lottery 级 `setup-cloud-server.sh` / systemd / nginx 样例；**本轮已补** |

**不要假设：**

- 跑完 setup 会自动改 Cloudflare DNS 或下线 Worker  
- 本机 SQLite 与 Turso 会自动双写同步（**不会**；切库需迁移方案，见 §6）  
- `npm install --omit=dev` 仍能 `tsx` 启动（`tsx` 在 dependencies，完整 install 更稳）

## 1. 架构（Node 生产）

```text
用户 → DNS A（建议灰云/仅 DNS）→ 服务器公网 IP
                ↓
         nginx :443（证书）
                ↓ 反代
         127.0.0.1:8788
                ↓
         tsx src/server.ts  （systemd: cf-auth）
                ↓
         SQLite file:./data/local.db
         或 libsql://…（Turso）
```

与 Workers 对比：

| | Cloudflare Workers | Node 云服务器 |
|--|-------------------|---------------|
| 入口 | `src/index.ts` | `src/server.ts` |
| 静态 Admin | wrangler `assets` → `public/` | Node `serveStatic` + `/admin` → `index.html` |
| 密钥 | wrangler secrets | `/opt/cf-auth/.env` |
| 适合 | 全球边缘、运维轻 | 大陆可达性、固定 IP、自管 |

**建议：** 同一时刻只让 **一个** 后端作为 `https://auth.eforge.xyz` 的权威源（OAuth issuer / Cookie / JWKS）。

## 3. 快速本地验证（不装 nginx）

在开发机（已有 Node ≥ 20）：

```bash
cd /path/to/cf-auth
cp .env.example .env   # 或 scripts/env.cloud-server.example
# 至少保证：
#   BETTER_AUTH_SECRET=（≥32）
#   BETTER_AUTH_URL=http://127.0.0.1:8788
#   DATABASE_URL=file:./data/local.db

npm install --legacy-peer-deps
npm run build:frontend
npm run db:migrate
HOST=127.0.0.1 PORT=8788 npm start
# 另一终端：
curl -sS http://127.0.0.1:8788/api/health
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8788/
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8788/admin
```

期望：`/api/health` 返回 JSON 且 `"ok":true`；`/` 与 `/admin` 为 **200**（需已 build frontend）。

## 4. 云服务器一键部署

### 4.1 前置

1. Debian 11/12（或兼容），公网 IP  
2. 安全组/防火墙放行 **22、80、443**（**不要**对公网暴露 8788；由 nginx 反代）  
3. 代码已在机器上，例如：

```bash
git clone https://github.com/qwdingyu/cf-auth.git /tmp/cf-auth
cd /tmp/cf-auth
```

### 4.2 执行

```bash
sudo bash scripts/setup-cloud-server.sh
# 默认安装到 APP_DIR=/opt/cf-auth
```

可选：

```bash
sudo APP_DIR=/opt/cf-auth SKIP_NGINX=0 bash scripts/setup-cloud-server.sh
```

### 4.3 必做人工项

```bash
sudo nano /opt/cf-auth/.env
```

至少改：

- `BETTER_AUTH_SECRET`（随机 ≥32，**与历史 JWKS 事故相关：勿频繁乱改**）  
- `BETTER_AUTH_URL=https://auth.eforge.xyz`（或你的真实 https 域名）  
- `GOOGLE_*` / `GITHUB_*`  
- `ADMIN_EMAILS` / `ADMIN_API_KEY`  
- `DATABASE_URL`（本机 file 或 Turso）  
- 保持 `TRUST_PROXY_HEADERS=true`（nginx 后）

```bash
sudo systemctl restart cf-auth
curl -sS http://127.0.0.1:8788/api/health
```

### 4.4 DNS 与证书

1. 将 `auth.eforge.xyz` 的 **A 记录** 指到服务器 IP  
2. 若域名在 Cloudflare：**建议代理状态为 DNS only（灰云）**，避免流量再进 Workers/CF 代理层  
3. **切流前**确认旧 Worker 自定义域不会与灰云 A 记录冲突（以你账号里实际 DNS/Routes 为准，本文不代改生产 DNS）  
4. SSL：

```bash
sudo certbot --nginx -d auth.eforge.xyz
```

### 4.5 社交回调

控制台中回调必须与 `BETTER_AUTH_URL` 一致：

- `https://auth.eforge.xyz/api/auth/callback/google`  
- `https://auth.eforge.xyz/api/auth/callback/github`  

RP 的 `redirect_uri`、issuer 仍指向同一域名时，**一般无需改 client_id**（仍是同一逻辑 IdP）。

## 6. 数据库：本机 SQLite vs 继续 Turso

| 策略 | 做法 | 注意 |
|------|------|------|
| A. 新环境空库 | `DATABASE_URL=file:./data/local.db` + `npm run db:migrate` | 无历史用户 |
| B. Node 仍连现网 Turso | `.env` 填现网 `TURSO_URL`/`TURSO_TOKEN` | 代码已支持；**延迟与密钥保管**自测 |
| C. 从 Turso 迁到本机文件 | **本仓库当前无** lottery 同款 `db:export` 一键脚本 | 需自行 dump/导入或先写导出工具后再切流；**勿假装已有** |

备份（file 库）：

```bash
# 停写或低峰
cp -a /opt/cf-auth/data/local.db /opt/cf-auth/data/backup-$(date +%F).db
```

## 7. 与 Cloudflare 生产并存时的风险

| 风险 | 说明 |
|------|------|
| 双权威 | 两套后端共用一名、各写各库 → session/OAuth 混乱 |
| 仅改 DNS 未迁库 | 用户「消失」或登录态全无 |
| 橙云 + 源站 | 若仍橙云指到 CF，流量可能不到你的 VPS |
| Secret 不一致 | Node `.env` 与 Worker secret 不同 → JWKS/session 不互通 |

**推荐切流顺序（原则）：**

1. 在 VPS 用 **临时域名** 或 **hosts** 验完 health / sign-in / admin  
2. 定库策略（同 Turso 或已迁 SQLite）  
3. 再改 `auth.eforge.xyz` DNS  
4. 观察后再决定是否删除/停用 Worker 路由

## 9. 故障速查

| 现象 | 排查 |
|------|------|
| systemctl 起不来 | `journalctl -u cf-auth -n 80`；检查 `tsx` 路径、`.env` 权限、`BETTER_AUTH_SECRET` 长度 |
| `/admin` 404 | 未 `build:frontend` 或 `public/` 不在 WorkingDirectory |
| 社交回调错 | `BETTER_AUTH_URL` 与控制台 URI、反代 `Host`/`X-Forwarded-Proto` |
| 管理 503 | 未配 `ADMIN_EMAILS` / `ADMIN_USER_IDS` / `ADMIN_API_KEY` |
| get-session 异常 | 历史：JWKS 与 `BETTER_AUTH_SECRET` 不一致（见 docs/018） |
