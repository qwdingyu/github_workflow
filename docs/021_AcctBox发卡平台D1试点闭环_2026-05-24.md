## 技术选择

### 为什么不是纯 Pages

发卡平台需要 API 和数据写入：

```text
商品列表
库存卡密
订单记录
发卡状态
```

纯 Pages 只适合静态展示，不适合做主业务写入。

### 为什么不是 KV 主库

KV 适合：

```text
配置
缓存
短链接
低频公开数据
```

但发卡库存需要：

```text
唯一约束
状态更新
库存统计
订单查询
避免重复发放
```

因此主库选 D1。

### Turso / libSQL 的位置

Turso / libSQL 适合做更通用的外部 SQL 主库，尤其是多项目共享、跨平台访问、边缘 SQL 场景。

本次先跑通 Cloudflare 原生闭环：

```text
Workers + D1
```

后续可以再做第二个试点：

```text
Workers + Turso/libSQL
```

## 固化规则

```text
1. database_id 必须来自 wrangler d1 create，不能猜。
2. D1 migration 必须提交到仓库。
3. seed.sql 只放演示数据，不能放真实账号。
4. smoke 会真实消耗一条库存。
5. 发卡库存和订单不能用 KV 做主库。
6. Worker 负责 API，Static Assets 负责前端。
7. 每次部署后必须跑 /api/health、/api/products、POST /api/orders。
8. Wrangler CLI 在非交互远程操作时使用 CLOUDFLARE_API_TOKEN，不是 CF_API_TOKEN。
9. npm/npx registry 解析失败是本地沙箱网络问题，不要误判为 D1 配置问题。
```
