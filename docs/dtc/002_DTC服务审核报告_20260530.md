## 二、代码审查发现的问题（已全部修复）

### 2.1 CRITICAL：脚本中使用了错误的 libsql 子路径

- **问题**：`scripts/import-data.mjs` 和 `scripts/generate-pages.mjs` 使用 `@libsql/client/web`
- **原因**：`/web` 子路径是 edge 运行时（Cloudflare Workers）专用的
- **影响**：在 Node.js 中运行时，该导入会抛出 `TypeError` 或返回空对象
- **修复**：改为 `@libsql/client`（与 cf-api 模板一致）

### 2.2 MEDIUM：package.json 包含未使用的依赖

- **问题**：`drizzle-zod` 和 `zod` 被列为依赖但从未使用
- **影响**：额外的 npm install 时间和存储
- **修复**：从依赖列表中移除

### 2.3 HIGH：缺少 .dev.vars.example

- **问题**：新开发者无法知道本地开发需要哪些环境变量
- **修复**：添加 `.dev.vars.example`，包含 TURSO_URL/TURSO_TOKEN/ADMIN_TOKEN

### 2.4 CRITICAL：scripts/*.mjs 直接写 raw SQL

- **问题**：`scripts/import-data.mjs` 和 `scripts/generate-pages.mjs` 使用 `client.execute("SELECT ...")` 等 raw SQL，违反了铁律 #13
- **原因**：为快速实现功能而绕过了 Drizzle ORM
- **影响**：SQL 注入风险、数据库切换成本高
- **修复**：两个脚本全部重写为 Drizzle ORM 的 query builder（import 新增内联 schema 定义，generate 替换所有 SQL 为 ORM 方法）
- **残留**：仅 `CREATE TABLE IF NOT EXISTS` 保留 `db.run(sql`...`)`，这是 Drizzle ORM 不自建表的必要妥协

## 四、安全审计

### 4.1 SQL 注入防护

所有数据库操作通过 Drizzle ORM 的 query builder 完成，无原生 SQL 拼接。
`sql` 模板标签仅用于 ORDER BY 等 ORM 不直接支持的场景，且参数化。

### 4.2 API 防护

| 防护措施 | 实现 | 来源 |
|---------|------|------|
| 请求体限制 | 50KB | cf-core bootstrap |
| 安全响应头 | X-Content-Type-Options/X-Frame-Options 等 | cf-core |
| API 路径隔离 | `/api/*` 前缀 | bootstrap 配置 |
| 静态资源隔离 | ASSETS binding | wrangler 配置 |

### 4.3 数据类型验证

- DTC 码输入：前端通过 `normalizeCode` 正则校验后再查询数据库
- 批量查询：唯一化 + 大小限制 (maxBatchSize=500)
- 翻页参数：limit/maxLimit 双重限制
