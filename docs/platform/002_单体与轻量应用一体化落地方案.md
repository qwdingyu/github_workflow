# 单体与轻量应用一体化落地方案

日期：2026-05-24

## 结论

结合 `/Users/dingyuwang/0-X/todo-monolith/docs/单体` 的旧讨论，以及今天已经实测跑通的 Cloudflare Workers 自动部署、Custom Domain、docs 固化流程，当前最优方案不是只选一个平台，也不是把所有项目都做成同一种单体。

最优方案是：

```text
一套开发规范
三条部署车道
一个统一 docs 知识库
一个可复制的 AI 上线闭环
```

三条车道如下：

```text
车道 A：Cloudflare Workers 应用工厂
适合 80% 的工具类、填表类、分享类、邀请类、落地页、小 API

车道 B：Next.js 产品型单体
适合需要登录、后台、订阅、Dashboard、复杂交互的 SaaS/产品

车道 C：VPS / Dokploy 重型兜底
适合 Docker、长驻服务、重 Python/Go、new-api、后台 worker、爬虫、浏览器自动化
```

默认选择顺序：

```text
能走车道 A 就走车道 A
车道 A 不够再走车道 B
需要 Docker/长驻进程/本地卷才走车道 C
```

这才符合个人开发者的现实约束：

- 成本低。
- 上线快。
- 运维少。
- 能复制。
- 能长期演进。
- 不过度设计。
- 不为 10 个用户预构建 1 万用户系统。

## 对旧单体文档的取舍

旧文档中值得保留的判断：

1. 成本是生存时间问题，不只是账单问题。
2. 默认不要上微服务、K8s、复杂队列。
3. SQLite/Turso 适合早期产品。
4. 基础设施要买成熟能力，但通过模块边界隔离 provider。
5. VPS/Dokploy 是多项目或重服务阶段的有用补充。
6. 单文件/单目录交付是战术工具，不是总战略。
7. 邮件、存储、支付、任务都要预留 provider abstraction。

需要修正的地方：

1. 旧文档偏向 `Next.js + Vercel + Turso` 作为默认主线；今天的实践证明，轻量应用默认应优先 Cloudflare Workers。
2. 旧文档把“单体应用”作为主要组织形态；现在应拆成“轻量应用工厂”和“产品型单体”两类。
3. 旧文档讨论 Dokploy/VPS 较多；现在它应作为重型兜底，不是默认上线路径。
4. 旧文档对版本号写得过死；后续应使用“当前 LTS / 当前稳定版”，避免文档过期。

## 总体架构

### 统一原则

```text
GitHub 是代码事实源
docs 是知识事实源
wrangler.jsonc / vercel.json / docker-compose.yml 是部署事实源
Cloudflare 是域名、HTTPS、防护和轻量应用默认运行层
Supabase/Turso/D1 是数据层，不是应用运行层
VPS/Dokploy 是重服务兜底，不是默认主线
```

### 项目分层

```text
展示层：HTML / React / Next.js / 静态资源
交互层：Worker API / Vercel Functions / Next.js Route Handlers
数据层：D1 / KV / R2 / Supabase / Turso
重服务层：VPS / Docker / Dokploy
知识层：github_workflow/docs
```

### 最小闭环

任何应用上线都必须形成：

```text
需求说明
-> 模板选择
-> 代码实现
-> 本地验证
-> 中文 commit
-> git push
-> 平台自动部署
-> 正式域名验证
-> 回退入口验证
-> docs 记录
```

## 车道 A：Cloudflare Workers 应用工厂

这是默认车道。

### 适用项目

- 落地页。
- 工具页。
- 表单收集。
- 线索收集。
- 分享页。
- 邀请裂变。
- 短链接。
- 文件上传。
- webhook。
- 简单 AI 工具壳。
- 不需要登录或只需要轻量登录的小后台。

### 推荐技术栈

```text
Language: TypeScript
Runtime: Cloudflare Workers
Router: Hono
Static: Workers Static Assets
DB: Cloudflare D1
Cache/short data: KV
Files: R2
Bot protection: Turnstile
Deploy: Workers Builds
Domain: Workers Custom Domains
Docs: github_workflow/docs
```

### 标准目录

```text
app-name/
  src/
    index.html
    assets/
    _headers
  worker/
    index.ts
    modules/
      form/
      invite/
      share/
      common/
  migrations/
  wrangler.jsonc
  README.md
```

### 数据选择

| 需求 | 默认选择 | 说明 |
| --- | --- | --- |
| 表单记录 | D1 | 结构化、可查询 |
| 邀请码 | D1 | 需要唯一约束和幂等 |
| 分享短链 | KV + D1 | KV 快速跳转，D1 统计 |
| 文件 | R2 | 文件不进数据库 |
| 配置 | KV | 读多写少 |
| 防刷 | Turnstile + D1/KV | 表单必须防刷 |

### 为什么这是默认车道

Cloudflare 官方 Static Assets 支持 Worker 代码和静态资源一次部署，形成一个紧密集成的单元。Workers GitHub/Builds 路线可以把 GitHub push 变成自动部署。Custom Domains 可以把子域名直接绑定 Worker。

这和我们已经跑通的 `ai.eforge.xyz` 模式一致。

### 上线标准命令

```bash
rtk git status --short
rtk git diff --check
rtk proxy npx wrangler deploy --dry-run
rtk git add <files>
rtk git commit -m "<中文原因>" -m "Tested: ..."
rtk git push origin main
rtk curl -I https://<正式域名>/
rtk curl -sS https://<正式域名>/ | rtk rg "<smoke-marker>"
rtk curl -I https://<workers-dev回退域名>/
rtk curl -sS https://<workers-dev回退域名>/ | rtk rg "<smoke-marker>"
```

### 什么时候不要走车道 A

出现以下任一条件，不要硬塞进 Workers：

- 需要完整 Node.js runtime。
- 需要本地 SQLite 文件持续写入。
- 需要长驻后台进程。
- 需要 Docker。
- 需要 Playwright/Chromium。
- Python/Go 依赖很重。
- 单次请求运行时间长。

这些进入车道 B 或 C。

## 车道 B：Next.js 产品型单体

这是产品车道，不是默认小工具车道。

### 适用项目

- 登录注册。
- 用户中心。
- 管理后台。
- SaaS Dashboard。
- 订阅付费。
- 多页面产品。
- SSR/SEO/内容产品。
- 强 React 交互。

### 推荐技术栈

```text
Runtime: Node.js 当前 LTS
Framework: Next.js 当前稳定版
Language: TypeScript
Package: pnpm
DB layer: Drizzle ORM
DB default: Supabase Postgres 或 Turso/libSQL
Auth: Auth.js / Better Auth
Payments: Stripe / Paddle
Email: Resend + SMTP fallback
Storage: R2
Monitoring: Sentry
Analytics: PostHog / Plausible
Deploy: Vercel
DNS: Cloudflare
```

### 数据库选择

| 场景 | 推荐 |
| --- | --- |
| SQLite 心智、低成本、轻 CRUD | Turso/libSQL |
| 需要 Auth、后台 SQL、关系复杂 | Supabase Postgres |
| 已经进入商业阶段 | Supabase Pro / Neon / 自管 Postgres |
| 单机私有部署 | SQLite + backup |

### 模块边界

产品型单体必须有模块边界，但不要拆微服务：

```text
modules/
  auth/
  billing/
  email/
  storage/
  analytics/
  permissions/
  jobs/
  ai/
```

规则：

- 页面和 route 不直接调用第三方 SDK。
- 业务代码只调用模块接口。
- 第三方 provider 藏在 infrastructure 层。
- 每个 provider 至少有一个本地/console/mock 兜底。

### 部署策略

默认：

```text
GitHub -> Vercel -> Cloudflare DNS
```

原因：

- Next.js 在 Vercel 上开发体验最省心。
- 预览部署成熟。
- 对个人开发者节省运维时间。

但必须保留可迁移能力：

- 不写 Vercel-only 业务逻辑。
- 环境变量保留 `.env.example`。
- 数据库和存储通过模块封装。
- 文档记录迁移路径。

### 什么时候不要走车道 B

- 只是一个落地页。
- 只是一个表单。
- 只是一个短链。
- 只是一个邀请页。
- 没有登录和复杂后台。

这些走车道 A 更快、更便宜、更好复制。

## 车道 C：VPS / Dokploy 重型兜底

这是兜底车道。

### 适用项目

- `new-api`。
- one-api 类网关。
- Docker Compose 项目。
- 长驻 Go/Python/Node 服务。
- WebSocket 常驻服务。
- 爬虫。
- Playwright/Chromium。
- 重后台任务。
- 文件处理。
- 私有化部署。

### 推荐技术栈

最低复杂度：

```text
VPS
-> Caddy
-> systemd
-> app process
-> SQLite/Postgres
-> R2 backup
-> Cloudflare DNS/WAF
```

多项目或 Docker 化：

```text
VPS
-> Dokploy
-> Docker Compose
-> per-app volume
-> Cloudflare DNS/WAF
-> R2 backup
```

### Dokploy 的位置

Dokploy 不是默认开发平台，而是：

```text
当你有多个 Docker/Node/Go/Python 长驻应用需要统一管理时的自建 PaaS
```

不要为了一个极简单应用上 Dokploy。

### new-api 推荐形态

```text
Cloudflare DNS / WAF / HTTPS
-> VPS / Dokploy / Docker Compose
-> new-api
-> SQLite volume 或 Supabase Postgres
-> R2 备份
```

不要把 new-api 硬改成 Workers/Vercel Functions。

## 极致开发方案

### 新项目启动流程

每个新项目先回答 6 个问题：

```text
1. 是否需要长驻进程？
2. 是否需要登录？
3. 是否需要后台管理？
4. 是否需要文件？
5. 是否需要复杂 SQL？
6. 是否需要 Docker 或系统依赖？
```

判定：

```text
长驻/Docker/重依赖 -> 车道 C
Next.js 产品后台 -> 车道 B
其余默认 -> 车道 A
```

### 模板优先级

先做 5 个模板，不做大平台：

```text
landing-template      落地页
form-template         表单收集
invite-template       邀请裂变
share-template        分享/短链
dashboard-template    产品型后台
```

每个模板必须包含：

- smoke marker。
- README。
- docs 说明。
- 部署配置。
- 最小测试。
- curl 验收命令。
- 域名绑定说明。

### 不要做什么

不要一开始做：

- 通用 SaaS 大平台。
- 插件系统。
- 多租户架构。
- 微服务。
- Kubernetes。
- 自研认证。
- 自研支付。
- 自研邮件系统。
- 复杂权限平台。

## 极致运维方案

### 域名规范

```text
ai.eforge.xyz          AI 工具入口
tools.eforge.xyz       工具集合
forms.eforge.xyz       表单收集
invite.eforge.xyz      邀请裂变
go.eforge.xyz          短链跳转
api.eforge.xyz         API 网关
admin.eforge.xyz       管理后台
```

规则：

- 根域不做实验。
- 每个正式应用一个子域名。
- workers.dev / vercel.app / VPS health URL 保留回退。
- 域名绑定必须写 docs。

### Token 策略

```text
Deploy Token：部署
Readonly Ops Token：读取状态
Domain Ops Token：域名/DNS 变更
Database Token：数据库迁移
Storage Token：R2/S3 文件
```

规则：

- 不长期使用全权限 token。
- 出现在聊天、日志、命令历史里的 token 视为泄露。
- Domain Ops Token 只在域名变更时启用。
- token 不写入 docs、README、commit。

### 数据备份

按数据层分：

```text
D1：导出 schema + 定期导出关键表
Supabase：至少 Pro 后启用正式备份；Free 阶段要手动导出
Turso：记录备份/导出命令
SQLite：每日复制到 R2
R2：设置生命周期和版本策略
VPS volume：定期压缩上传 R2
```

低负载阶段可以先做到：

```text
每日备份
保留 7 天
每次重要发布前手动备份
```

### 监控

最低要求：

```text
curl uptime check
平台部署日志
错误日志
Cloudflare Analytics
```

产品型单体增加：

```text
Sentry
PostHog
关键漏斗事件
邮件发送失败记录
支付 webhook 失败记录
```

VPS 增加：

```text
systemd status
journald logs
磁盘空间
内存
备份是否成功
```

## 极致 AI 工作流

AI 接管部署不是让 AI 随便改，而是让它按固定 SOP 执行。

每次任务必须执行：

```text
1. 读取 docs 中的对应方案
2. 确认车道 A/B/C
3. 读取当前仓库结构和部署配置
4. 修改核心功能
5. 同步 docs
6. 本地验证
7. 中文 Lore commit
8. push
9. 线上 curl 验证
10. 写踩坑或闭环记录
```

AI 不允许：

- 不读全局文档就改。
- 不验证就说完成。
- 不提交。
- 不同步 docs。
- 直接创建第二套部署平台。
- 把临时兜底当主路径。

## 决策矩阵

| 项目类型 | 车道 | 平台 | 数据 | 备注 |
| --- | --- | --- | --- | --- |
| 纯落地页 | A | Cloudflare Workers Static Assets | 无 | 最快 |
| 带表单落地页 | A | Workers + D1 | D1 | 默认 |
| 邀请裂变 | A | Workers + D1 | D1 | 幂等与防刷 |
| 短链分享 | A | Workers + KV/D1 | KV+D1 | KV 跳转，D1 统计 |
| 文件上传 | A | Workers + R2 | R2+D1 | 文件不进 DB |
| 简单 AI 工具 | A | Workers | D1/R2 | 轻代理 |
| SaaS Dashboard | B | Vercel + Next.js | Supabase/Turso | 登录和后台 |
| 会员内容站 | B | Vercel/Cloudflare | Supabase | Auth 更重要 |
| 支付订阅产品 | B | Vercel | Supabase/Turso | Stripe/Paddle |
| new-api | C | VPS/Dokploy | SQLite/Postgres | Docker 长驻 |
| Python 重应用 | C | VPS/Docker | Postgres/SQLite | 不硬塞 serverless |
| Go 长驻后端 | C | VPS/systemd | Postgres/SQLite | 简洁稳定 |

这样后续应用变多也不会失控。

## 当前最优最终方案

如果只保留一句话：

```text
以 Cloudflare Workers 应用工厂作为默认上线能力，以 Next.js 产品型单体作为复杂产品能力，以 VPS/Dokploy 作为重型服务兜底；所有能力通过模板、docs、GitHub push、自动部署、Custom Domain、curl 验证形成可复制闭环。
```

这比单纯押注 Vercel、单纯押注 Cloudflare、或者单纯自建 VPS 都更优。

原因：

- Cloudflare 负责最高频的小应用量产。
- Vercel/Next.js 负责复杂产品体验。
- Supabase/Turso/R2 负责托管数据和存储。
- VPS/Dokploy 只处理真正需要长驻服务的重任务。
- docs 和模板避免每次重新设计。
- AI 可以沿固定 SOP 接管开发、部署、验证、记录。
