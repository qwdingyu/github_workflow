# Cloudflare 配置层安全基线脚本

## 背景

前面的部署闭环已经解决：

```text
本地开发
-> GitHub
-> Cloudflare Pages / Workers
-> 自定义域名
-> HTTPS
-> curl / smoke 验证
```

现在需要补上配置层安全基线。这里的“配置层”不是改业务代码，而是利用 Cloudflare zone、WAF、TLS、Transform Rules、静态资源 `_headers` 等能力，为不同项目建立最低成本、可复用、可脚本化的基础防护。

## 结论

个人开发者最优做法是：

```text
Cloudflare 配置层：挡扫描、强制 HTTPS、限制危险路径、保护管理路径、补响应头。
应用代码层：校验输入、Turnstile、防重放、限流、鉴权、审计日志。
数据层：D1/KV/R2 最小权限、私有化存储、备份和密钥隔离。
```

配置层不能替代业务安全。尤其是发卡、填表、邀请、下载、支付回调这类写接口，仍然必须在 Worker/服务端代码中做 Turnstile、限流、幂等和权限校验。

## 新增脚本

### 1. Cloudflare zone 安全基线脚本

路径：

```text
scripts/cloudflare/security_baseline.mjs
```

用途：

```text
1. 配置 zone 级 HTTPS/TLS/浏览器安全设置。
2. 创建或更新 WAF Custom Rules。
3. 可选创建或更新响应头 Transform Rule。
4. 通过稳定 ref 幂等更新本脚本创建的规则。
5. 保留已有人工规则，不删除其他规则。
```

默认行为：

```text
只预览，不写入 Cloudflare。
```

写入条件：

```text
CF_APPLY=true
```

这是刻意设计。配置层改动会影响整个 zone，不能默认直接写入。

### 2. 静态资源 `_headers` 生成脚本

路径：

```text
scripts/cloudflare/write_security_headers.mjs
```

用途：

```text
为 Cloudflare Pages 或 Workers Static Assets 生成 _headers 文件。
```

默认写入：

```text
public/_headers
```

可覆盖：

```text
CF_HEADERS_FILE="src/_headers"
CF_HEADERS_FILE="dist/_headers"
```

默认不覆盖已有文件，避免误删项目已有 CSP。

覆盖条件：

```text
CF_OVERWRITE_HEADERS=true
```

## 安全基线脚本变量

### 必填变量

二选一提供 zone：

```text
CF_ZONE_ID
CF_ZONE_NAME
```

如果提供了 `CF_CUSTOM_DOMAIN`，脚本会尝试从域名推导 zone，例如：

```text
acctbox.eforge.xyz -> eforge.xyz
```

必须提供目标域名：

```text
CF_CUSTOM_DOMAIN
```

或多个目标域名：

```text
CF_TARGET_HOSTNAMES="acctbox.eforge.xyz,shop.eforge.xyz"
```

鉴权二选一：

```text
CF_API_TOKEN="<scoped-api-token>"
```

或：

```text
CF_AUTH_EMAIL="<cloudflare-login-email>"
CF_GLOBAL_API_KEY="<global-api-key>"
```

最佳实践是 scoped API Token。Global API Key 只作为临时兜底，不应长期放在自动化环境里。

### 场景变量

```text
CF_SECURITY_SCENARIO="static"
CF_SECURITY_SCENARIO="app"
CF_SECURITY_SCENARIO="form"
```

含义：

| 场景 | 适用项目 | 默认策略 |
| --- | --- | --- |
| `static` | 纯静态落地页、展示页 | 强 HTTPS、阻断危险路径、管理路径挑战，可选阻断非 GET/HEAD |
| `app` | 静态站 + 少量 API | 强 HTTPS、阻断危险路径、管理路径挑战 |
| `form` | 表单、发卡、邀请、下载申请 | 配置层做基础防护，公开写接口必须代码层 Turnstile + 限流 |

不要把 `form` 场景误解成“WAF 能保护所有表单”。WAF 只能挡通用恶意流量，无法理解业务库存、订单、联系方式、支付回调。

### Zone 设置变量

默认启用：

```text
CF_ENABLE_ZONE_SETTINGS=true
```

脚本会写入：

```text
always_use_https=on
automatic_https_rewrites=on
min_tls_version=1.2
tls_1_3=on
brotli=on
browser_check=on
challenge_ttl=1800
security_level=medium
```

可调整：

```text
CF_MIN_TLS_VERSION="1.2"
CF_SECURITY_LEVEL="medium"
CF_CHALLENGE_TTL="1800"
```

默认不修改 SSL mode：

```text
CF_APPLY_SSL_MODE=false
```

原因：

```text
Cloudflare Pages / Workers 通常不需要手动改 SSL mode。
如果同一个 zone 下还有传统源站，强行改 SSL mode 可能导致源站不可访问。
```

只有确认整个 zone 的源站证书都没问题时，才显式执行：

```bash
CF_APPLY_SSL_MODE=true \
CF_SSL_MODE="full" \
CF_APPLY=true \
rtk node scripts/cloudflare/security_baseline.mjs
```

HSTS 不在脚本默认配置中。

原因：

```text
HSTS 尤其是 preload 有回滚成本。
个人项目应等域名、证书、所有子域名稳定后再单独开启。
```

### WAF 规则变量

默认启用：

```text
CF_ENABLE_WAF_RULES=true
```

默认阻断危险路径：

```text
/.env
/.git
/wp-admin
/wp-login.php
/phpmyadmin
/vendor
/node_modules
```

可覆盖：

```bash
CF_DANGEROUS_PATHS="/.env,/.git,/wp-admin,/wp-login.php"
```

默认挑战管理路径：

```text
/admin
/internal
```

可覆盖：

```bash
CF_ADMIN_PATHS="/admin,/dashboard,/internal"
```

纯静态站可开启方法白名单：

```bash
CF_SECURITY_SCENARIO="static" \
CF_BLOCK_STATIC_UNSAFE_METHODS=true
```

这会阻断非 GET/HEAD 请求。

注意：

```text
如果静态站未来加入 Pages Functions、Worker API 或表单 POST，不要开启这个开关。
```

### 响应头 Transform Rule

默认不启用：

```text
CF_ENABLE_HEADER_TRANSFORM=false
```

原因：

```text
Pages / Workers Static Assets 更推荐在项目内使用 _headers。
Transform Rule 是 zone 级配置，适合临时兜底或统一补漏，但不应掩盖项目配置缺失。
```

如需启用：

```bash
CF_ENABLE_HEADER_TRANSFORM=true \
CF_APPLY=true \
rtk node scripts/cloudflare/security_baseline.mjs
```

脚本设置：

```text
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
X-Frame-Options: DENY
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
```

不在 Transform Rule 默认设置完整 CSP。

原因：

```text
CSP 和应用资源强相关。
不同项目可能需要不同 script-src、connect-src、frame-src。
完整 CSP 应优先写在项目的 _headers 或 Worker 响应中。
```

## 推荐执行路径

### 纯静态站

先预览：

```bash
CF_AUTH_EMAIL="<cloudflare-login-email>" \
CF_GLOBAL_API_KEY="<global-api-key>" \
CF_CUSTOM_DOMAIN="shop.eforge.xyz" \
CF_SECURITY_SCENARIO="static" \
CF_BLOCK_STATIC_UNSAFE_METHODS=true \
rtk node scripts/cloudflare/security_baseline.mjs
```

确认预览输出合理后写入：

```bash
CF_AUTH_EMAIL="<cloudflare-login-email>" \
CF_GLOBAL_API_KEY="<global-api-key>" \
CF_CUSTOM_DOMAIN="shop.eforge.xyz" \
CF_SECURITY_SCENARIO="static" \
CF_BLOCK_STATIC_UNSAFE_METHODS=true \
CF_APPLY=true \
rtk node scripts/cloudflare/security_baseline.mjs
```

项目内生成 `_headers`：

```bash
CF_HEADERS_FILE="src/_headers" \
CF_HEADERS_SCENARIO="static" \
rtk node ../scripts/cloudflare/write_security_headers.mjs
```

如果已有 `_headers` 并确认要覆盖：

```bash
CF_HEADERS_FILE="src/_headers" \
CF_HEADERS_SCENARIO="static" \
CF_OVERWRITE_HEADERS=true \
rtk node ../scripts/cloudflare/write_security_headers.mjs
```

### 静态站 + 少量 API

预览：

```bash
CF_AUTH_EMAIL="<cloudflare-login-email>" \
CF_GLOBAL_API_KEY="<global-api-key>" \
CF_CUSTOM_DOMAIN="acctbox.eforge.xyz" \
CF_SECURITY_SCENARIO="app" \
rtk node scripts/cloudflare/security_baseline.mjs
```

写入：

```bash
CF_AUTH_EMAIL="<cloudflare-login-email>" \
CF_GLOBAL_API_KEY="<global-api-key>" \
CF_CUSTOM_DOMAIN="acctbox.eforge.xyz" \
CF_SECURITY_SCENARIO="app" \
CF_APPLY=true \
rtk node scripts/cloudflare/security_baseline.mjs
```

项目内 `_headers` 建议：

```bash
CF_HEADERS_FILE="public/_headers" \
CF_HEADERS_SCENARIO="app" \
CF_CONNECT_SRC="'self'" \
rtk node ../scripts/cloudflare/write_security_headers.mjs
```

### 表单 / 发卡 / 邀请

配置层只做基础防护：

```bash
CF_AUTH_EMAIL="<cloudflare-login-email>" \
CF_GLOBAL_API_KEY="<global-api-key>" \
CF_CUSTOM_DOMAIN="acctbox.eforge.xyz" \
CF_SECURITY_SCENARIO="form" \
CF_APPLY=true \
rtk node scripts/cloudflare/security_baseline.mjs
```

必须同步做代码层：

```text
1. POST 接口接 Turnstile。
2. Worker 内部按 IP + 联系方式 + action 限流。
3. 订单/提交加 idempotency_key。
4. 管理接口使用 ADMIN_TOKEN 或 Cloudflare Access。
5. 写入 request_logs / audit_logs。
```

如果没有完成这些，不允许宣称“发卡/表单已安全可运营”。

## 权限要求

建议 scoped token 权限：

```text
Zone - Zone Settings - Edit
Zone - WAF - Edit
Zone - Zone - Read
```

如果要使用 Transform Rule，仍属于 Rulesets 相关能力，通常也需要 Zone 级规则编辑权限。

如果只是生成 `_headers`，不需要 Cloudflare API 权限。

## 验证命令

检查 HTTPS 和响应头：

```bash
rtk curl -sS -I https://acctbox.eforge.xyz/
```

检查危险路径是否被拦截：

```bash
rtk curl -sS -I https://acctbox.eforge.xyz/.env
rtk curl -sS -I https://acctbox.eforge.xyz/.git/config
```

检查管理路径是否触发 Cloudflare challenge：

```bash
rtk curl -sS -I https://acctbox.eforge.xyz/admin
```

可能看到：

```text
403
Managed Challenge 相关响应
Cloudflare challenge 页面
```

这说明规则在边缘生效。不要用业务 Worker 的返回内容判断 WAF 是否生效。

检查业务 API：

```bash
BASE_URL="https://acctbox.eforge.xyz" rtk npm run verify
```

发卡类写入 smoke 要谨慎，因为可能消耗库存。常规巡检优先使用只读 verify。

## 踩坑记录

### 1. 不要把 Pages CNAME 和 Workers Custom Domain 混用

Pages：

```text
自定义域名 -> DNS CNAME -> project.subdomain
```

Workers：

```text
Workers Custom Domains API -> Cloudflare 自动生成只读 AAAA 100::
```

安全脚本只处理 zone 配置和 WAF，不负责绑定 Pages/Workers 域名。域名绑定继续使用：

```text
scripts/cloudflare/pages_github_domain_workflow.mjs
scripts/cloudflare/workers_custom_domain_bind.mjs
```

### 2. 不要默认开 HSTS preload

HSTS preload 一旦提交到浏览器列表，回滚慢。个人项目、试点项目、频繁更换子域名时不适合默认开启。

### 3. 不要对所有 API 加 Managed Challenge

浏览器访问可以 challenge，但 server-to-server webhook、支付回调、第三方 API 调用不适合 challenge。

写接口更稳的做法：

```text
Turnstile
应用内限流
幂等键
签名校验
```

### 4. 不要让脚本覆盖人工规则

`security_baseline.mjs` 只维护这些稳定 ref：

```text
cf_baseline_block_dangerous_paths
cf_baseline_challenge_admin_paths
cf_baseline_static_method_allowlist
cf_baseline_security_headers
```

更新时会保留其他规则。未来新增规则也必须使用稳定 ref，避免重复创建。

### 5. 免费层 WAF 配额有限

Cloudflare 免费层 Custom Rules 数量有限，不适合为每个路径创建一条规则。

本脚本把多个危险路径合并成一条规则，把多个管理路径合并成一条规则，目的就是节省配额。

## 最小复用清单

新项目上线时按顺序执行：

```text
1. 判断项目类型：static / app / form。
2. 先完成 GitHub -> Cloudflare -> 域名 -> HTTPS。
3. 生成项目内 _headers。
4. 预览 security_baseline.mjs。
5. 确认规则表达式只命中目标域名。
6. 设置 CF_APPLY=true 写入。
7. curl 验证 HTTPS、响应头、危险路径、管理路径。
8. 跑项目 verify/smoke。
9. 把域名、项目类型、脚本命令、验证结果写入 docs。
10. 提交并 push。
```
