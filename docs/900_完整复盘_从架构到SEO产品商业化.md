### 007 文档的核心发现

对 eshop（发卡商城）、xtools（在线工具集）、vcode（验证码 API）三个已上线项目做了全量代码审计：

| 项目 | 后端代码 | 前端代码 | 数据库表 | 总代码量 |
|------|---------|---------|---------|---------|
| eshop | ~6,074 行 / 25 文件 | ~8,099 行 (Vue3+管理端) | 16 张 | ~21,400 行 |
| xtools | ~7,306 行 / 22 文件 | ~3,766 行 (原生 HTML) | 3 张 | ~13,520 行 |
| vcode | ~7,891 行 / 23 文件 | ~3,000 行 (原生 HTML) | 10 张 | ~18,946 行 |

**核心发现：**
- 技术栈完全一致：Hono + Turso (libSQL) + Drizzle + TypeScript + Cloudflare Workers
- 基础设施层代码重复度 >90%（http.ts、security.ts、rate-limit.ts、DB 初始化等）
- 业务模式层重复度 >70%（Adapter/Registry 模式在三项目中都有）
- DevOps 层重复度 >80%（CI/CD、部署脚本、冒烟测试）

**提出的三层架构方案：**
1. **Layer 1：共享内核** `@eforge/cf-core` — 抽取公共基础设施
2. **Layer 2：产品模板** `cf-shop` / `cf-tools` / `cf-api` — 三类业务模板
3. **Layer 3：业务插件** — 可插拔功能模块（支付、邮件、OAuth 等）

**目标：** "30 分钟从模板到上线"的批量产品工厂

## 三、技术架构决策与踩坑记录

### 3.1 数据库选型：D1 → Turso 的血泪史

#### 初始错误：选择了 D1

最初方案选择了 Cloudflare D1（嵌入式 SQLite），理由看似合理：
- Cloudflare 原生集成
- wrangler 直接管理
- 零配置绑定

**致命问题：**

| 指标 | D1 Free | SEO Guardian 需求 | 差距 |
|------|---------|------------------|------|
| 存储空间 | 5 MB | 每次扫描 ~2-5KB，100 站点 × 30 次/月 = ~150KB 基础 | 看似够用 |
| 行读取 | 500 万行/天 | 全量扫描 + 周报 + 仪表盘 = 实际远超 | **严重不足** |
| 行写入 | 10 万行/天 | 每次扫描写入 scans + alerts + geo_checks = ~50 行/站点 | **100 站点就爆** |
| 单次查询 | 有限制 | GEO 检查需要多表 JOIN | **性能瓶颈** |

**数学证明 D1 不行：**
- 100 个站点，每天 1 次扫描
- 每次扫描：1 次 scans 写入 + 平均 5 次 alerts 写入 + 平均 8 次 geo_checks 写入 = 14 行
- 每天：100 × 14 = 1,400 行写入
- 每月 Cron 周报：额外 ~5,000 行读取
- 用户日常访问仪表盘：每天 ~200 次查询 × 100 用户 = 20,000 次读取
- **月写入：42,000 行（接近 Free 上限的 42%）**
- **月读取：600,000+ 行（超过 Free 上限的 12%）**
- 只要用户量翻倍，立刻超限

#### 正确选择：Turso (libSQL)

| 指标 | Turso Free | SEO Guardian 需求 | 结论 |
|------|-----------|------------------|------|
| 存储空间 | 8 GB/月 | 预计 <100 MB | ✅ 充裕 80 倍 |
| 行读取 | 无限制 | 任意 | ✅ 无瓶颈 |
| 行写入 | 无限制（公平使用） | 任意 | ✅ 无瓶颈 |
| 分布式 | ✅ 原生 | 全球用户 | ✅ 低延迟 |
| SQLite 兼容 | ✅ 100% | 现有 SQL 语法 | ✅ 零迁移成本 |

**Turso 的隐藏优势：**
- HTTP API 天然适合 Workers 环境（通过 `@libsql/client` 的 HTTP 模式）
- 支持 libsql 扩展语法（未来可用 append-only 表做日志）
- 8GB Free 可支撑数万个站点的数据

### 3.2 踩坑记录：D1 → Turso 迁移中的 Bug

#### Bug 1：`createTursoDB` 导入但从未调用

**问题：** `index.ts` 导入了 `createTursoDB`，但从未在 HTTP 请求中调用它。Turso 不是 Workers 原生 binding，不能像 D1 那样通过 `env.DB` 直接获取。

**根因：** 误以为 Turso 可以像 D1 一样通过 `wrangler.jsonc` 的 `d1_databases` 配置自动注入。

**修复：** 添加 HTTP middleware，每个请求用 `TURSO_DB_URL` + `TURSO_AUTH_TOKEN` 创建 client：

```typescript
app.use("/api/*", async (c, next) => {
  const db = createTursoDB(c.env.TURSO_DB_URL, c.env.TURSO_AUTH_TOKEN || undefined);
  Object.defineProperty(c.env, "DB", { value: db, writable: false, configurable: false });
  return next();
});
```

#### Bug 2：Cron 和 Queue 处理器无法访问 DB

**问题：** Cron 处理器 (`cronHandler`) 和 Queue 消费者 (`queueConsumer`) 不走 HTTP middleware，`env.DB` 为 undefined。

**根因：** 只考虑了 HTTP 请求路径，忽略了 Workers 的其他触发方式。

**修复：** 在 cron 和 queue 入口手动创建 Turso client：

```typescript
// cron.ts
export async function cronHandler(c: Context) {
  const env = c.env as Env;
  const db = createTursoDB(env.TURSO_DB_URL, env.TURSO_AUTH_TOKEN || undefined);
  Object.defineProperty(env, "DB", { value: db, writable: false, configurable: false });
  // ...
}
```

#### Bug 3：Turso adapter 字段名错误

**问题：** `turso.ts` adapter 的 `run()` 方法使用了错误的字段名：
- `result.changes` → 实际是 `result.rowsAffected`
- `result.lastRowId` → 实际是 `result.lastInsertRowid`

**根因：** 参考了 D1 的返回结构，但 `@libsql/core@0.14.0` 的 `ResultSet` 接口字段名不同。

**修复：**
```typescript
async run(): Promise<DBRunResult> {
  const result = await client.execute({ sql, args });
  return {
    changes: result.rowsAffected ?? 0,           // ✅ 正确
    lastRowId: result.lastInsertRowid != null ? String(result.lastInsertRowid) : 0,  // ✅ 正确
    meta: {},
  };
}
```

#### Bug 4：`lastInsertRowid` 类型不匹配

**问题：** `@libsql/core` 返回的 `lastInsertRowid` 是 `bigint | undefined`，但 `DBRunResult` 接口要求 `string | number`。

**修复：** 用 `String()` 显式转换。

### 3.3 架构教训总结

| 教训 | 场景 | 预防措施 |
|------|------|---------|
| **Workers binding ≠ 所有数据库** | Turso 不是原生 binding | 部署前检查 `wrangler.jsonc` 是否有对应 binding 配置 |
| **三条入口必须分别处理** | HTTP / Cron / Queue | 建立 checklist：每次加数据库支持，检查三个入口 |
| **第三方库 API 必须读源码** | `@libsql/core` 字段名与 D1 不同 | 不要假设 API 兼容，必须查看实际类型定义 |
| **TypeScript 类型要精确** | `bigint` vs `string \| number` | 严格模式 + 定期 `tsc --noEmit` |

## 九、关键决策回顾

### 9.1 做对了的决策

| 决策 | 理由 | 结果 |
|------|------|------|
| 选 Turso 而非 D1 | D1 Free 5MB 完全不够用 | ✅ 8GB 空间，无读写限制 |
| 选 Hono 而非 Express | Workers 原生支持，冷启动快 | ✅ 生态成熟，类型安全 |
| 选原生 HTML 而非 React | 减少构建步骤，Pages 直接托管 | ✅ 部署简单，加载快 |
| 用 Queues 做异步扫描 | 避免超时，可重试 | ✅ 可靠的任务处理 |
| 用 Workers AI 做摘要 | 零额外成本，原生集成 | ✅ 差异化功能 |
| 数据保留策略 | 90 天自动清理 | ✅ 控制存储增长 |

### 9.2 做错的决策

| 决策 | 问题 | 修正 |
|------|------|------|
| 初始选 D1 | Free 限额数学上就不行 | 迁移到 Turso |
| 假设 Turso 是原生 binding | 需要手动创建 client | 添加 middleware + 手动注入 |
| 只考虑 HTTP 入口 | Cron/Queue 也需要 DB | 三个入口分别处理 |
| 复制 D1 adapter 字段名 | `@libsql/core` API 不同 | 读源码，修正字段名 |
