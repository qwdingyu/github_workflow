    可行性分析：支付配置迁移到 Web 管理后台

    ---

    一、new-api 的参考价值

    new-api 的 Channel 模式就是我们的目标模版：


    ┌─────────────────────────────────────────────────────────────┬────────────────────────────────────┐
    │ new-api 特性                                                │ cf-shop 可借鉴                     │
    ├─────────────────────────────────────────────────────────────┼────────────────────────────────────┤
    │ 渠道（Channel）配置全部在 DB + Web UI 管理，无 env var 依赖 │ 对应每个支付 Provider 是一个"渠道" │
    ├─────────────────────────────────────────────────────────────┼────────────────────────────────────┤
    │ API Key 只要管理员权限即可查看（有安全验证保护）            │ 支付私钥更敏感，需要加密存储       │
    ├─────────────────────────────────────────────────────────────┼────────────────────────────────────┤
    │ 启动时全量加载到内存，定时刷新                              │ Workers 无常驻进程，需按需加载     │
    ├─────────────────────────────────────────────────────────────┼────────────────────────────────────┤
    │ 提供商的 API Key 不在环境变量中                             │ 这正是我们要达到的目标             │
    ├─────────────────────────────────────────────────────────────┼────────────────────────────────────┤
    │ 列表 API 默认 Omit Key，不返回敏感字段                      │ 已内置 _key/_secret/_token 脱敏    │
    └─────────────────────────────────────────────────────────────┴────────────────────────────────────┘

    关键差异：new-api 明文存储凭据，靠数据库和 API 层访问控制保护。cf-shop 不能这么做 — 支付私钥（如 Alipay RSA
    私钥）泄露风险极高，必须 AES-256-GCM 加密存储。好在 cf-core 已提供此能力。

    3.1 DB 存储设计

    复用 systemConfig 表，用前缀区分：

     1 Key: payment_provider:zpay
     2 Value: enc:<AES-256-GCM base64>

    加密内容（解密后）：
      1 {
      2   "enabled": true,
      3   "type": "zpay",
      4   "config": {
      5     "ZPAY_PID": "xxx",
      6     "ZPAY_KEY": "xxx",
      7     "ZPAY_GATEWAY": "https://zpayz.cn/mapi.php",
      8     "ZPAY_QUERY_API": "https://zpayz.cn/api.php",
      9     "ZPAY_RETURN_URL": ""
     10   }
     11 }

    3.2 Factory 重构（最小侵入）

    当前 Factory 签名：
     1 interface ProviderFactory {
     2   name: string;
     3   priority: number;
     4   isAvailable(env: Record<string, unknown>): boolean;
     5   create(env: Record<string, unknown>): PaymentProvider;
     6 }

    新增 fromDbConfig 可选方法，不破坏现有接口：
     1 interface ProviderFactory {
     2   name: string;
     3   priority: number;
     4   isAvailable(env: Record<string, unknown>): boolean;
     5   create(env: Record<string, unknown>): PaymentProvider;
     6
     7   // 可选：从 DB 配置对象创建，DB 配置优先于 env
     8   fromDbConfig?(config: Record<string, unknown>): PaymentProvider;
     9 }

    createProviderRegistry 的签变更：
     1 function createProviderRegistry(
     2   env: Record<string, unknown>,
     3   factories: ProviderFactory[],
     4   dbConfigs?: Record<string, Record<string, unknown>>,  // 新增
     5 ): ProviderRegistry

    调用方（pay.ts 等）：
     1 const dbConfigs = await loadPaymentProviderConfigs(db, encryptionKey);
     2 const registry = createProviderRegistry(c.env, factories, dbConfigs);

    3.3 冷启动性能

    每次冷启动加载全部支付配置（5-8 个 Provider，总数据量 < 2KB），解密后合并到 env。

     - Turso HTTP 查询耗时：~20-50ms（新加坡边缘节点）
     - AES-256-GCM 解密：~5-10ms（Web Crypto API 硬件加速）
     - 总计 < 60ms，可接受

    也可用 Cache API 缓存配置（TTL 60s），进一步降低对 Turso 的调用频率。

    结论

    方案可行，且与 cf-core 现有加密能力和 systemConfig 表完全兼容。 new-api 的"DB + Web UI
    管理提供商配置"模式可以直接借鉴，区别在于我们需要加一层 AES 加密（cf-core crypto.ts 已就绪），new-api
    没有这个能力也不需要。
