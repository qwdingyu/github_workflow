# 支付生命周期与发卡流程分析

> 日期：2026-06-25
> 背景：梳理 cf-shop 五种订单模式（balance / online / offline / direct / manual）的完整生命周期，明确"创建订单"与"发卡"的时序关系
> 目标：为前端收银台、管理员后台、测试用例提供权威流程依据

---

## 一、核心结论速查

| 模式 | 创建订单后 | 是否立即发卡 | 后续触发发卡的条件 |
|------|-----------|-------------|------------------|
| **余额支付** | `/pay/unified` 返回 | ✅ 是 | 无；创建订单后同步调用 `handleBalancePayment` → `markPaidAndIssue` |
| **线上支付** | `/pay/unified` 返回支付信息 | ❌ 否 | 支付平台异步回调 `/pay/callback/:provider` 验签通过后调用 `markPaidAndIssue` |
| **线下支付** | `/pay/unified` 返回收款信息 | ❌ 否 | 管理员后台点击 `/admin/orders/:id/mark-paid` 调用 `markPaidAndIssue` |
| **/orders direct** | `/orders` 返回 | ✅ 是 | 创建订单时直接 `fulfillCardInventory` + 写 `issued` |
| **/orders manual** | `/orders` 返回 | ❌ 否 | 管理员后台点击 `/admin/orders/:id/mark-paid` 调用 `markPaidAndIssue` |

## 二、完整生命周期图

### 2.1 余额支付（balance）

```
前端提交 /pay/unified { balancePayment: true }
    ↓
后端创建订单（status = pending）
    ↓
handleBalancePayment
    ├─ 查询 user_balances
    ├─ 原子扣减余额
    └─ markPaidAndIssue
         ├─ checkAndExpireOrder（如已过期则作废）
         ├─ pending → paid（原子 UPDATE）
         ├─ fulfillCardInventory（领取卡密）
         └─ 更新 status = issued + issuedCardId
    ↓
前端收到 { mode: "balance", status: "issued", delivery: {...} }
    ↓
前端直接展示成功结果 + 卡密
```

### 2.2 线上支付（online）

```
前端提交 /pay/unified { balancePayment: false }
    ↓
后端创建订单（status = pending）
    ↓
Provider.createPayment（生成二维码/跳转链接）
    ↓
前端收到 { mode: "online", qrcode: "..." }
    ↓
用户扫码支付
    ↓
支付平台异步回调 /pay/callback/:provider
    ↓
provider.verifyCallback（验签）
    ↓
markPaidAndIssue
    ├─ pending → paid
    ├─ fulfillCardInventory
    └─ 更新 status = issued
    ↓
前端轮询 /pay/status/:orderId?token=xxx
    ├─ pending → 继续轮询
    ├─ paid → 显示"正在发卡"
    └─ issued → 显示成功 + delivery
```

### 2.3 线下支付（offline）

```
前端提交 /pay/unified
    ↓
后端创建订单（status = pending）
    ↓
返回 { mode: "offline", wechatQr, alipayQr, offlineNoteCode }
    ↓
前端展示收款码 + 倒计时
    ↓
用户扫码付款 + 输入流水号后4位 + 点击确认
    ↓
/pay/offline/confirm { orderId, orderToken, payRefLast4 }
    ↓
后端记录 paymentRef = "last4:1234"
    ↓
前端开始轮询 /pay/status/:orderId?token=xxx
    ↓
管理员后台点击"确认收款"
    ↓
/admin/orders/:id/mark-paid
    ↓
markPaidAndIssue
    ├─ pending → paid
    ├─ fulfillCardInventory
    └─ 更新 status = issued
    ↓
前端轮询到 issued → 显示成功 + delivery
```

### 2.4 /orders direct 模式

```
前端提交 /api/orders { productId, buyerEmail }
    ↓
后端校验商品 + 优惠码
    ↓
fulfillCardInventory（原子领卡）
    ↓
创建订单（status = issued，直接写入 issuedCardId）
    ↓
消耗 coupon（如有）
    ↓
发送邮件通知（异步）
    ↓
前端直接收到 { status: "issued", delivery: {...} }
```

### 2.5 /orders manual 模式

```
前端提交 /api/orders { productId, buyerEmail }
    ↓
后端校验商品 + 优惠码
    ↓
软锁定卡密（lockFulfillmentInventory）
    ↓
创建订单（status = pending）
    ↓
发送邮件通知（异步）
    ↓
前端收到 { status: "pending" }
    ↓
管理员后台点击"确认发卡"
    ↓
/admin/orders/:id/mark-paid
    ↓
markPaidAndIssue
    ├─ pending → paid
    ├─ fulfillCardInventory（领取已锁定的卡密）
    └─ 更新 status = issued
    ↓
发送发卡邮件通知（异步）
```

### 3.6 markPaidAndIssue：统一履约入口

**文件**：`templates/cf-shop/src/services/order-service.ts`

```typescript
export async function markPaidAndIssue(db, orderId, env?, executionCtx?) {
  // 1. 检查过期
  const { expired: wasExpired } = await checkAndExpireOrder(...);
  if (wasExpired) return { ok: false, status: 410, message: "订单已过期" };
  
  // 2. pending → paid（原子 UPDATE）
  if (order.status === "pending") {
    const locked = await db.update(orders)
      .set({ status: "paid", paidAt: nowStr })
      .where(and(eq(orders.id, order.id), eq(orders.status, "pending")))
      .returning({ id: orders.id });
  }
  
  // 3. 领取卡密（优先领取该订单软锁的卡密）
  issued = (await fulfillCardInventory(db, order.id, order.productId))?.card;
  
  // 4. 更新为已发卡
  await db.update(orders)
    .set({ status: "issued", issuedCardId: issued.id, issuedAt: nowStr })
    .where(eq(orders.id, order.id));
  
  // 5. 消耗 coupon（如有）
  if (order.couponCode) {
    await consumeCoupon(db, order.couponCode);
  }
  
  return { ok: true, card: issued };
}
```

## 四、前端轮询逻辑

### 4.1 余额支付

- **不轮询**。创建订单后同步返回 `status: "issued"` + `delivery`，前端直接展示结果。
- **文件**：`templates/cf-shop/frontend/src/components/PayModal.vue`

```typescript
if (res.mode === 'balance') {
  if (res.delivery) {
    showResult('success', '支付成功', '余额支付已完成', res.delivery)
  } else {
    showResult('success', '支付成功', '余额支付已完成，请到订单详情查看交付状态')
  }
}
```

### 4.2 线上支付

- **自动轮询**。进入 `online` 步骤后，启动 `startOnlinePolling`，每 3 秒调用 `getPayStatus`。
- **超时**：5 分钟超时自动停止并提示"订单已过期"。
- **状态流转**：`pending` → 继续轮询 → `paid` → 显示"正在发卡" → `issued` → 显示成功

```typescript
// useCheckoutFlow.ts
function startStatusPolling() {
  pollTimer = setInterval(async () => {
    const res = await options.getPayStatus(state.orderId, state.orderToken)
    if (res.status === 'issued' && res.delivery) {
      stopPolling()
      options.showResult('success', '支付成功', '卡密已发放', res.delivery)
    } else if (res.status === 'paid') {
      onlineStatus.value = '支付已确认，正在发卡…'
    }
  }, 3000)
}
```

### 4.3 线下支付

- **用户确认后轮询**。用户输入流水号后4位并点击确认后，调用 `/pay/offline/confirm`，然后启动 `startStatusPolling`。
- **不自动轮询**：如果用户不点击确认，前端不会自动轮询（需管理员后台确认后用户手动刷新订单详情页）。
- **超时**：30 分钟倒计时（基于订单 `expiresAt`）。

```typescript
// useOfflinePayment.ts
async function confirm(orderId: string, orderToken: string) {
  await options.confirmOfflinePay({ orderId, orderToken, payRefLast4: refLast4.value })
  offlineConfirmStatus.value = '已提交确认，等待管理员核对…'
  options.startStatusPolling()  // ← 确认后才开始轮询
}
```

## 五、管理员确认流程

### 5.1 接口

**文件**：`templates/cf-shop/src/routes/admin.ts`

```typescript
adminRoute.post("/orders/:id/mark-paid", async (c) => {
  const id = c.req.param("id");
  const db = getDb(c);
  const dbConfig = await readRuntimeConfig(db);
  const emailEnv = mergeRuntimeConfig(dbConfig, c.env);
  const result = await markPaidAndIssue(db, id, emailEnv);
  if (!result.ok) return fail(c, result.message, result.status);
  await writeAdminAudit(db, {
    action: "mark_paid_and_issue",
    targetType: "order",
    targetId: id,
    ipHash: await getIpHash(c)
  });
  return ok(c, { message: "订单已标记为已支付并完成发卡" });
});
```

### 5.2 适用场景

- **线下支付订单**：用户已确认付款（`/pay/offline/confirm`），管理员核对后点击"确认收款并发卡"。
- **manual 模式订单**：管理员确认发卡（无需用户付款确认）。

### 5.3 前置条件

`markPaidAndIssue` 会检查订单状态：
- `pending` → 原子更新为 `paid`，然后发卡
- `paid` → 直接尝试发卡（恢复路径）
- `issued` → 返回 `alreadyIssued: true`（幂等）
- 其他状态（`expired`、`failed`、`cancelled`）→ 拒绝操作

## 六、状态机与幂等性

### 6.1 订单状态流转

```
pending（待支付）
    ↓ markPaidAndIssue
paid（已支付，待发卡）
    ↓ markPaidAndIssue
issued（已发卡）
```

### 6.2 幂等保证

| 操作 | 幂等机制 |
|------|---------|
| `/pay/unified` | `Idempotency-Key` header → `checkIdempotency` / `saveIdempotentResponse` |
| `/pay/callback/:provider` | 支付平台重试 → `markPaidAndIssue` 内部检查 `issued` 状态直接返回 |
| `/admin/orders/:id/mark-paid` | `markPaidAndIssue` 检查 `issued` 状态直接返回 `alreadyIssued` |
| `/pay/offline/confirm` | 仅更新 `paymentRef`，不改变订单主状态 |

## 七、常见误区澄清

### 误区 1："所有支付方式都是先创建订单，再回调发卡"

❌ **错误**。余额支付和 direct 模式是"创建订单即发卡"，不经过回调。

### 误区 2："线下支付前端会自动轮询直到发卡"

❌ **错误**。线下支付前端在用户点击"确认付款"后才会开始轮询。如果用户不确认，前端不会自动轮询。

### 误区 3："支付回调会先改 paid，再由 markPaidAndIssue 发卡"

⚠️ **部分正确**。回调路由 `/pay/callback/:provider` 会先更新 `paymentRef` + `paidAt`，然后调用 `markPaidAndIssue`。但 `markPaidAndIssue` 内部会再次检查状态，并发场景下能正确处理 `paid` 状态。

### 误区 4："direct 模式不需要管理员确认"

✅ **正确**。direct 模式在 `/orders` 接口中直接发卡，不需要管理员干预。
