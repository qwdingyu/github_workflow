# 支付体系全局整合方案

> 撰写时间：2026 年 5 月 31 日
> 分析对象：cf-core/features/payment/ + cf-shop/src/services/payments/ + cf-shop/src/routes/pay.ts
> 核心问题：同一套支付代码在两个地方各维护一份，如何整合？

---

## 第一部分：现状诊断 — 代码分裂的严重程度

### 1.1 代码位置对照

```
位置 A：packages/cf-core/features/payment/index.ts  (618 行，单体文件)
  ├── CreatePaymentInput / CreatePaymentResult / CallbackResult 等接口
  ├── fetchWithRetry() 工具函数
  ├── RSA2 签名工具（signRSA2 / verifyRSA2）
  ├── AlipayProvider 类 + alipayFactory
  ├── StripeProvider 类 + stripeFactory
  ├── Trc20Provider 类 + trc20Factory
  ├── createProviderRegistry()（基于 ProviderFactory 数组）
  └── 测试：tests/index.test.ts（507 行）

位置 B：templates/cf-shop/src/services/payments/  (7 个文件)
  ├── types.ts              — PaymentProvider 接口（与 A 几乎相同）
  ├── registry.ts           — createProviderRegistry()（基于 Bindings 硬编码）
  ├── alipay-provider.ts    — AlipayProvider 类
  ├── stripe-provider.ts    — StripeProvider 类（305 行，更详细）
  ├── trc20-provider.ts     — Trc20Provider 类
  ├── index.ts              — 统一导出
  └── 依赖：src/lib/alipay-sign.ts（RSA2 签名，独立文件）
```

### 1.2 两套代码的关键差异

| 维度 | cf-core/features/payment | cf-shop/services/payments |
|------|--------------------------|--------------------------|
| **注册机制** | ProviderFactory 数组（灵活，可外部扩展） | Bindings 硬编码（简单，但死板） |
| **优先级** | alipay(100) > stripe(200) > trc20(300) | stripe > alipay > trc20 |
| **Stripe success_url** | `/lookup?session_id={CHECKOUT_SESSION_ID}` | 同左 |
| **fetch 封装** | 内置 fetchWithRetry（10s 超时，2 次重试） | 直接 fetch（Stripe 无重试） |
| **RSA2 签名** | 内置在 index.ts | 独立文件 src/lib/alipay-sign.ts |
| **测试** | ✅ 507 行完整测试 | ❌ 无测试 |
| **实际使用者** | ❌ 无人使用（cf-shop 用的是 B） | ✅ cf-shop 实际运行代码 |
| **代码质量** | 紧凑但 618 行单文件 | 分文件好维护，但 Stripe 305 行太长 |

### 1.3 核心问题：cf-core 的 payment 是"幽灵代码"

```
cf-core/features/payment/index.ts 虽然存在且有测试，
但 cf-shop 实际运行的是 src/services/payments/ 下的副本。

cf-core 的版本：
- 有 ProviderFactory 抽象（更优雅）
- 有 fetchWithRetry 封装（更健壮）
- 有完整测试
- 但——没有任何项目真正 import 它

cf-shop 的版本：
- 是实际运行的代码
- 分文件更清晰
- 但——没有测试、没有 fetch 重试、硬编码 Bindings
```

**这是一个典型的"理想设计 vs 现实代码"分裂。**

## 第二部分：根因分析

### 2.1 为什么会出现分裂？

```
时间线推测：
1. 先在 cf-shop 中写了 payments/（位置 B）— 快速迭代，能跑就行
2. 后来意识到应该放到 cf-core（位置 A）— 重新设计，加了 Factory 模式
3. 但没有把 cf-shop 迁移到 cf-core 版本 — 因为：
   - cf-core 版本用 Record<string, unknown> 作为 env 类型
   - cf-shop 用强类型 Bindings
   - 迁移需要改 cf-shop 的 registry.ts
   - 当时觉得"能跑就行"，没做迁移
```

### 2.2 分裂的代价

| 代价类型 | 具体表现 |
|---------|---------|
| **Bug 修复双倍** | 修一个 Provider bug 要改两个地方 |
| **新功能双倍** | 加微信支付要写两份代码 |
| **测试覆盖不均** | cf-core 有测试但没人跑，cf-shop 没测试但在跑 |
| **认知负担** | 新人不知道该看哪个版本 |
| **优先级矛盾** | cf-core 说 alipay 优先，cf-shop 说 stripe 优先，谁对？ |

## 第三部分：全局整合方案

### 3.1 整合原则

```
原则 1：cf-core 是唯一的支付实现来源
  - 删除 cf-shop/src/services/payments/ 的全部实现代码
  - cf-shop 只保留路由层（pay.ts），从 cf-core 导入支付能力

原则 2：cf-core 吸收 cf-shop 的优点
  - 分文件结构（types、providers 独立文件）
  - 但保持 ProviderFactory 抽象（比硬编码 Bindings 更好）

原则 3：cf-shop 的路由层不变
  - pay.ts 是业务逻辑（订单创建、发卡、余额支付）
  - 它不应该被移到 cf-core（这是业务代码）
  - 它只需要从 cf-core 导入 PaymentProvider 能力

原则 4：优先级由业务项目决定
  - cf-core 不提供默认优先级
  - 每个项目自己决定 factory 顺序
```

### 3.2 目标架构

```
packages/cf-core/features/payment/
├── index.ts              ← 统一导出（薄层，50 行以内）
├── types.ts              ← PaymentProvider 接口定义
├── registry.ts           ← createProviderRegistry + ProviderFactory
├── providers/
│   ├── alipay.ts         ← AlipayProvider + alipayFactory + RSA2 签名
│   ├── stripe.ts         ← StripeProvider + stripeFactory
│   ├── trc20.ts          ← Trc20Provider + trc20Factory
│   └── fetch-utils.ts    ← fetchWithRetry（共享 HTTP 工具）
└── tests/
    └── index.test.ts     ← 完整测试（保留并增强）

templates/cf-shop/src/
├── services/payments/
│   └── registry.ts       ← 仅 10 行：选择 factory 顺序 + 创建 registry
├── routes/pay.ts         ← 不变（业务逻辑层）
└── lib/alipay-sign.ts    ← 删除（已合并到 cf-core）
```

### 3.3 cf-shop 的新用法（整合后）

```typescript
// cf-shop/src/services/payments/registry.ts（整合后，仅 15 行）
import {
  createProviderRegistry,
  stripeFactory,
  alipayFactory,
  trc20Factory,
} from "@usethink/cf-core/features/payment";

// cf-shop 的优先级：stripe > alipay > trc20
export function createPaymentRegistry(env: Record<string, unknown>) {
  return createProviderRegistry(env, [
    stripeFactory,    // 国际用户优先
    alipayFactory,    // 国内用户
    trc20Factory,     // 兜底
  ]);
}

export const VALID_PROVIDER_NAMES = ["stripe", "alipay", "usdt_trc20"] as const;
```

```typescript
// cf-shop/src/routes/pay.ts（整合后，改动极小）
// 之前：
//   import { createProviderRegistry, VALID_PROVIDER_NAMES } from "../services/payments";

//
// 之后：
//   import { createPaymentRegistry, VALID_PROVIDER_NAMES } from "../services/payments/registry";
//   const registry = createPaymentRegistry(c.env);
//

```

重构后：
  packages/cf-core/features/payment/
  ├── index.ts              (≈50 行)  统一导出
  ├── types.ts              (≈100 行) PaymentProvider 接口 + 数据类型

### 4.2 每个文件的责任

| 文件 | 责任 | 依赖 |

### 4.3 代码合并策略

```

  - ProviderFactory 抽象（比硬编码好）
  - fetchWithRetry 封装（加到 Stripe/Alipay 调用中）

Step 3: 放到 cf-core 的分文件结构中

Step 4: cf-shop 删除本地副本，改为从 cf-core 导入

## 第五部分：国际站（devtools-intl）的支付需求分析

### 5.1 国际站需要支付吗？

```
cf-static（国际开发者工具站）：
- 技术栈：Eleventy 纯静态
- 变现方式：Google AdSense（广告）
- 不需要支付系统 ✅

cf-calculators（中国计算器站）：
- 技术栈：Eleventy 纯静态
- 变现方式：微信生态 / 国内广告
- 不需要支付系统 ✅

cf-ai（AI 工具站，待创建）：
- 技术栈：Workers + Astro
- 变现方式：Freemium + Stripe 订阅
- 需要支付系统 ⚠️ 但需求与 cf-shop 完全不同
```

### 5.2 cf-ai 的支付需求 vs cf-shop

| 维度 | cf-shop（卡密电商） | cf-ai（AI 工具 SaaS） |
|------|-------------------|---------------------|
| **商品** | 卡密（一次性发货） | AI API 调用（按 token 计费） |
| **支付频率** | 单次购买 | 月度订阅 + 按量付费 |
| **支付流程** | 下单 → 支付 → 发卡 | 注册 → 订阅 → 持续使用 |
| **退款** | 几乎不退（虚拟商品） | 需要退款（订阅取消） |
| **核心支付** | 支付宝 + Stripe + USDT | Stripe Subscription 为主 |
| **需要 cf-core payment** | ✅ 完整使用 | ⚠️ 只需要 Stripe |

### 5.3 结论：cf-ai 不需要复制支付代码

```
cf-ai 只需要 Stripe Subscription 功能。
cf-core 的 StripeProvider 已经实现了基础支付。
cf-ai 需要的是在 StripeProvider 之上加 Subscription 层：

packages/cf-core/features/payment/providers/stripe.ts
  ├── StripeProvider.createPayment()     ← 已有（单次支付）
  ├── StripeProvider.createSubscription() ← 新增（月度订阅）
  └── StripeProvider.cancelSubscription() ← 新增（取消订阅）

cf-ai 直接从 cf-core 导入，不需要自己写支付代码。
```

## 第七部分：关于国际站项目命名

### 7.1 你的问题：国际站项目名称应该简短

```
当前状态：
- cf-static：保留中文（国内备用）+ 通用开发者工具
- cf-calculators：中国计算器站

国际站选项：
| 名称 | 优点 | 缺点 |
|------|------|------|
| cf-intl | 简短，清楚是国际版 | 太泛，不知道是什么 |
| cf-devtools | 清楚是开发者工具 | 稍长 |
| devtools | 最简短 | 不与 cf- 前缀统一 |
| cf-web | 简短 | 太泛 |
```

### 7.2 我的建议

```
不需要为国际站创建新项目。

原因：
1. cf-static 已经是通用开发者工具站
2. 你说了"保留中文"——说明 cf-static 是"中文为主，英文为辅"

→ 命名为 cf-devtools（清晰、简短、与 cf- 前缀统一）

### 8.2 核心决策

| 决策 | 方案 | 理由 |
