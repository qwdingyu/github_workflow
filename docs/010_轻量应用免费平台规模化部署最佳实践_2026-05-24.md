# 轻量应用免费平台规模化部署最佳实践

日期：2026-05-24

## 结论

你说的工具类、填表类、分享类、邀请类、落地页、数据收集类应用，绝大多数都不需要像 `new-api` 那样跑 Docker 长驻服务。

最佳实践是把应用拆成三层：

```text
展示层：静态页面 / 前端 SPA / 落地页
交互层：少量 API / 表单提交 / 邀请码 / webhook
数据层：D1 / Supabase / Turso / R2 / KV
```

然后用已经跑通的经验放大：

```text
GitHub main
-> Cloudflare Workers Builds / Vercel Git Integration
-> 自定义域名
-> curl 验证
-> docs 记录
```

个人开发者的最优主线：

```text
默认优先 Cloudflare Workers + Workers Static Assets + D1/KV/R2
需要 Postgres/Auth/后台管理时使用 Supabase
需要 Next.js 产品体验时使用 Vercel
需要 SQLite 风格外部 SQL 时使用 Turso/libSQL
需要 Docker/长驻服务时才使用 VPS/容器平台
```

## 和 new-api 的本质区别

`new-api` 重，是因为它需要：

- Docker。
- 长驻 HTTP 服务。
- 持久化 `/data`。
- SQLite/MySQL/PostgreSQL。
- 可选 Redis。
- 管理后台、日志、账号、渠道、计费等复杂状态。

而你说的轻量应用通常只需要：

- 打开页面。
- 填一个表。
- 生成一个邀请码或分享链接。
- 保存一条记录。
- 展示一个结果页。
- 发一封邮件或 webhook。
- 下载一个文件。

这类应用不要按传统后端部署，优先 serverless / edge 化。

## 应用类型与推荐平台

| 应用类型 | 推荐主路径 | 数据层 | 说明 |
| --- | --- | --- | --- |
| 落地页 | Cloudflare Workers Static Assets / Pages | 无 | 最简单，静态即可 |
| 展示型工具 | Cloudflare Workers Static Assets | 可选 KV/D1 | 前端为主，少量配置 |
| 表单收集 | Cloudflare Workers + D1 / Supabase | D1 或 Supabase | 低负载优先 D1，需要后台管理优先 Supabase |
| 邀请码 / 裂变 | Cloudflare Workers + D1 | D1，必要时 Durable Objects | 需要唯一约束、计数、防刷 |
| 分享页 | Cloudflare Workers + KV/D1/R2 | KV/D1/R2 | 短链接用 KV，结构数据用 D1，文件用 R2 |
| 小型 API | Cloudflare Workers / Vercel Functions | D1/Supabase/Turso | 看语言和依赖复杂度 |
| Next.js 产品原型 | Vercel + Supabase | Supabase | Vercel 对 Next.js 体验最好 |
| Python 简单 HTTP API | Vercel Python Functions / Cloudflare Python Workers | Supabase/Turso/API | 依赖少可以 serverless，依赖重用容器 |
| Go 简单 HTTP API | Vercel Go Functions / VPS | Supabase/Turso/API | 轻函数可 Vercel；传统 Go server 用 VPS |
| 文件收集 / 上传 | Cloudflare Workers + R2 | R2 + D1 | R2 存文件，D1 存元数据 |
| 后台定时任务 | Cloudflare Workers Cron Triggers | D1/R2/KV | 适合定时清理、统计、同步 |

## 语言选择边界

### Node.js / TypeScript

最推荐。

适合：

- Cloudflare Workers。
- Vercel Functions。
- Hono / itty-router / Next.js API routes。
- 表单、邀请、分享、短链、webhook。

最佳实践：

```text
新项目优先 TypeScript + Hono + Cloudflare Workers
```

原因：

- Cloudflare Workers 对 JavaScript/TypeScript 是一等支持。
- 生态成熟。
- 部署快。
- 更容易复用我们已跑通的 Workers 工作流。

注意：

- Cloudflare Workers 不是完整 Node.js 服务器。
- 不要依赖本地文件系统。
- 不要默认使用 Express 长驻服务模型。
- Node 原生模块、二进制依赖、长连接后台任务要谨慎。

### Python

可以，但要分清两类。

适合 serverless 的 Python：

- 简单 HTTP handler。
- 表单处理。
- 轻量数据清洗。
- webhook。
- 调用第三方 API。

不适合 serverless 的 Python：

- Flask/Django 全量传统应用。
- 需要大量系统依赖。
- pandas/numpy/scipy 重计算。
- Playwright/浏览器自动化。
- 常驻后台 worker。
- Streamlit/Gradio 这类长驻交互服务。

推荐：

```text
简单 Python API -> Vercel Python Functions
Cloudflare 原生工作流 -> Python Workers 只用于依赖很轻的场景
重 Python 应用 -> VPS/容器平台
```

### Go

Go 也可以，但需要选对形态。

适合：

- 简单 HTTP function。
- 单文件 API。
- 性能敏感但逻辑简单的服务。

不适合：

- 把传统 `net/http` 长驻服务硬塞进 edge/serverless。
- 需要本地持久文件。
- 需要后台 goroutine 长期运行。

推荐：

```text
简单 Go function -> Vercel Go Functions
完整 Go 后端 -> VPS/容器平台
Cloudflare Workers 上 Go -> 只在明确接受 Wasm/运行时约束时使用
```

## 推荐的可复制架构

### 标准模板 A：Cloudflare 小工具模板

适合 80% 的工具类、表单类、分享类、邀请类应用。

```text
src/
  index.html
  assets/
  _headers

worker/
  index.ts

wrangler.jsonc
docs/
```

运行方式：

```text
静态页面 -> Workers Static Assets
API -> 同一个 Worker
数据 -> D1/KV/R2
部署 -> GitHub push -> Workers Builds
域名 -> Workers Custom Domains
```

适合：

- 一个页面 + 一个提交接口。
- 邀请码生成。
- 表单收集。
- 短链接。
- 小型活动页。
- 文件上传到 R2。

优势：

- 成本低。
- 部署快。
- 一个 Cloudflare 项目就够。
- 和 `ai.eforge.xyz` 这次成功经验完全一致。

### 标准模板 B：Vercel 产品原型模板

适合 Next.js 类产品。

```text
Next.js
-> Vercel Hobby
-> Supabase Postgres/Auth
-> Cloudflare DNS
```

适合：

- 登录注册。
- Dashboard。
- 多页面产品。
- 需要预览部署。
- 需要 React/Next.js 生态。

注意：

- 不要把 Vercel 当 Docker 平台。
- 后台任务不要放 Vercel Function 里长跑。
- 低负载可用，商业服务要关注超限和账单。

### 标准模板 C：Supabase 数据后台模板

适合重数据、轻服务。

```text
Cloudflare/Vercel 前端
-> Supabase Auth
-> Supabase Postgres
-> Supabase Storage
```

适合：

- 表单数据管理。
- 用户账号。
- 简单 CRM。
- 活动报名。
- 邀请关系表。

优势：

- 有现成数据库后台。
- SQL 强。
- Auth 省事。
- 对个人开发者节省大量后端时间。

注意：

- Free 项目有容量和活跃限制。
- 不要存大量日志。
- 数据增长后要及时清理或升级。

### 标准模板 D：Turso/libSQL 小库模板

适合很多小应用独立数据库。

```text
Cloudflare Workers / Vercel Functions
-> Turso/libSQL
```

适合：

- SQLite 思维。
- 多个小应用。
- 低成本 CRUD。
- 配置、表单、轻量关系数据。

注意：

- 不是 Postgres。
- 不要用于需要 PostgreSQL 特性的业务。
- ORM 和 driver 必须确认支持 libSQL。

## 数据层选择

### D1

优先用于 Cloudflare Workers 原生小应用。

适合：

- 表单记录。
- 邀请码。
- 分享记录。
- 短链映射。
- 简单订单/线索。

不适合：

- 重分析。
- 高并发写入。
- 复杂事务。
- 跨平台直接连接。

### KV

适合：

- 配置。
- 短链跳转。
- 低频更新、高频读取。
- token 黑名单。
- feature flag。

不适合：

- 需要强一致的计数。
- 邀请码库存扣减。
- 复杂查询。

### R2

适合：

- 文件上传。
- 图片。
- 导出文件。
- SQLite 备份。
- 用户附件。

不适合：

- 在线查询数据库。
- 频繁小事务。

### Supabase Postgres

适合：

- 结构化业务数据。
- 需要 SQL 管理后台。
- 需要 Auth。
- 需要关系约束。

不适合：

- 大量日志堆积。
- 无限制公开写入。
- 高频爬虫写入。

### Turso/libSQL

适合：

- SQLite 兼容小应用。
- 多项目小库。
- 低成本结构化数据。

不适合：

- Postgres/MySQL 专属项目。
- 未确认 driver 支持的老项目。

## 具体应用怎么选

### 填表类

推荐：

```text
Cloudflare Worker + D1
```

如果需要后台查看和导出：

```text
Cloudflare Worker + Supabase
```

表结构至少包括：

```text
id
created_at
source
name / contact
payload_json
ip_hash
user_agent_hash
status
```

必须做：

- Turnstile 或简单验证码。
- IP 频率限制。
- honeypot 字段。
- 提交后跳转感谢页。
- 数据导出或备份。

### 分享类

推荐：

```text
Cloudflare Worker + KV/D1
```

选择：

- 只做短链接：KV。
- 要统计和查询：D1。
- 要存图片/文件：R2。

必须做：

- slug 唯一性。
- 过期时间。
- 违规内容处理。
- 基础访问统计。

### 邀请类

推荐：

```text
Cloudflare Worker + D1
```

表结构：

```text
users
invite_codes
invite_events
reward_events
```

注意：

- 邀请码唯一约束。
- 防重复领取。
- 防刷。
- 奖励发放必须幂等。
- 低负载 D1 足够；高并发计数再考虑 Durable Objects。

### 落地页

推荐：

```text
Cloudflare Workers Static Assets / Pages
```

如果有收集表单：

```text
Cloudflare Worker API + D1/Supabase
```

必须做：

- 页面加载快。
- CTA 明确。
- 表单字段少。
- 记录来源参数。
- 不依赖第三方慢脚本。

### 简单管理后台

推荐：

```text
Supabase Auth + Supabase Postgres + 前端部署到 Cloudflare/Vercel
```

理由：

- 自己写 Auth 很浪费时间。
- Supabase 提供现成后台和 SQL。
- 对个人开发者节省精力。

## 统一部署生产线

目标是把成功经验放大成模板，而不是每个项目重新摸索。

### 每个应用的标准目录

```text
app-name/
  src/
  worker/
  wrangler.jsonc
  README.md
```

外层统一文档：

```text
github_workflow/docs/
```

每个应用的文档归档到外层 `docs/`，文件名保持：

```text
序号_中文文件名_日期.md
```

### 标准上线步骤

```text
1. 从模板复制新项目
2. 修改 wrangler.jsonc 的 name
3. 绑定 GitHub 仓库
4. 配置 Workers Builds
5. 绑定自定义子域名
6. 推送 main
7. curl 验证正式域名和 workers.dev
8. docs 记录部署结果
```

### 标准验收命令

```bash
rtk git status --short
rtk git diff --check
rtk proxy npx wrangler deploy --dry-run
rtk git push origin main
rtk curl -I https://<正式域名>/
rtk curl -sS https://<正式域名>/ | rtk rg "<smoke-marker>"
rtk curl -I https://<workers-dev回退域名>/
rtk curl -sS https://<workers-dev回退域名>/ | rtk rg "<smoke-marker>"
```

## 多应用域名规划

建议不要所有工具都堆在一个域名路径下。

推荐：

```text
ai.eforge.xyz        AI 工具主入口
forms.eforge.xyz     表单/收集类
go.eforge.xyz        短链/跳转类
invite.eforge.xyz    邀请裂变类
tools.eforge.xyz     工具集合
demo.eforge.xyz      Demo/落地页
```

规则：

- 每个正式应用一个子域名。
- workers.dev 保留回退。
- 不使用根域名作为试验入口。
- 不同应用独立 Worker，避免一个项目出问题影响全部。

## 多应用复用策略

### 不建议一开始做大平台

不要上来做：

```text
统一 SaaS 平台
统一用户中心
统一插件系统
统一管理后台
```

这会拖慢上线。

### 推荐做小模板

先做 3 个模板：

```text
landing-template     落地页模板
form-template        表单收集模板
invite-template      邀请裂变模板
```

每个模板只保留：

- 最小页面。
- 最小 API。
- 最小数据表。
- 最小验证。
- 最小部署文档。

后续项目复制模板，而不是复制一堆历史代码。

## AI 接管部署的边界

AI 可以自动做：

- 创建新仓库。
- 复制模板。
- 修改 `wrangler.jsonc`。
- 写 `src/` 和 `worker/`。
- 创建 D1 schema。
- 写文档。
- 中文 commit。
- push GitHub。
- 调用 Cloudflare API 绑定 Custom Domain。
- curl 验证。

AI 不应无确认自动做：

- 删除生产 Worker。
- 删除数据库。
- 删除域名记录。
- 改根域名。
- 打开公开注册。
- 暴露管理后台。
- 保存高权限 token。

## 成本控制策略

1. 默认 Cloudflare Workers。
2. 能 D1 就不先上 Supabase。
3. 需要 Auth/后台才上 Supabase。
4. 能 KV 就不用数据库。
5. 文件进 R2，不进数据库。
6. 每个应用限制提交频率。
7. 表单必须防刷。
8. 日志只保留必要字段。
9. 大文件和备份设置生命周期。
10. 所有 token 分层，不长期使用全权限 token。
11. 不为每个小工具单独买服务器。
12. Docker 服务集中放一台低价主机，轻量应用尽量 serverless。

## 技术选型决策树

### 第一步：是否需要长驻进程？

如果需要：

```text
VPS / 容器平台
```

如果不需要，继续。

### 第二步：是否主要是静态页面？

如果是：

```text
Cloudflare Workers Static Assets / Pages
```

如果需要少量 API：

```text
Cloudflare Workers
```

### 第三步：是否需要用户登录？

如果需要：

```text
Supabase Auth + Postgres
```

如果不需要，继续。

### 第四步：是否只需要收几条表单数据？

如果是：

```text
Cloudflare Workers + D1
```

### 第五步：是否需要文件？

如果需要：

```text
Cloudflare R2
```

### 第六步：是否是 Next.js 产品原型？

如果是：

```text
Vercel + Supabase
```

否则：

```text
Cloudflare Workers 优先
```

## 最佳实践总路线

对你现在的情况，最优路线是：

```text
把 Cloudflare Workers 项目模板化
把 docs 迁到外层统一管理
每个小应用一个独立 Worker + 独立子域名
数据默认 D1/KV/R2
需要后台和登录再接 Supabase
需要 SQLite 外部库再接 Turso
需要 Docker 才上 VPS
```

这条路线能最大化复用当前成功经验：

```text
GitHub push
-> Cloudflare 自动部署
-> Custom Domain
-> curl 验证
-> docs 记录
```

并且不会把精力浪费在大而全平台上。
