# cf-shop 微电商闭环审查报告

审查日期：2026-06-23

审查范围：`packages/cf-core`、`templates/cf-shop`，重点覆盖个人创业者经营虚拟资料、卡密、折扣码、充值码、线上/线下支付、库存发卡、后台管理、前后端契约和 Cloudflare Workers + libSQL Free 约束。

## 一、结论摘要

当前系统已经具备微电商的核心雏形：商品、卡密库存、下单、支付、发卡、订单查询、后台导入、后台确认付款、邮件通知、限流、人机验证、幂等、审计日志均有实现。

但按“个人创业者可直接上线收款并稳定交付”的行业通用要求看，当前版本不建议直接上线。主要原因不是功能少，而是闭环中存在几处上线阻断和高风险断层：

1. 数据库迁移 SQL 与运行时代码 schema 严重不一致，新库部署后大概率运行失败。
2. 支付回调与 `markPaidAndIssue` 状态机存在断层，在线支付成功后可能只停在 `paid`，不发卡。
3. 前端订单查询、充值码、余额支付与后端返回契约不一致，用户侧闭环不完整。
4. 余额支付扣款与发卡不是事务闭环，失败后需要人工补偿，容易产生客诉。
5. 卡密、订单、优惠券缺少必要唯一约束和一致性约束，长期运行后会积累脏数据。
6. Cloudflare/libSQL Free 场景下的外部调度、部署迁移、支付回调、邮件发送依赖较多，缺少“一键上线前检查”闭环。

综合判断：适合作为 MVP 模板继续打磨；不适合在当前状态下承载真实付费流量。建议先修复 P0/P1 后再小规模灰度。

代码中已经覆盖虚拟商品微电商常见对象：

- 商品：`products`
- 卡密：`cards`
- 卡密批次：`cardBatches`
- 订单：`orders`
- 订单事件：`orderEvents`
- 优惠码：`coupons`

表定义见 `templates/cf-shop/src/db/schema.ts:22` 至 `templates/cf-shop/src/db/schema.ts:282`。

### 2. 库存发卡方向正确

卡密发放和软锁使用单条 `UPDATE ... RETURNING`，避免“先查库存再更新”的 TOCTOU 竞争：

这对卡密类商品非常关键。只要底层 SQL 与表结构匹配，并且状态机没有绕开这两条路径，就能降低超卖概率。

### 3. 下单入口具备基础防护

下单和支付入口有 Zod 校验、限流、Turnstile 和幂等键：

- `/orders`：`templates/cf-shop/src/routes/orders.ts:42`

这符合轻量发卡站的最低安全要求。

### 4. 后台管理能力覆盖基本运营

后台已覆盖商品、卡密导入、订单、卡密状态、优惠码、充值码、系统配置、日志、库存预警和清理：

- 卡密导入路由：`templates/cf-shop/src/routes/admin.ts:291`

- 充值码生成：`templates/cf-shop/src/routes/admin.ts:897`
- 清理过期订单：`templates/cf-shop/src/routes/admin.ts:859`

对个人创业者而言，这些功能方向是正确的。

## 三、上线阻断问题（P0）

### P0-1：迁移 SQL 与运行时 schema 严重不一致

运行时代码使用的字段包括：

- `products.title`
- `products.sales_copy`
- `products.cover_url`
- `products.active`
- `cards.account_label`
- `cards.delivery_secret`
- `cards.delivery_note`
- `cards.locked_order_id`
- `cards.lock_expires_at`
- `cards.issued_order_id`
- `orders.buyer_contact`
- `orders.payment_provider`
- `orders.payment_ref`
- `orders.order_token_hash`
- `orders.issued_card_id`
- `orders.campaign_code`
- `orders.referral_code`
- `orders.ip_hash`
- `orders.user_agent`

运行时 schema 见 `templates/cf-shop/src/db/schema.ts:22` 至 `templates/cf-shop/src/db/schema.ts:95`。

但初始化迁移 `templates/cf-shop/migrations/0001_init.sql` 仍是旧结构，例如：

- `products.name`、`enabled`、`image_url`：`templates/cf-shop/migrations/0001_init.sql:60`
- `cards.card_data`、`locked_by_order_id`：`templates/cf-shop/migrations/0001_init.sql:86`
- `orders.quantity`、`paid_cents`、`buyer_ip_hash`、`payment_trade_no`：`templates/cf-shop/migrations/0001_init.sql:99`

影响：

- 新建 Turso/libSQL 数据库后，Worker 查询 `products.title`、`cards.delivery_secret` 等字段会直接报错。
- 卡密导入会尝试写入不存在的 `account_label`、`delivery_secret` 字段。
- 订单创建会尝试写入不存在的 `buyer_contact`、`order_token_hash` 字段。
- 线上支付回调金额校验、订单查询、发卡均可能失效。

结论：这是当前最大上线阻断。必须先统一迁移与 Drizzle schema。

建议：

1. 以 `src/db/schema.ts` 为准重写 `migrations/0001_init.sql`。
2. 为已有旧库提供 `0003_align_runtime_schema.sql`，补齐新字段并迁移旧字段。
3. 每次 CI 加一条“空库执行迁移 + 启动 smoke-readonly + smoke-write”的验证。
4. 禁止手写 schema 与迁移长期分叉；至少增加脚本比对表列名。

### P0-2：在线支付回调可能无法完成发卡

`/pay/callback/:provider` 中先把订单从 `pending` 更新为 `paid`：

`templates/cf-shop/src/routes/pay.ts:522`

随后调用：

`templates/cf-shop/src/routes/pay.ts:540`

但 `markPaidAndIssue` 的主路径只接受 `pending -> paid` 的锁定更新：

`templates/cf-shop/src/services/order-service.ts:455`

如果回调已经把订单改成 `paid`，`markPaidAndIssue` 会进入恢复分支。恢复分支会释放该订单锁定的卡密，再调用 `issueAvailableCard`：

`templates/cf-shop/src/services/order-service.ts:493`

风险点：

- 回调路由已经完成 `pending -> paid`，`markPaidAndIssue` 读到 `paid` 后不走正常锁单发卡路径。
- `releaseLockedCardByOrder` 会释放 locked 卡密，随后再从 available 中发卡。
- 并发下虽然仍可能发出卡，但状态机语义混乱，且存在中途失败停在 `paid` 的风险。
- 这会造成用户已支付但页面一直不显示卡密，需要人工介入。

建议：

1. 支付回调不要提前把订单改成 `paid`，只验签、验金额、查订单，然后把“设置 paymentRef/paidAt + 发卡”交给一个原子服务完成。
2. 或者重构 `markPaidAndIssue`，让它显式支持 `pending` 和 `paid` 两种入口，并且不要在正常 paid 恢复路径先释放该订单已锁定卡密。
3. 增加测试：在线支付回调成功后，断言订单状态为 `issued` 且 `issuedCardId` 非空。
4. 增加测试：同一回调重复请求 2 次，只发一张卡。

### P0-3：迁移/依赖验证未能通过当前环境

本次执行：

- `node scripts/validate-architecture.mjs`：通过。
- `pnpm test`、`pnpm type-check`、`pnpm --dir frontend build`：未能跑到业务编译阶段。

失败过程：

1. 第一次非 CI 执行被 pnpm 阻断：`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`。
2. 设置 `CI=true` 后，pnpm 尝试访问 npm registry，受网络限制出现大量 `ENOTFOUND`。
3. 授权网络后，pnpm 又被 `ERR_PNPM_IGNORED_BUILDS` 阻断，要求 `pnpm approve-builds` 允许 `esbuild`、`sharp`、`workerd` 等构建脚本。

影响：

- 当前无法证明后端类型检查、Vitest、前端构建通过。
- 刚才的 pnpm 尝试还重建过 `templates/cf-shop/node_modules`，说明本地依赖状态可能已被扰动。

建议：

1. 在仓库中固化 pnpm 构建脚本审批策略，避免 CI/代理每次被 `approve-builds` 阻断。
2. 单独建立 `verify:shop` 脚本，串联 `db:migrate`、后端 `type-check`、后端 `test`、前端 `build`。
3. 文档和 CI 中写清楚首次安装必须执行的 pnpm 11 安全审批步骤。

## 四、高风险问题（P1）

### P1-1：前端订单查询与后端返回结构不一致

前端 `lookupOrders` 固定期望：

`templates/cf-shop/frontend/src/api/index.ts:112`

即后端返回 `{ orders: Order[] }`。

但后端 `/orders/lookup` 在 token、订单号、折扣码查询时返回：

`templates/cf-shop/src/routes/orders.ts:121`

即 `{ order }`，只有邮箱查询才返回 `{ orders }`：

`templates/cf-shop/src/routes/orders.ts:96`

影响：

- 用户输入订单 Token 后，前端会读取 `d.orders`，结果是 `undefined`。
- `LookupView` 里直接使用 `orders.value.length`：`templates/cf-shop/frontend/src/views/LookupView.vue:96`，可能运行时报错或显示异常。
- 订单找回闭环不稳定。

建议：

1. 后端统一返回 `{ orders: [...] }`。
2. 或前端根据 `{ order }` / `{ orders }` 做兼容。
3. 订单号和邮箱查询需要 Turnstile，前端目前没有传 `turnstileToken`，这也需要同步。

### P1-2：订单金额字段前后端口径不一致

后端公开订单返回 `amountCents`：

`templates/cf-shop/src/services/order-service.ts:102`

前端展示订单列表时使用 `order.priceCents`：

`templates/cf-shop/frontend/src/views/LookupView.vue:42`

类型中同时存在 `priceCents` 与 `amountCents`：

`templates/cf-shop/frontend/src/types/index.ts:17`

影响：

- 查询结果金额可能显示为 `NaN` 或空。
- 用户无法核对付款金额，线下支付场景尤其危险。

建议：前端统一使用 `amountCents`，类型中删除或弃用 `priceCents`。

### P1-3：充值码和余额支付后端已做，前端没有闭环

后端已实现充值码：

- 兑换：`templates/cf-shop/src/routes/vouchers.ts:52`
- 查询余额：`templates/cf-shop/src/routes/vouchers.ts:94`
- 余额支付：`templates/cf-shop/src/routes/pay.ts:261`

但前端 API 没有 `redeemVoucher`、`fetchBalance`，`unifiedPay` payload 类型也没有 `balancePayment`：

`templates/cf-shop/frontend/src/api/index.ts:60`

前端 `/redeem` 页面仍是“折扣码直接发卡”：

`templates/cf-shop/frontend/src/views/RedeemView.vue:4`

影响：

- 产品文档中的“充值码 -> 用户余额 -> 余额支付”对用户不可见。
- 用户只能用折扣码兑换卡密，不能使用充值码储值消费。
- 个人创业者常用的“站外收款后发充值码”模式未闭环。

建议：

1. 前端新增“充值码兑换”页，调用 `/api/vouchers/redeem`。
2. 支付弹窗新增余额查询和余额支付选项。
3. `unifiedPay` 类型加 `balancePayment?: boolean`。
4. 后台充值码生成后提供 CSV 导出和复制交付。

### P1-4：余额扣款与发卡不是事务闭环

余额支付流程：

1. 创建订单并锁卡。
2. 扣减余额：`templates/cf-shop/src/routes/pay.ts:187`
3. 调用 `markPaidAndIssue` 发卡：`templates/cf-shop/src/routes/pay.ts:193`

代码注释明确写了发卡失败时余额不回退：

`templates/cf-shop/src/routes/pay.ts:196`

影响：

- 用户余额已扣，但卡密未发。
- 个人创业者需要手工补偿，低频可以接受，但不能作为默认可靠路径。
- 如果是库存不足、DB 瞬断、支付状态机异常，会放大客诉。

建议：

1. libSQL 支持事务时，使用事务包住“扣余额 + 标记支付 + 发卡 + 更新订单”。
2. 如果不做事务，至少增加 `balance_transactions` 流水表，记录扣款、失败、补偿。
3. 失败时自动创建后台待处理工单，而不是只 `console.error`。
4. 用户侧返回“处理中”，不要返回“余额已扣减请联系管理员”作为常态设计。

### P1-5：订单取消释放卡密逻辑有缺口

`cancelOrder` 查询订单只拿 `issuedCardId`：

`templates/cf-shop/src/services/admin-service.ts:1111`

但 manual/offline 下单时只是将卡密 `locked_order_id = orderId`，订单 `issuedCardId` 仍为空。取消逻辑只有 `order.issuedCardId` 存在才释放：

`templates/cf-shop/src/services/admin-service.ts:1132`

影响：

- 管理员取消 pending 订单后，对应 locked 卡密可能不释放。
- 库存会被锁住直到清理任务兜底释放，造成可售库存被占用。

建议：取消订单直接复用 `releaseLockedCardByOrder(db, id)`，不要依赖 `issuedCardId`。

### P1-6：软锁订单会被恶意耗尽库存

`/pay/unified` 每 IP 每分钟 8 次：

`templates/cf-shop/src/routes/pay.ts:210`

每次下单会锁定一张卡 30 分钟：

`templates/cf-shop/src/routes/pay.ts:253`

影响：

- 小库存商品可以被少量 IP/代理快速锁空。
- 即使有 Turnstile，真实用户或低成本打码也可能消耗库存窗口。

建议：

1. 对同一邮箱、同一 IP、同一商品增加“未过期 pending 订单数量上限”。
2. 对低库存商品缩短锁定时间，例如 5-10 分钟。
3. 对线下支付单独降低限额；当前 `/pay/offline` 是 5 次，但 `/pay/unified` 线上失败降级线下仍是 8 次。
4. 后台展示“锁定库存”和“可售库存”，不要只显示 available。

## 五、中风险问题（P2）

### P2-1：缺少关键唯一约束和索引

运行时 schema 只有 primary key，没有在 Drizzle schema 中表达这些业务约束：

- `products.slug` 应唯一。
- `orders.orderNo` 应唯一。
- `cards` 应至少对同一商品同一 `deliverySecret` 或导入批次内重复做去重。
- `coupons.code` 已是 primary key，方向正确。

迁移旧版曾给 `orders.order_no`、`products.slug` 做唯一约束，但因为迁移与运行时已经分叉，不能依赖。

影响：

- 订单号重复会导致回调查错单。
- 商品 slug 重复会导致用户访问商品详情不确定。
- 重复导入同一卡密会造成两个买家拿到同一虚拟资料。

建议：

1. Drizzle schema 与迁移中同时声明唯一约束。
2. 导入卡密时检查同商品重复 `accountLabel + deliverySecret`。
3. 订单号生成失败时捕获唯一冲突并重试。

### P2-2：折扣码“直接兑换发卡”和“下单优惠”概念混用

系统同时存在：

- `/redeem`：折扣码直接发卡。
- `/coupons/quote`：折扣码下单抵扣。
- `/vouchers/redeem`：充值码兑换余额。

这三个概念用户很容易混淆。前端 `/redeem` 文案是“兑换折扣码”，而新增充值码后，这个入口更容易误导。

建议：

1. 将“折扣码”定义为下单减免，不直接发卡。
2. 将“兑换码/提货码”定义为可直接兑换商品。
3. 将“充值码”定义为兑余额。
4. schema 层拆出 `redemption_codes`，不要复用 `coupons` 承载直接发卡。

### P2-3：免单和 direct 模式需要更强约束

`createOrder` 中 direct 模式会创建即发卡：

`templates/cf-shop/src/services/order-service.ts:288`

注释称 direct 只用于免单/演示/低风险商品：

`templates/cf-shop/src/services/order-service.ts:292`

但代码没有强制 `payableCents === 0`。如果后台误把付费商品设置成 direct，用户可以通过 `/orders` 直接拿卡。

建议：

1. direct 模式只允许 `quote.payableCents === 0`。
2. 付费商品必须走 `/pay/unified`。
3. 后台创建商品时对 direct 模式显示高风险提示。

### P2-4：支付金额、订单金额、折扣金额语义不统一

`createOrder` manual 分支插入 `amountCents: product.priceCents`，但返回 `amountCents: quote.payableCents`：

`templates/cf-shop/src/services/order-service.ts:229`

`/pay/unified` 插入 `amountCents: payableCents`：

`templates/cf-shop/src/routes/pay.ts:67`

影响：

- 不同下单入口的 `orders.amount_cents` 语义不同：有时是原价，有时是应付价。
- 支付回调金额校验依赖 `orders.amountCents`，必须统一为“实付/应付金额”。

建议：

1. `orders.amountCents` 固定表示应付金额。
2. 增加 `originalAmountCents` 或 `productPriceCents` 表示下单时原价快照。
3. 所有响应字段统一使用 `payableCents` 或 `amountCents`，不要混用。

### P2-5：日志和报错可能暴露敏感信息

全局错误处理返回 `{ error: error.message }`：

`templates/cf-shop/src/index.ts:58`

影响：

- 生产环境可能把数据库字段名、第三方接口报错、内部异常暴露给用户。

建议：

1. 生产环境统一返回通用错误码。
2. 详细错误只进入结构化日志。
3. 日志中避免输出完整卡密、完整邮箱、完整支付流水。

## 六、前后端一致性审查

### 已一致

- 商品列表：后端 `/api/products` 返回 `products`，前端 `fetchProducts` 读取 `products`。
- 统一支付：前端调用 `/api/pay/unified`，后端返回 `mode/orderId/orderToken/amountCents/currency`。
- 支付轮询：前端调用 `/api/pay/status/:orderId?token=...`，后端要求 token。
- 线下支付确认：前端提交 `orderId/orderToken/payRefLast4`，后端校验这三个字段。

### 不一致

1. 订单查询返回结构不一致：`order` vs `orders`。
2. 订单金额字段不一致：`priceCents` vs `amountCents`。
3. 订单详情路由可能不一致：前端 `goToOrder(order.id)` 走命名路由 `order`，支付成功链接使用 query `{ orderId, token }`，需要确认 router 是否同时支持。
4. 充值码和余额支付前端缺失。
5. 邮箱/订单号查询后端要求 Turnstile，前端没有 Turnstile 参数。

## 七、超卖、超买、竞争、空单专项判断

### 超卖

低概率，但不是零。

已降低风险的点：

- 发卡和锁卡使用 `UPDATE ... RETURNING`，比先查再改安全。
- 下单时会软锁卡密。
- 过期订单会释放锁。

仍有风险的点：

- 支付回调状态机混乱，可能出现 paid 不发卡或恢复路径重复操作。
- 迁移不一致会让锁卡字段不存在，直接破坏库存保护。
- 取消订单释放逻辑不完整。

### 超买

存在。

优惠码报价与消费分离，`consumeCoupon` 有条件 UPDATE，能防止超用；但下单时多个用户看到同一个优惠价，最终付款确认时才发现优惠码无法消耗。当前 `markPaidAndIssue` 中优惠码消耗失败只记警告，不回滚订单：

`templates/cf-shop/src/services/order-service.ts:515`

影响：用户可能按优惠价付款成功，最终订单已发卡，但优惠码计数没扣上或已被他人占用。

建议：支付前锁定优惠资格，或支付成功后 coupon 消耗失败时进入人工核对，不应静默发卡。

### 竞争

主要竞争点：

- 支付回调与管理员确认同时触发。
- 用户重复点击下单。
- 同一充值码并发兑换。
- 同一余额并发支付。
- 同一折扣码并发消费。

已有原子保护：

- 充值码 `status='active'` 条件 UPDATE。
- 余额 `balance_cents >= amount` 条件 UPDATE。
- 优惠码 `usedCount < maxUses` 条件 UPDATE。
- 卡密发放 `UPDATE ... RETURNING`。

不足：

- 没有事务统一多个原子步骤。
- 支付回调和发卡状态机边界不清。
- 幂等键是可选 header；前端没有显式传 `Idempotency-Key`。

### 空单

存在几类空单：

1. 支付创建失败后降级线下，会释放旧订单锁并创建新线下订单；旧订单如果已经插入但支付创建失败，代码没有删除旧订单，只释放卡锁。
2. 余额支付扣款成功但发卡失败，会留下需要人工处理的异常订单。
3. direct 模式如果订单写入失败会释放卡密，但如果释放失败会有库存脏状态。

建议：增加异常订单状态和后台“待处理异常”队列，例如 `payment_failed`、`issue_failed`、`refund_required`。

## 八、产品经理视角：是否适合个人创业者

### 适合的场景

- 小流量虚拟资料售卖。
- 卡密类一次性交付。
- 站外收款 + 手动确认。
- 有少量用户咨询能力的个人卖家。
- 可接受手工补偿和人工处理异常订单的早期 MVP。

### 暂不适合的场景

- 高频秒杀或大库存并发售卖。
- 对自动发卡成功率要求很高的付费广告投放。
- 充值余额规模较大、需要严格账务审计的业务。
- 多管理员、多角色权限、多商户场景。
- 需要完整退款、发票、客服工单、风控仲裁的业务。

## 十二、最终建议

该项目方向正确，功能覆盖面也足够轻量微电商 MVP，但当前最大问题是“实现很多，闭环没有被同一个验收标准拉齐”。个人创业者真正需要的不是更多支付方式，而是每一笔订单在异常情况下都有确定归宿。

建议把近期目标从“增加功能”调整为“收敛交易闭环”：

1. 数据库迁移可信。
2. 支付成功必发卡或进入明确异常队列。
3. 用户能自助找回卡密。
4. 库存不会被锁死。
5. 余额和充值码有账务流水。
6. 前端展示与后端契约一致。

完成这些后，再考虑更多支付渠道、营销、推荐、Telegram Bot 等扩展。
