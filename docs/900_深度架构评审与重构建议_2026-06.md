## 二、与行业最佳实践对标

### 2.1 Cloudflare Workers 官方推荐模式

**官方推荐：**
- Workers + Hono + D1/Turso + R2 + KV + Queues
- Services 模式（跨 Worker 调用）
- Asset Management（前端打包到 Workers）

**当前实现：**
```
cf-core (Hono + Turso/Drizzle) → 模板项目 → 部署
```

**对标差距：** ✅ 高度吻合。Hono 是 Cloudflare 官方推荐的 Workers 框架，Drizzle 是 libSQL 层的最佳 ORM（比 raw SQL 类型安全，比 Prisma 轻量）。

**建议改进：** 模板支持 `create-project.mjs` 脚手架，已开发现有基于 `cp -r` + 变量替换的方式，可升级为更正式的 CLI。

### 2.2 SaaS 多租户工厂模式

**行业最佳实践：** 3 层分离：
```
平台层 (可复用的运行时) → 产品层 (业务逻辑) → 实例层 (客户配置)
```

**当前架构：**
```
Layer 1: @eforge/cf-core (基础设施)
Layer 2: templates/cf-shop / cf-tools / cf-api (产品模板 -- 设计中有但仅实现 cf-shop)
Layer 3: 业务插件 (6 个 feature 目录 -- 存在但不统一)
```

**对标差距：** 2→3 层过渡不完整。Feature 目录缺乏正式的独立发布机制，plugin 接口未标准化。

### 2.3 微内核 (Microkernel) 架构

**行业标准：** 核心系统 + 插件系统，插件通过稳定接口热插拔。

**当前实现：** `cf-core` 作为基础设施库提供函数/类，Feature 在 `features/` 目录下独立模块。

**对标差距：** 
- 无正式的 Plugin 生命周期接口（init/start/stop/health）
- Feature 模块仍然硬编码在 `package.json exports` 中
- 没有 Feature 的动态发现/注册机制

## 三、深度发现的 12 个重构机会

### 🔴 P0 — 必须修复

#### 1. DbRateLimiter 竞态条件 (idempotency.ts 同理)

**现状：** `DbRateLimiter.check()` 在 INSERT 后发现 `count > limit` 返回 429，但此时记录已经插入。恶意请求可以通过并发 INSERT 使 count 远大于 limit。

**最佳实践：** 限流应该使用 `ON CONFLICT DO NOTHING` 模式，或者在 `DO UPDATE SET` 中嵌入条件检查（`SET requestCount = requestCount + 1 WHERE requestCount < limit`）。

**修复方案：**
```typescript
// 使用 WHERE request_count < limit 条件防止超额
.onConflictDoUpdate({
  target: [...],
  set: { requestCount: sql`request_count + 1` },
  // 需要 Drizzle 支持 setWhere，否则回退到 returning 后二次检查
})
```

**影响范围：** 高频并发下单场景下可能导致限流失效。

#### 2. Payment 模块缺少重试与超时

**现状：** AlipayProvider.queryStatus 直接 `fetch()` 无超时。StripeProvider 同理。

```typescript
const resp = await fetch("https://openapi.alipay.com/gateway.do", {
  method: "POST",
  body: new URLSearchParams(params).toString(),
  // ❌ 无 AbortController，Workers 默认 30 秒超时
  // ❌ 无重试
});
```

**最佳实践：** 所有第三方 API 调用必须有：
- `AbortController` 设置合理超时（5-10s）
- 指数退避重试（最少 2 次）
- 错误分类（区分可重试/不可重试）

**影响范围：** 支付回调/查询可能因网络波动失败，造成订单状态不一致。

### 🟠 P1 — 应该修复

#### 3. bootstrap 缺少请求级超时中间件

**现状：** bootstrap.ts 中只有请求体限制，没有请求总超时中间件。一个慢查询或挂起的 fetch 请求会耗尽 Worker CPU 时间。

**最佳实践：** 所有 Workers 应用应该实现请求级超时（建议 10-25s，留余量给 CF 默认 30s）：

```typescript
api.use("*", async (c, next) => {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), 25000);
  try {
    c.set("signal", controller.signal);
    await next();
  } finally {
    clearTimeout(timeout);
  }
});
```

#### 4. 全局错误处理未告警

**现状：** `onError` 中只 `console.error` 了错误，没有发送告警。

**最佳实践：** 生产环境错误处理链应该是：
```
错误捕获 → 结构化日志 → 发送告警（Email/Webhook/Slack） → 返回 HTTP 错误
```

**影响范围：** 生产错误无人知晓，用户报告才发现。

#### 5. CSP 策略过于宽松

**现状：** 当前 CSP 包含 `'unsafe-inline'` 和可选的 `'unsafe-eval'`。

```csp
script-src 'self' 'unsafe-inline' https://unpkg.com ... ['unsafe-eval']
```

**最佳实践：** 
- 管理后台使用 `'unsafe-eval'` 是必要的（Vue UMD），但前端用户页面可以通过 Nonce/Hash 消除 `'unsafe-inline'`
- 限制 `frame-src` 更严格
- 使用 `strict-dynamic`（现代浏览器 CSP 3 特性）

**影响范围：** 如果某个 unpkg.com 包被投毒，所有站点暴露。

#### 6. 支付回调缺少幂等性保护

**现状：** `verifyCallback` 只验证签名，返回 `shouldProceed`，但调用方自行决定如何幂等。没有自动去重能力。

**最佳实践：** 支付回调天然应该幂等——相同的回调通知应该只处理一次：

```typescript
// 在回调处理入口
const { shouldProceed } = await checkIdempotency(db, tradeNo, "payment.callback");
if (!shouldProceed) return ok(c, { status: "already_processed" });
```

**影响范围：** 支付宝/Stripe 可能重复发送回调通知（特别是网络超时重试时），导致同一个订单多次发货。

### 🟡 P2 — 值得改进

#### 7. Test Coverage 有缺口

**现状：**
- cf-core 核心模块测试覆盖率高 ✅
- features/ 各模块有基础测试 ✅
- **缺少：** `SystemConfig` 类测试、`bootstrap.ts` 完整集成测试、E2E 支付测试

**建议：** 集成测试应覆盖：
- bootstrap + schema 初始化 → 业务 CRUD，验证完整请求生命周期
- Feature 模块的集成测试（payment registry + provider）

#### 8. Feature 模块接口风格不统一

**现状：** 六大 Feature 模块有三种不同的初始化模式：

| Feature | 模式 | 构造函数接收 |
|---------|------|------------|
| payment | ProviderFactory (registry) | env 对象 |
| email | EmailService (实例) | config 对象 |
| webhook | WebhookService (实例) | config 对象 |
| anti-abuse | AntiAbuseService (实例) | config 对象 |
| thompson-router | ThompsonRouter (实例) | config 对象 |
| telegram-miniapp | 纯函数 | — |

**建议：** 统一为一种或两种模式：
```typescript
// 模式 A: 通过工厂创建（适合需要 env 的模块）
const paymentRegistry = createPaymentProviders(env);

// 模式 B: 直接 new（适合纯业务逻辑模块）
const email = new EmailService({ apiKey: env.RESEND_API_KEY });
```

当前 `payment/index.ts` 的 `ProviderFactory` 设计最佳（`isAvailable()` + `create()`），可作为其他 Feature 的参考标准。

#### 9. 缺少数据库连接池配置项

**现状：** `getOrCreateClient` 中 `createClient({ url, authToken })` 没有传递任何连接池参数。

**最佳实践：** libSQL client 支持 `syncUrl`, `encryptionKey`, `concurrency` 等参数。虽然 Workers 的单 Isolate 模型天然限制了并发连接数，但明确配置更好。

**建议：**
```typescript
const client = createClient({
  url,
  authToken,
  // 显式声明并发上限
  concurrency: 10,
  // 可选 sync 配置
  ...options,
});
```

#### 10. 缺少 OpenAPI / 接口文档

**现状：** 所有 API 路由没有 Swagger/OpenAPI 注解或独立文档。

**最佳实践：** 对于模板项目，应该内置 OpenAPI 生成机制（如 `@hono/zod-openapi`），或者在 `docs/` 目录下维护 API 文档。

**影响范围：** 新项目接手时需阅读源代码才能了解 API 接口。

#### 11. scripts/create-project.mjs 需要改进

**现状：** 脚手架脚本只复制模板 + 替换变量名。缺少：
- 交互式配置向导
- 自动创建 Turso 数据库
- 自动生成 secrets
- 验证步骤

**最佳实践：** 参考 `create-next-app` 或 `create-vite` 的交互式脚手架体验。

#### 12. 限流器缺少 Reset-After 头

**现状：** 429 响应中返回了简单的错误信息，没有 `Retry-After` 响应头。

**最佳实践：** 429 响应应该包含：
```
Retry-After: <seconds>
X-RateLimit-Limit: 30
X-RateLimit-Remaining: 0
X-RateLimit-Reset: <unix-timestamp>
```

## 六、具体技术优化建议

### 6.1 立即修复：DbRateLimiter 竞态

```typescript
// rate-limit.ts - 修复后
export class DbRateLimiter implements RateLimiter {
  async check(key: string, limit: number, windowMs: number): Promise<RateLimitResult> {
    const now = Math.floor(Date.now() / 1000);
    const windowSeconds = Math.floor(windowMs / 1000);
    const windowStart = Math.floor(now / windowSeconds) * windowSeconds;
    
    try {
      const result = await this.db.execute({
        sql: `INSERT INTO rate_limit_windows (action, ip_hash, window_start, request_count)
              VALUES (?, '', ?, 1)
              ON CONFLICT(action, ip_hash, window_start)
              DO UPDATE SET request_count = request_count + 1
              WHERE request_count < ?
              RETURNING request_count`,
        args: [key, windowStart, limit],
      });
      
      // 如果 affectedRows === 0，说明达到了 limit
      // 或用 RETURNING 结果判断
      const count = result.rows?.[0]?.request_count ?? 0;
      if (count > limit) {
        return { ok: false, message: "请求过于频繁", status: 429 };
      }
      return { ok: true, remaining: limit - count };
    } catch {
      return { ok: true };
    }
  }
}
```

### 6.3 支付回调幂等性集成

```typescript
// 在 orders.ts 的支付回调处理中：
app.post("/api/payments/callback/:provider", async (c) => {
  const db = c.get("db");
  const provider = c.req.param("provider");
  const body = await c.req.parseBody();
  
  // 幂等键 = provider + 交易号

    return ok(c, { status: "already_processed" });
  }
```
