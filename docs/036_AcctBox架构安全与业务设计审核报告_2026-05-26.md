## 一、接口边界确认（最关键的问题）

### 1.1 路由架构总览

```
/api/*
  ├── /health                          ← 公开
  ├── /products                        ← 公开（商品列表）
  ├── /coupons/quote                   ← 公开（查价格用折扣码）
  ├── /orders                          ← 公开（下单入口）
  ├── /orders/lookup                   ← 公开（用户查询）
  ├── /system-config                   ← 公开（仅白名单参数）
  ├── /pay/*                           ← 公开（支付回调）
  └── /admin/*                         ← Bearer Token 保护
```

**✅ 结论：管理员接口（`/admin/*`）与用户公开接口物理隔离，不可能在不知晓 `ADMIN_TOKEN` 的情况下被调用。**

验证路径：
- `index.ts` L19：`api.route("/admin", new Hono().use("*", requireAdmin).route("/", adminRoute))`
- `requireAdmin` 中间件：读取 `AUTHORIZATION: Bearer <token>` header，与环境变量 `ADMIN_TOKEN` 比较
- 无 `ADMIN_TOKEN` 时返回 503，生产环境必须配置

### 1.2 管理员接口清单

以下接口在 `/admin/*` 下，**用户无法访问**：

| 接口 | 方法 | 功能 | 是否涉及数据泄漏 |
|------|------|------|----------------|
| `/admin/orders` | GET | 列出所有订单（支持按 status/productId/q 过滤） | ⚠️ 含敏感订单数据 |
| `/admin/orders/:id` | GET | 单笔订单详情（含卡密） | ⚠️ 含卡密 |
| `/admin/orders/:id/mark-paid` | POST | 标记已付款+发卡 | ⚠️ |
| `/admin/orders/:id/refund` | POST | 退款+回收卡密 | ⚠️ |
| `/admin/cards/import` | POST | 批量导入卡密 | ⚠️ |
| `/admin/cards/export` | GET | 导出卡密 | ⚠️ |
| `/admin/products` | CRUD | 商品管理 | ⚠️ |
| `/admin/coupons` | CRUD | 折扣码管理 | ⚠️ |
| `/admin/summary` | GET | 今日统计 | 仅统计数据 |
| `/admin/system-config` | CRUD | 系统参数配置 | ⚠️ |

**✅ 结论：管理员接口物理隔离正确，Bearer Token 鉴权是行业标准做法（类比 Stripe Admin API）。**

## 二、行业最佳实践参考：发卡网运营模式

### 2.1 调研对象：链动小铺 (ldxp.cn) 及行业通用做法

经过对链动小铺及多个主流发卡网平台（快发卡、幻世发卡、星光寄售等）的调研，得出以下行业标准做法：

#### 核心发现 1：下单成功不发送邮件

**所有发卡网均无下单成功邮件通知。**

- 链动小铺：用户付款后自动获得卡密，无邮件环节
- 幻世发卡FAQ："如果买家已经付款，但是他说没有收到卡密该怎么办？可以发给客户卡密查询地址"
- 星光寄售：提供"卡密查询"页面，用户凭支付记录中的订单号查询

**行业逻辑：**
- 数字商品（卡密）即买即得，不需要邮件确认
- 频繁邮件造成用户困扰，增加发件服务器的运营成本
- 发卡网的商品是"自动发货"，用户不需要等待

#### 核心发现 2：卡密查询页是标配，且基于人类可读订单号

**所有发卡网都有独立的"卡密查询"页面，输入 orderNo（人类可读格式）即可查到卡密。**

典型格式：
- 幻世发卡：`FK` 开头 + 数字（如 `FK20260526001`）
- 星光寄售：`FK` 开头 + 数字
- 用户在微信/支付宝付款后，支付凭证里有这个订单号

**用户场景：**
```
用户付款 → 打开微信支付记录 → 看到订单号 "FK20260526001"
→ 访问发卡网查询页 → 输入 "FK20260526001" → 获得卡密
```

**AcctBox 当前问题：**
- orderToken 是 UUID 格式，用户无法从支付记录中找到对应的 Token
- 支付平台的订单号（如微信支付单号）和 AcctBox 的 orderToken 没有关联
- 用户付款后，无法靠支付记录找回卡密

#### 核心发现 3：查询页无需登录

发卡网的卡密查询页是公开的，任何人知道 orderNo 就可以查。

**这是行业标准，因为：**
- orderNo 本身就是随机编号，无法猜测
- 卡密查询需要同时知道 orderNo + （有时需要）验证码
- 用户需要自己保护好 orderNo

#### 核心发现 4：orderNo 的重要性

orderNo 是连接"支付记录"和"查询页"的桥梁。

| 字段 | 格式 | 用途 |
|------|------|------|
| 微信/支付宝订单号 | 微信/支付宝内部单号 | 用户在支付记录里看到 |
| orderNo（平台侧） | 人类可读编号如 `O20260526ABC123` | 用户在查询页输入 |
| orderToken（UUID） | 45字符随机字符串 | 高权限凭证，仅用户下单时获得 |

用户拿到 orderNo 的渠道：
1. 下单成功后页面显示（但用户可能没截图就关闭了）
2. 支付记录的备注/描述里（如果平台做了嵌入）
3. 管理员/客服告诉用户

用户拿到 Token 的渠道：
1. 下单成功后页面显示（但用户可能没截图就关闭了）

**行业标准：用户主要靠 orderNo 查询（因为可以从支付记录找），Token 作为备用或高权限场景。**

### 2.2 AcctBox 应该采用的模式

基于行业最佳实践，AcctBox 的用户查询链路应该是：

```
下单成功 → 页面显示 orderNo（如 O20260526ABC123）+ orderToken
  → 同时在支付时，把 orderNo 嵌入支付备注（如果支持）
  → 用户付款后，去支付记录里找 orderNo
  → 访问 /lookup → 输入 orderNo → 返回卡密
  → 或者输入 orderToken → 返回卡密
```

**不需要发邮件，页面即结束。**

用户如果忘记了 orderNo：
- 联系客服，客服按邮箱/联系方式查询，帮用户找到 orderNo
- 这是最小化了客服成本的做法（只处理例外情况，而不是每个用户都发邮件）

## 三、用户场景审核（从真实使用流程出发）

### 3.1 用户下单流程

```
用户 → GET /products → 选择商品 → 填写下单表单
  → POST /orders（productId + buyerEmail + buyerContact + couponCode + turnstileToken）
  → Turnstile 人机验证
  → 限流检查（8次/分钟/IP）
  → 幂等性检查（idempotency-key）
  → 折扣码校验（无效折扣码不扣库存）
  → 发卡/创建待处理订单
  ← 返回 orderNo + orderToken（用户截图/存到邮箱）
```

**✅ 设计正确：**
- Turnstile 在下单前，能拦住机器人和爬虫
- 限流防止滥用
- 幂等性防止重复下单
- 折扣码校验在扣库存之前，符合最佳实践

**✅ 符合行业最佳实践：**

### 3.2 用户查询订单流程（核心场景）

**现状流程（Token 查询）：**
```
用户 → 访问 /lookup
  → 输入 orderToken（长 UUID，45字符）
  → GET /orders/lookup?token=<token>
  → 返回订单详情（含卡密，如果已发卡）
```

**当前缺失：用户无法用 orderNo（人类可读格式）查询，这是最大问题。**

**行业标准流程：**
```
用户付款 → 打开支付记录 → 看到 orderNo（如 O20260526ABC123）
→ 访问 /lookup → 输入 orderNo → 直接返回卡密
```

### 3.3 管理员查询订单流程

```
管理员 → GET /admin/orders?q=alice@email.com
  → 返回该邮箱相关的所有订单
  → 点击订单 → 查看详情（包含卡密）
  → 操作：标记已付款 / 退款 / 导出
```

管理员不需要登录前端页面，可以通过 API 操作。

**✅ 管理员查询链路完整。**

## 四、设计漏洞与安全问题

### 漏洞 1：用户查询链路断裂（P0 — 功能性漏洞）

**问题描述：**

当前用户查询只有两个入口：
1. `orderToken` — UUID 格式，用户记不住，且没有发邮件通知
2. `couponCode` — 只能查到"用折扣码下单 + 已发卡"的订单，覆盖面极小

**现实场景：**
- 用户买了东西，过了一周想查看卡密 → 找不到入口
- 用户换了设备，想找回订单 → 找不到入口
- 用户忘记保存 orderToken → 只能联系客服

**行业最佳实践：数字商品平台的标准查询链路是"用户从支付记录找到 orderNo → 输入查询页 → 获得卡密"。**

**修复方向：增加"orderNo 查询"和"邮箱查询"接口，用户可选择任一方式查询卡密。**

---

### 漏洞 2：发卡邮件内容错误（P0 — 数据质量问题）

**问题描述：**

邮件发给了用户，但内容是错的：
- 订单号显示的是内部 UUID（用户根本不认识）
- 商品标题显示的是卡密的账号名字段（不是商品标题）

用户收到邮件后，无法用邮件里的订单号去联系客服或再次查询。

**修复方向：**
- `order_no` → 显示 `OXXXXX` 格式的订单号
- `product_title` → 显示真实商品标题（从 `products` 表查询）

---

### 漏洞 3：管理员无法直接通过 orderNo 查询用户订单（P1 — 操作效率问题）

**问题描述：**

管理员在 `/admin/orders` 页面搜索 `q=OABC123456`，用户无法直接使用 `orderNo`（格式 `OXXXXX`）在前端查询自己的订单。

这会导致：
- 用户打电话问客服："我的订单号是 OABC123456，怎么查？"
- 客服需要在管理后台代替用户查询

**修复方向（可选）：** 在用户查询接口增加 `orderNo` 参数支持，用户可以在管理后台找到自己的订单号后，输入订单号查询。这不是必须的（邮箱查询已经够用），但能提升用户体验。

---

### 漏洞 4：订单创建时 buyerEmail 为空字符串（P0 — 数据质量问题）

**问题描述：**

`require_email=false` 时，前端不显示邮箱字段，但后端 Zod schema 已经是 `.nonempty()` 了。

关键问题在于 `order-service.ts` L104、L153：
```ts
input.buyerEmail?.trim() || ""  // 如果 buyerEmail 为空，插入 ""
```

如果有人绕过前端直接调 API，且 Zod 校验被意外绕过，数据库会插入空字符串而不是 null。

**修复方向：确保 `buyerEmail` 为空时创建订单失败（已在 Zod 层强制校验）。同时 service 层改为直接用值。**

---

### 漏洞 5：管理员后台无审计日志可见性（P2 — 操作追溯问题）

**问题描述：**

管理员操作订单（标记已付款/退款）后，审计日志写入了，但管理员自己在后台看不到操作历史。

这会导致：管理员需要查"谁把这笔订单标记了已付款"，但没有界面可用。

**修复方向（可选）：** 在管理后台订单详情页显示该订单的操作历史（事件流）。

## 六、需要确认的业务细节

### 6.1 下单成功邮件

**结论：不需要发送下单成功邮件。**

行业最佳实践：
- 发卡网（链动小铺、快发卡、幻世发卡等）均无下单成功邮件
- 数字商品即买即得，用户不需要等待确认邮件
- 发邮件会增加运营成本，且可能被视为垃圾邮件

**用户查询卡密的入口：**
1. 下单成功后页面直接显示 orderNo + orderToken（用户截图）
2. 从支付记录里找 orderNo（行业标准链路）
3. 邮箱查询（如果用户记得自己的邮箱）

### 6.2 查询页面是否需要登录？

当前 `/lookup` 页面是公开的，任何人知道 orderNo 或 orderToken 都可以查看订单。

**这是行业标准做法。**

不需要登录，因为：
- orderNo 和 orderToken 本身就是访问凭证
- 已发卡订单需要保护，但 orderNo/Token 是随机 UUID，无法猜测
- 发卡网的卡密查询页都是公开的

## 七、修正后的设计建议

### 7.1 用户查询链路（最终设计）

```
用户访问 /lookup
    ├── 输入 orderNo（如 O20260526ABC123）
    │     → GET /orders/lookup?orderNo=xxx
    │     → 返回订单详情（含卡密）
    │
    ├── 输入 orderToken（45字符 UUID）
    │     → GET /orders/lookup?token=xxx
    │     → 返回订单详情（含卡密）
    │
    └── 输入邮箱（如 alice@email.com）
          → GET /orders/lookup?email=xxx
          → 返回该邮箱所有订单列表（不含卡密，最多 10 笔，倒序）
          → 用户点击某笔订单 → 获取 orderToken → 查询详情（含卡密）
```

**说明：**
- `orderNo` 和 `orderToken` 都能查到完整卡密（两者权限等同）
- 邮箱查询是兜底方案，适合用户只记得自己邮箱的场景
- 用户用 orderNo 查询时，需要返回卡密（用户核心诉求就是卡密）

### 7.2 管理员查询链路（保持不变）

```
GET /admin/orders?q=<搜索词>
  → 支持 orderNo / buyerEmail / buyerContact 的 LIKE 搜索
  → 返回所有匹配订单（含订单数据）
  → 点击查看详情 → 显示卡密
```

## 八、结论：管理员接口是否安全？

**✅ 管理员接口被用户调用的风险：极低。**

原因：
1. 所有 `/admin/*` 接口都有 `requireAdmin` 中间件保护，没有 `ADMIN_TOKEN` 无法访问
2. 物理上用户接口和管珞接口在不同的路由树下，没有交集
3. 即使知道 orderToken，也无法调用任何管理接口

**⚠️ 需要修复的业务问题（不影响安全，但影响用户体验和数据质量）：**

| 优先级 | 问题 | 影响 |
|--------|------|------|
| **P0** | 用户查询链路断裂（无 orderNo/邮箱查询入口） | 用户无法找回自己的订单 |
| **P0** | 发卡邮件订单号和商品标题错误 | 用户收到的邮件信息无效 |
| **P0** | `buyerEmail?.trim() \|\| ""` 插入空字符串 | 历史数据质量 |
| **P1** | 用户无法用 orderNo 查询自己的订单 | 只能靠 orderToken，客服压力大 |
| **P2** | 管理员操作无二次确认 | 误操作风险 |
