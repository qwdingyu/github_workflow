# 支付架构深度分析 — 多通道集成方案

> 日期：2026-06-04
> 背景：完成 eshop 支付抽象层分析，评估充值码/USDT/Stripe 集成方式
> 目标：不做大重构，用最小变更实现三通道（充值码 / USDT / Stripe），不造轮子

---

## 一、当前支付架构评估

### 1.1 现有抽象层（payments/）质量评估

| 模块 | 文件 | 评估 | 需要改动？ |
|------|------|------|-----------|
| `PaymentProvider` 接口 | `types.ts` | ✅ 设计到位，方法覆盖全面 | 不需要改 |
| 注册表工厂 | `registry.ts` | ✅ per-request 注入，env 驱动注册 | **需要扩展** |
| Alipay 实现 | `alipay-provider.ts` | ✅ 完整实现，签名/验签/轮询全 | 不需要改 |
| 统一下单路由 | `pay.ts` | ✅ 含降级、幂等、限流、安全头 | **需要扩展** |
| 回调路由 | `pay.ts` | ✅ Provider 抽象验签 + 事务安保 + markPaidAndIssue | **需要扩展** |
| 发卡服务 | `issue-service.ts` | ✅ UPDATE RETURNING 原子性 OK | 不需要改 |

**结论：抽象层设计到位，不需要重构。** 当前 `PaymentProvider` 覆盖了 80% 的场景。问题是**新支付方式不全都是 Provider 接口的合适实现者**。

### 1.2 当前支付流的定义

```
/pay/unified 路由
   │
   ├─ 支付宝（selectOnline 选择）
   │    → 创建支付二维码
   │    → 用户扫码
   │    → 异步回调 /pay/callback/alipay
   │    → verifyCallback → markPaidAndIssue
   │
   └─ 降级 → 线下支付
        → 创建 order + 锁卡
        → 用户转账 + 确认流水号
        → 管理员后台手动确认 → markPaidAndIssue
```

### 1.3 现有抽象不能完全覆盖三类新支付

| 支付方式 | 适合 Provider 接口？ | 原因 |
|----------|---------------------|------|
| **充值码** | ❌ 不是外部队列 | 纯粹内部账务系统，不需要 createPayment/callback |
| **USDT/TRC20** | ⚠️ 部分适合 | createPayment 可用，但 verifyCallback 需要区块链监听器 |
| **Stripe** | ✅ 完全适合 | 标准的 createPayment → redirect → webhook callback |

## 二、三通道集成方案

### 2.1 核心设计原则

> **不改 PaymentProvider 接口，不重构 pay.ts 主体逻辑**  
> 每个通道以最小侵入方式"挂入"现有架构

### 2.2 [P0] 充值码系统

#### 定位
充值码不是支付方式，是**预付费凭证**。用户在系统外付款，你给他一个码，他在你的网站上兑换成余额，然后用余额购买商品。

#### 架构位置（不经过 pay.ts）

```
第三方支付了 → 你给用户充值码
用户到站点 → POST /api/vouchers/redeem { code, buyerEmail, turnstileToken }
     ↓
验证码有效 + 未使用 → user_balances 增加余额
     ↓
用户选购商品 → POST /api/pay/unified { productId, buyerEmail, balancePayment: true }
     ↓
pay.ts 检测 balancePayment → 检查余额 → 扣减 → 直接走 markPaidAndIssue 发卡
     ↓
发卡成功 → 返回卡密
```

#### 新增数据库表

```sql
-- 充值码表
CREATE TABLE voucher_codes (
  code          TEXT PRIMARY KEY,          -- 如 VCH-A1B2C3D4
  amount_cents  INTEGER NOT NULL,          -- 面值（分）
  status        TEXT DEFAULT 'active',      -- active | used | expired | revoked
  used_by_email TEXT,                       -- 使用人邮箱
  used_at       TEXT,                       -- 使用时间
  expires_at    TEXT,                       -- 过期时间
  batch_id      TEXT,                       -- 批次号
  notes         TEXT,                       -- 备注
  created_at    TEXT NOT NULL
);

-- 用户余额表
CREATE TABLE user_balances (
  email         TEXT PRIMARY KEY,          -- 用户邮箱
  balance_cents INTEGER DEFAULT 0,        -- 当前余额（分）
  total_deposited_cents INTEGER DEFAULT 0, -- 累计充值
  total_spent_cents INTEGER DEFAULT 0,     -- 累计消费
  updated_at    TEXT NOT NULL
);
```

#### 新增文件

| 文件 | 职责 |
|------|------|
| `src/services/voucher-service.ts` | 充值码 CRUD、兑换逻辑、余额查询 |
| `src/routes/vouchers.ts` | 充值码路由（用户端 redeem + balance，管理员端 generate/list） |

#### 对 pay.ts 的变更

**仅一处修改**：在 `pay.ts` 的统一下单路由中增加余额支付校验分支：

```typescript
// 在 /pay/unified 开始处，查库存之前
if (body.data.balancePayment) {
  return await handleBalancePayment(db, product, body.data.buyerEmail, ...);
}
```

`handleBalancePayment` 函数：
1. 查询 `user_balances` 检查余额
2. 余额不足 → 返回错误
3. 余额充足 → 扣减余额（原子 UPDATE RETURNING）
4. 调用 `markPaidAndIssue` 发卡
5. 返回卡密

**无需改动现有 Order、Issue、Email 服务。**

#### 充值码 vs 现有 redeem 的区别

| 维度 | 现有 redeem（折扣码） | 新建 voucher（充值码） |
|------|---------------------|----------------------|
| 金额 | 0 元（免费兑换） | 有面值（预付费） |
| 来源 | 营销创建 | 系统生成批量销售 |
| 核销 | 绑定到订单（优惠金额） | 转为余额再消费 |
| 用途 | 促销 | 变现 |

### 2.3 [P1] USDT/TRC20 集成

#### 定位
USDT/TRC20 是**零资质、零门槛的全球收款方式**。适合外网用户、大额订单，与支付宝互补。

#### 核心挑战
USDT 不是"创建支付 → 回调通知"模式，而是"用户向指定地址转账 → 你查链上交易确认"模式。

#### 方案选择

| 方案 | 复杂度 | 可靠性 | 推荐？ |
|------|--------|--------|--------|
| A: 每订单生成唯一地址 | ❌ 高，需要 HD 钱包 | ✅ 最好 | 过度设计 |
| B: 单地址 + 唯一 Memo/标签 | ✅ 低 | ✅ 好 | **推荐** |
| C: 单地址 + 金额匹配 | ✅ 极低 | ⚠️ 金额碰撞 | 不推荐 |

#### 方案 B 的实现

```
USDT 采用 TRC20 协议（单地址 + 每订单唯一 Memo）
            ↓
createPayment 返回：{ address: "TR7NH...", amount: 5.00, memo: "123456" }
            ↓
用户使用支持 Memo 的钱包（OKX/Binance 等）转账
            ↓
TronGrid API 轮询该地址的 USDT 交易
    ↓ 匹配 memo + 金额 + 确认数 ≥ 19
    ↓
调用 markPaidAndIssue
```

#### Provider 实现

```typescript
class Trc20Provider implements PaymentProvider {
  readonly name = "usdt_trc20";
  readonly displayName = "USDT (TRC20)";
  readonly supportedCurrencies = ["USDT"];

  async createPayment(input: CreatePaymentInput): Promise<CreatePaymentResult> {
    // 生成 6 位随机 Memo
    const memo = generateMemo(input.orderNo);
    // 将 memo 存到订单表（新字段 payment_ref 或扩展 metadata）
    // 返回地址 + 金额 + memo
    return {
      redirectUrl: undefined,
      qrCode: undefined,
      raw: {
        address: this.walletAddress,
        amount: (input.amountCents / 100).toFixed(2),
        memo,
        network: "TRC20",
      }
    };
  }

  async verifyCallback(params: Record<string, string>): Promise<CallbackResult> {
    // USDT 不走 HTTP 回调，这方法对 USDT 实际上不会使用
    // 保留接口实现以防未来 webhook 方案
    throw new Error("USDT uses polling, not HTTP callbacks");
  }

  async queryStatus(tradeNo: string): Promise<{ paid: boolean }> {
    // 查 TronGrid API 看该 orderNo 对应的 memo+金额是否已到账
    // 核心逻辑在 Trc20Monitor 中，这里只是状态查询
  }
}
```

#### 区块链监控服务

这是 USDT 的特色——需要一个**链上交易监听器**。

方案有两种：

**方案 A：TronGrid 轮询（推荐）**
- 在 `/pay/status` 轮询接口中**增强**：当 provider 是 USDT 时，查 TronGrid
- 也可以做一个独立的 GitHub Actions 定时任务（每分钟）调 USDT 监听端点
- TronGrid Free 方案每分钟可查 10 次，足够

**方案 B：TronGrid Webhook**
- TronGrid 不支持主动 webhook
- 可以自己部署一个 Cloudflare Workers 定时 Cron（每 1 分钟）
- 但 Free 版 Cron 仅 10ms CPU 时间，不够用
- 需要 Workers Paid 或 GitHub Actions 替代

**推荐方案**：增强 `/pay/status/:orderId` 轮询接口，当订单的 `paymentProvider === "usdt_trc20"` 时，查 TronGrid API 检查该订单的 memo+金额是否匹配到链上交易。

```typescript
// 在 /pay/status/:orderId 中增强
const statusResult = await payStatusQuery(db, orderId, token);

// 如果订单支付方式是 USDT，检查链上交易
if (statusResult.paymentProvider === "usdt_trc20" && statusResult.status === "pending") {
  const paid = await checkTrc20Transaction(statusResult);
  if (paid) {
    await markPaidAndIssue(db, orderId);
    statusResult.status = "issued";
  }
}
```

#### 新增文件

| 文件 | 职责 |
|------|------|
| `src/services/payments/trc20-provider.ts` | Trc20Provider 实现（createPayment, queryStatus） |
| `src/services/trc20-monitor.ts` | TronGrid API 查询、交易匹配 |
| `src/services/payments/index.ts` | 导出注册（更新） |

#### 对 registry.ts 的变更

```typescript
// registry.ts 中增加 USDT 注册
if (env.TRC20_WALLET_ADDRESS && env.TRONGRID_API_KEY) {
  registry.set("usdt_trc20", new Trc20Provider(
    env.TRC20_WALLET_ADDRESS,
    env.TRONGRID_API_KEY,
  ));
}
```

#### 对 Bindings 的变更

```typescript
// bindings.ts 增加
TRC20_WALLET_ADDRESS?: string;  // TRC20 收款地址
TRONGRID_API_KEY?: string;      // TronGrid API Key
```

#### 对 pay.ts 的变更

在统一下单路由中，`selectOnline()` 之后增加一个判断：如果 `payableCents > 10000`（¥100），在前端展示 USDT 选项：

```typescript
// 在统一下单成功后，附加 USDT 支付选项
const availableMethods = [{ provider: provider.name, qrcode: payResult.qrCode }];
if (registry.get("usdt_trc20")) {
  availableMethods.push({ provider: "usdt_trc20", method: "transfer" });
}
```

或者更简单：**让前端知道所有可用 provider 列表，用户自己选择**（不自动 fallback）。

### 2.4 [P2] Stripe（资质就绪后）

Stripe 是最"标准"的集成——完全适配现有的 `PaymentProvider` 接口。

#### Provider 实现

```typescript
class StripeProvider implements PaymentProvider {
  readonly name = "stripe";
  readonly displayName = "Stripe";
  readonly supportedCurrencies = ["USD", "EUR", "GBP", ...];

  async createPayment(input: CreatePaymentInput): Promise<CreatePaymentResult> {
    const session = await stripe.checkout.sessions.create({
      line_items: [{ price_data: { ... }, quantity: 1 }],
      mode: "payment",
      success_url: `${origin}/lookup?session_id={CHECKOUT_SESSION_ID}`,
      cancel_url: `${origin}/cancel`,
    });
    return { redirectUrl: session.url };
  }

  async verifyCallback(params: Record<string, string>): Promise<CallbackResult> {
    const event = stripe.webhooks.constructEvent(payload, sig, webhookSecret);
    // 提取 orderNo 从 metadata
    return { orderNo, providerTradeNo, amountCents, ... };
  }

  async queryStatus(sessionId: string): Promise<{ paid: boolean }> {
    const session = await stripe.checkout.sessions.retrieve(sessionId);
    return { paid: session.payment_status === "paid" };
  }
}
```

**修改 registry.ts**（取消 Stripe 注释）：

```typescript
if (env.STRIPE_SECRET_KEY && env.STRIPE_WEBHOOK_SECRET) {
  registry.set("stripe", new StripeProvider(env.STRIPE_SECRET_KEY, env.STRIPE_WEBHOOK_SECRET));
}
```

**对 pay.ts 的修改**：几乎为零改动。Stripe 完整适配现有接口。

### 3.2 绝对不改的部分

| 模块 | 原因 |
|------|------|
| PaymentProvider 接口（types.ts） | 设计已到位，覆盖所有需要的方法 |
| issue-service.ts | 原子发卡逻辑成熟，所有支付都走它 |
| order-service.ts（markPaidAndIssue） | 发卡+邮件+扣券一体化，改它风险极高 |
| email-service.ts | 已经够用 |

### 3.3 不需要做的（避免过度设计）

| ❌ 不做 | 原因 |
|---------|------|
| 用户注册/登录系统 | 充值码用邮箱绑定就够了，不需要密码 auth |

| 链上自动出金 | 初期手动用 Binance P2T 出金即可 |
| 多链支持 | 只做 TRC20，不做 ETH/BSC/SOL |
| 退款自动化 | 初期手动退款（加密货币退款本身就不是个简单事） |

| 通道 | 优先级 | 预估文件数 | 预估新增代码行数 | 对现有代码侵入度 |
|------|--------|-----------|-----------------|----------------|

```

结论：从 P0 到 P1 的路径最清晰，收益最高
```

## 五、核心流程：所有支付方式统一走向的路

这个图展示了所有支付方式最终汇入同一条发卡路径：

```
        ┌──────────────┐
        │  用户下单     │
        └──────┬───────┘
               │
      ┌────────┴────────┐
      ▼                 ▼
  选择方式          直接购买
      │                 │
  ┌───┴───────┐    ┌────┴────┐
  │ 支付宝在线 │    │ 余额支付 │
  │ USDT 转账  │    │(充值码)  │
  │ Stripe     │    └────┬────┘
  │ 线下汇款   │         │
  └───┬───────┘         │
      │                 │
      ▼                 ▼
  确认已付款      检查余额足够
      │                 │
      └────────┬────────┘
               ▼
      ┌────────────────┐
      │ markPaidAndIssue│  ← 唯一发卡入口
      │ (order-service) │
      └────────┬───────┘
               ▼
      ┌────────────────┐
      │ 原子发卡 + 邮件 │
      │ + 扣优惠券     │
      └────────────────┘
```

**关键结论**：`markPaidAndIssue` 是所有支付通道的**统一出口**。不管用户从哪个通道付款，最终都走到这里。新通道不需要自己写发卡逻辑，只需要在"确认已付款"后调用它。

## 六、风险与边界条件

### 6.1 USDT 特有风险

| 风险 | 概率 | 缓解方案 |
|------|------|---------|
| Memo 被用户遗忘 | 高 | 前端提示 + 客服人工匹配（额外提供转账 txid 查询） |
| 金额小额偏差 | 中 | 允许 ±2% 偏差（考虑链上手续费扣减） |
| 链上确认时间长 | 中 | 19 确认 ≈ 60s，前端显示"检测中"状态 |
| 40% USDT 被冻结 | 低 | 只用主流交易所出金（Binance/OKX） |
| TronGrid API 限流 | 低 | Free 方案每分钟 10 次，足够 |

### 6.2 充值码特有风险

| 风险 | 概率 | 缓解方案 |
|------|------|---------|
| 充值码泄露 | 中 | 导出 CSV 时警告"等同现金"，批量设置过期时间 |
| 代理未付款 | 高 | 先收款后给码，不接受赊账 |
| 对账困难 | 中 | 批次号管理 + 管理员统计接口 |
