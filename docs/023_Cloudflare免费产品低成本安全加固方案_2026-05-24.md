# Cloudflare 免费产品低成本安全加固方案

## 背景

当前我们已经跑通：

```text
Cloudflare Pages 静态站
Cloudflare Workers + Static Assets
Workers Custom Domains
D1 数据库
少量 API / 表单 / 发卡 demo
```

但目前重点在“上线跑通”，还没有系统加固。本文从防守角度梳理适合个人开发者的低成本安全方案，目标是：

```text
低成本
可执行
可复制
不过度工程化
能防住最常见攻击和误操作
```

## 先给结论

个人开发者使用 Cloudflare 免费产品，最优安全策略不是堆复杂系统，而是做三层防线：

```text
第一层：Cloudflare 边缘防护
WAF / DNS / TLS / HTTPS / Bot / Turnstile / 基础访问规则

第二层：Worker 应用层防护
输入校验 / 速率限制 / 幂等 / 权限 / 日志 / 安全响应头

第三层：数据和运维防护
D1/KV/R2 最小权限 / 备份 / 密钥隔离 / GitHub 保护 / 文档化脚本
```

最小可执行方案：

```text
1. Cloudflare 账号和 GitHub 全部启用 2FA。
2. 禁止继续依赖 Global API Key，逐步改为 scoped API Token。
3. 所有 POST 表单/API 接入 Turnstile。
4. 所有写接口加 Worker 内部限流。
5. D1 使用 prepared statements，禁止拼 SQL。
6. 管理接口必须有鉴权，不暴露在公开页面。
7. R2 文件默认私有，通过 Worker 签名/鉴权发放。
8. 每个项目记录域名、数据库、存储、密钥、部署脚本。
9. 每次上线跑 smoke，且 smoke 分只读和写入两类。
10. 每次踩坑记录到 docs。
```

## 威胁模型

### 我们最可能遇到的攻击

```text
1. 爬虫抓取静态页、批量提交表单。
2. 暴力刷发卡接口，耗尽库存。
3. 重放 POST 请求，重复创建订单或重复消耗库存。
4. 枚举订单 ID、商品 ID、下载链接。
5. R2 文件直链泄露后被批量下载。
6. D1/KV 被高频访问打爆免费额度。
7. GitHub token / Cloudflare token 泄露。
8. 误把真实卡密写入 seed.sql 或 Git 仓库。
9. 管理 API 没有鉴权，被公开访问。
10. 域名、DNS、Worker、Pages 项目混用导致误删或误绑定。
```

### 当前项目风险分级

| 场景 | 风险 | 说明 |
| --- | --- | --- |
| 纯静态 Pages | 低 | 主要风险是钓鱼仿冒、脚本注入、错误链接、缓存 |
| 静态页 + 表单 | 中 | POST 被刷、垃圾数据、额度消耗 |
| 发卡/库存 | 中高 | 库存被刷空、重复发放、卡密泄露 |
| 文件下载/R2 | 中高 | 盗链、批量下载、资料泄露 |
| 管理后台 | 高 | 权限绕过、凭据泄露、数据篡改 |
| 支付回调 | 高 | 伪造回调、重复回调、订单状态错误 |

## Cloudflare 边缘层加固

### 1. TLS 和 HTTPS

必须配置：

```text
SSL/TLS mode：Full (strict)
Always Use HTTPS：开启
Minimum TLS Version：TLS 1.2 或更高
Automatic HTTPS Rewrites：开启
```

谨慎配置：

```text
HSTS
```

HSTS 一旦打开并 preload，回滚成本高。个人项目建议等域名和证书稳定后再开。

### 2. DNS 和域名

规则：

```text
1. Pages 使用 DNS-only CNAME 指向 project.subdomain。
2. Workers Custom Domain 使用 Cloudflare 自动生成的 read_only AAAA 100::。
3. 不手动改 Workers Custom Domain 的 DNS 记录。
4. 不把 Pages 和 Workers 域名流程混用。
5. 域名绑定后必须 curl 验证。
```

项目文档必须记录：

```text
正式域名
Cloudflare 产品：Pages / Workers
项目名 / Worker service
DNS 记录
默认域名
绑定脚本
验证命令
```

### 3. WAF / Security Rules

免费层可做基础规则。推荐先做“少而准”的规则，不要一上来大面积拦截。

建议规则：

```text
1. 阻止明显危险路径：
   /wp-admin
   /wp-login.php
   /.env
   /.git
   /phpmyadmin

2. 对管理路径加 Challenge 或 Cloudflare Access：
   /admin/*
   /internal/*

3. 对 API 写接口加更严格规则：
   /api/orders
   /api/forms
   /api/upload

4. 对非预期方法阻断：
   静态站只允许 GET/HEAD。
   API 按需允许 POST/OPTIONS。
```

注意：

```text
不要对所有 API 直接上 Managed Challenge。
浏览器表单可以挑战，server-to-server webhook 不适合挑战。
```

### 4. Bot 和 Turnstile

表单、发卡、邀请、下载申请类接口建议接 Turnstile。

适合：

```text
POST /api/orders
POST /api/forms
POST /api/invitations
POST /api/download-request
```

流程：

```text
前端加载 Turnstile
用户提交时带 turnstile token
Worker 调 Cloudflare Turnstile siteverify
验证成功才写 D1/KV/R2
```

最小策略：

```text
公开写接口必须 Turnstile + Worker 限流。
内部管理接口不靠 Turnstile，必须鉴权。
```

### 5. Rate Limiting

优先级：

```text
第一选择：Cloudflare 规则层限流，如果当前计划可用。
第二选择：Worker 内部限流。
第三选择：D1/KV 记录 IP + action + 时间窗口。
```

Worker 内部限流建议：

```text
按 IP 限制：
每分钟最多 5 次订单创建
每小时最多 20 次表单提交

按 buyerContact 限制：
同一个联系方式每小时最多 3 次

按 productId 限制：
库存不足时快速返回，避免继续查写
```

不要只按 IP：

```text
代理用户会共享 IP。
攻击者会换 IP。
因此 IP + 联系方式 + 行为类型组合更稳。
```

## Worker 应用层加固

### 1. 输入校验

每个 API 必须做：

```text
method 校验
content-type 校验
body size 限制
字段类型校验
字段长度限制
枚举值白名单
正则白名单
```

禁止：

```text
直接把用户输入拼进 SQL。
直接把用户输入作为 R2 object key。
直接把用户输入写入响应 HTML。
```

### 2. SQL 和 D1

必须：

```text
使用 db.prepare().bind()
使用 migration 管理表结构
索引所有查询条件
关键状态使用 CHECK 约束
唯一字段使用 UNIQUE
```

发卡类业务必须：

```text
库存状态：available / issued / disabled
订单状态：issued / sold_out / failed
卡密 issued_order_id UNIQUE
发卡时 UPDATE ... RETURNING 领取库存
订单写入失败时回滚卡密状态
```

当前 AcctBox 已做到：

```text
cards.status CHECK
orders.status CHECK
cards.issued_order_id UNIQUE
idx_cards_product_status
UPDATE cards ... RETURNING
```

后续建议增强：

```text
增加 idempotency_key，防止重复提交。
增加 request_log，记录限流和异常。
增加 admin_audit_logs，记录管理操作。
```

### 3. KV 使用边界

KV 不适合作为发卡主库。

KV 适合：

```text
活动开关
页面配置
短链接映射
缓存公开商品列表
限流计数的辅助缓存
```

KV 不适合：

```text
库存扣减
订单状态
支付状态
强一致计数
唯一约束
```

如果用 KV 做限流：

```text
只作为低成本防刷层。
不能把它当成严格风控系统。
```

### 4. R2 文件安全

默认规则：

```text
R2 bucket 私有。
不公开真实 object key。
下载必须经过 Worker。
Worker 验证订单或授权后再返回文件。
大文件使用短期签名 URL。
```

防盗链：

```text
下载链接加过期时间。
下载链接绑定订单或用户。
记录下载次数。
超过次数后要求重新验证。
```

### 5. 管理接口安全

管理接口不要暴露给普通用户。

低成本方案：

```text
Cloudflare Access 保护 /admin/*
或 Worker 校验 ADMIN_TOKEN
```

最低要求：

```text
ADMIN_TOKEN 使用 wrangler secret，不写入 Git。
管理 API 必须检查 Authorization: Bearer <token>。
所有管理操作写 audit log。
```

禁止：

```text
/api/admin/import-cards 无鉴权。
前端隐藏按钮但 API 不鉴权。
把 admin token 写在 public/app.js。
```

### 6. 安全响应头

静态资源建议：

```text
Content-Security-Policy
Referrer-Policy
X-Content-Type-Options
Permissions-Policy
frame-ancestors 'none'
```

当前 AcctBox 已在 `public/_headers` 配置基础安全头。

Worker JSON API 建议也返回：

```text
cache-control: no-store
content-type: application/json
```

当前 AcctBox API 已返回 `cache-control: no-store`。

## 数据和密钥安全

### 1. Cloudflare API Token

不要长期依赖 Global API Key。

推荐：

```text
日常部署 token：
Account - Workers Scripts: Edit
Account - D1: Edit
Account - Workers Builds / Pages 按需

域名 token：
Account - Workers Custom Domains: Edit
Zone - DNS: Edit 或按具体 API 需要

只读诊断 token：
Account - Workers Scripts: Read
Zone - DNS: Read
```

规则：

```text
1. token 只放本地环境变量或 CI secret。
2. token 不写入 docs、README、commit。
3. 每个项目尽量使用 scoped token。
4. Global API Key 只作为临时救火，不作为长期自动化凭据。
5. token 泄露后立即轮换。
```

### 2. Wrangler secrets

敏感值使用：

```bash
rtk npx wrangler secret put ADMIN_TOKEN
rtk npx wrangler secret put TURNSTILE_SECRET_KEY
```

不要写入：

```text
wrangler.jsonc
public/app.js
seed.sql
docs
README
```

### 3. GitHub 安全

必须：

```text
GitHub 账号 2FA。
仓库 private。
启用 secret scanning。
保护 main 分支。
部署脚本和 docs 同步提交。
```

个人项目可接受：

```text
一个人开发时不强制 PR。
但生产项目至少要求本地 check/smoke 通过再 push。
```

### 4. seed.sql 安全

规则：

```text
seed.sql 只能放演示数据。
真实卡密用管理接口导入，或本地临时 SQL 导入后不提交。
```

如果误提交真实卡密：

```text
1. 立即作废卡密。
2. 从 GitHub secret scanning 角度视为泄露。
3. 重写历史不是首选，先让泄露内容失效。
4. 记录事故复盘。
```

## 低成本加固路线

### 第 0 层：今天就做

```text
1. 所有账号启用 2FA。
2. 所有项目写清楚 repo/domain/database/storage 映射。
3. 所有公开 POST 接口加输入校验和长度限制。
4. 所有 API 返回 no-store。
5. 所有部署后跑 npm run verify / npm run smoke。
6. docs 记录真实域名、D1 id、Worker service。
```

### 第 1 层：最低成本有效防护

```text
1. Turnstile 加到表单和发卡 POST。
2. Worker 内部加 IP + buyerContact 限流。
3. 管理接口加 ADMIN_TOKEN。
4. R2 私有化，下载走 Worker。
5. D1 增加 request_logs 和 audit_logs。
```

### 第 2 层：适合开始有真实用户后

```text
1. Cloudflare WAF 规则阻断危险路径。
2. Cloudflare Access 保护后台。
3. 支付回调签名验证和幂等表。
4. D1 定期导出备份。
5. GitHub 分支保护和 CI smoke。
```

### 第 3 层：业务变重要后

```text
1. 分离 admin Worker 和 public Worker。
2. D1 / Supabase / Turso 做主从或同步策略。
3. R2 下载加短期签名和次数限制。
4. 告警：错误率、库存异常、请求暴增。
5. token 分项目、分权限、定期轮换。
```


## 标准安全检查清单

新项目上线前必须回答：

```text
1. 是否有公开 POST 接口？
2. POST 是否有 Turnstile 或同等防刷？
3. 是否有限流？
4. 是否有 D1/KV/R2 写入？
5. 写入是否有输入校验？
6. 是否有管理接口？
7. 管理接口是否鉴权？
8. 是否有真实密钥或卡密进入 Git？
9. 是否有 R2 公共文件？
10. 是否跑过 verify/smoke？
11. 是否记录 repo/domain/database/storage 映射？
12. 是否使用 scoped token？
```

任何一项不清楚，不允许宣称“已上线可运营”。

## 最终建议

对个人开发者，最优安全方案不是买很多服务，而是：

```text
Cloudflare 边缘规则挡大部分噪音。
Turnstile 防公开写接口被刷。
Worker 内部限流做第二道防线。
D1 做结构化数据和约束。
R2 私有化存文件。
GitHub 和 Cloudflare token 最小权限。
每个项目文档化映射和验证脚本。
```

这套方案成本最低，复杂度可控，适合我们现在的多小项目、低流量、快速上线模式。
