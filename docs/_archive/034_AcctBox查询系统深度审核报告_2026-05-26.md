## 二、逐行 Bug 清单（按严重程度）

### 🔴 Bug 1（严重）：折扣码查询返回错误订单 — 数据泄露风险

**文件**：`src/services/order-service.ts` L242-268

```ts
// 当前代码
const row = await db.prepare(`
  SELECT ... FROM orders o
  JOIN coupons cp ON lower(cp.code) = lower(o.coupon_code)
  WHERE lower(o.coupon_code) = ?1 AND cp.max_uses = 1   ← 限制 max_uses=1
  ORDER BY o.created_at DESC
  LIMIT 1                                              ← 只取最新一笔
`).bind(code).first<OrderSummaryRow>();
```

**问题 A — 只支持 max_uses=1 的折扣码**：
多用户折扣码（`max_uses > 1`）完全无法通过折扣码查询。例如管理员生成一个 `SAVE20` 折扣码给所有用户用，当 100 个用户都用这个码下单后，这 100 个用户中没有一个人能用折扣码找回订单。

**问题 B — LIMIT 1 永远返回最新的**：
考虑这个场景：
1. 张三用折扣码 `VIP50` 下单 → 订单A
2. 李四用同一个折扣码 `VIP50` 下单 → 订单B（created_at 更新）
3. 张三访问查询页，输入 `VIP50` → `ORDER BY created_at DESC LIMIT 1` → 返回李四的订单B

张三看到的是李四的订单，包含了李四的账号和卡密信息。**这是严重的数据泄露**。

**正确做法**：
- 折扣码查询应该要求用户**同时提供订单号或邮箱**，做二次验证
- 或者**去掉 `LIMIT 1`**，返回**该用户自己的订单**（但需要识别"用户是谁"）
- 如果 `require_email=true`：折扣码查询必须同时提供 `buyerEmail`，后端验证邮箱匹配

**文件**：`src/services/order-service.ts` L318-324

```ts
// 当前代码
templateData: {
  order_no:      order.id,               // ❌ 用了内部 UUID，应该是 orderNo

  delivery_secret: issued.deliverySecret,
  delivery_note: issued.deliveryNote || ""
```

### 🔴 Bug 3（严重）：查询入口完全不完整

**文件**：`src/routes/orders.ts` L76-84

```ts
// 当前 lookup 路由
orderRoute.get("/orders/lookup", async (c) => {
  const token = c.req.query("token")?.trim();
  const code = c.req.query("code")?.trim();
  if (!token && !code) return fail(c, "请输入订单 Token 或折扣码", 400);
  const order = token
    ? await getOrderByToken(c.env.DB, token)
    : await getOrderByCouponCode(c.env.DB, code || "");
  if (!order) return fail(c, "订单不存在，或该折扣码不支持查询", 404);
  return ok(c, { order });
});
```

**缺失的查询方式**：
| 查询方式 | 用户需求 | 当前状态 |
|---------|---------|---------|
| orderToken | 有 lookupUrl 的用户 | ✅ 已实现 |
| 折扣码(code) | 免单用户（但有 Bug） | ⚠️ 有 Bug（见 Bug 1） |
| **邮箱(email)** | **用户记不住订单号，但记得邮箱，这是业界最广泛的做法** | ❌ 完全不存在 |
| **订单号(orderNo)** | **用户可看到订单号（在付款界面/确认邮件中）** | ❌ 完全不存在 |

用户说的核心问题："给他订单号他记不住，但是让他填邮箱可以"——这个需求当前系统完全没有实现。

### 🟡 Bug 4（中等）：Server 端 `require_email` 完全没有强制校验

**文件**：`src/routes/orders.ts` L12-19

```ts
// createOrderSchema
const createOrderSchema = z.object({
  productId: z.string().regex(...).optional(),
  buyerContact: z.string().trim().min(3).max(120).optional(),
  buyerEmail: z.string().trim().email().max(160).optional(),  // ← 永远可选，无条件
  couponCode: ...
  ...
});
```

**问题**：
- 前端通过 `requireEmail` 变量控制邮箱字段显示/必填（`app.js` L479）
- 但后端 `buyerEmail` 在 Zod schema 中是 `.optional()`，**完全没有读 `system_config` 表中 `require_email` 的值**
- 用户可以绕过前端，直接调 API 跳过邮箱验证
- `system-config.ts` 已经有白名单机制，但 `orders.ts` 路由完全没有使用它

**正确做法**：在后端读 `system_config` 的 `require_email`，动态决定 schema 是否强制要求 `buyerEmail`：

```ts
// 路由层
const { results } = await c.env.DB.prepare(
  "SELECT value FROM system_config WHERE key = 'require_email'"
).first<{ value: string }>();

const requireEmailServer = results?.value === "true";

const schema = requireEmailServer
  ? createOrderSchemaRequireEmail  // buyerEmail: z.string().email().min(1)
  : createOrderSchemaOptionalEmail; // buyerEmail: z.string().email().optional()
```

### 🟡 Bug 5（中等）：线下购买 `buyerContact` 写死为占位符

**文件**：`src/routes/pay.ts` L61, L290

```ts
// 在线支付
buyer_contact = `pay:${orderNo.slice(-8)}`

// 线下购买
buyer_contact = `offline:${orderNo.slice(-8)}`
```

**问题**：
- `buyerContact` 在当前系统中似乎用于显示给管理员看的联系方式标识
- 但如果管理员在管理后台查询某用户，需要按联系方式筛选，这个字段填 `offline:XXXXXX` 没有任何筛选价值
- 线下购买路径根本没有要求用户填联系方式（只有邮箱可选），导致管理后台 `q` 参数搜索无效

**注**：如果 `buyerContact` 只是用于"演示/低风险商品不需要联系方式"的场景，这是合理的。但如果系统设计要求支持联系方式查询，这个字段就没有意义了。建议确认业务需求。

### 🟡 Bug 6（中等）：前端查询入口的判断逻辑不完整

**文件**：`src/public/app.js` L507-509

```js
// 当前判断
const value = String(new FormData(lookupForm).get("token") || "").trim();
const key = value.length > 40 ? "token" : "code";
const data = await api(`/api/orders/lookup?${key}=${encodeURIComponent(value)}`);
```

**问题**：
- 只判断了"长字符串→token，短字符串→code"两种情况
- 用户输入 `alice@email.com` → 会被误判为 `code`，发送 `/lookup?code=alice@email.com` → 404
- 用户输入 `AB20260526XXXXXX`（订单号）→ 被误判为 `code` → 可能查到错误订单（如果恰好有订单用了这个字符串作为折扣码）
- **自动识别逻辑完全缺失**

**正确做法**：
```js
let query;
if (value.includes("@")) {
  query = `email=${encodeURIComponent(value)}`;
} else if (value.length > 40) {
  query = `token=${encodeURIComponent(value)}`;
} else {
  query = `orderNo=${encodeURIComponent(value)}`;
}
const data = await api(`/api/orders/lookup?${query}`);
```

## 三、核心问题总结（一句话）

| # | 问题 | 一句话描述 |
|---|------|----------|
| 1 | 折扣码查询 LIMIT 1 | 多用户折扣码场景下返回别人的订单（严重数据泄露） |
| 2 | 折扣码查询 max_uses=1 | `max_uses > 1` 的折扣码完全无法查询 |
| 3 | 邮件模板填充错误 | 订单号用 UUID，商品标题用卡密账号名 |
| 4 | 邮箱查询缺失 | 完全没有 `?email=` 查询接口 |
| 5 | 订单号查询缺失 | 完全没有 `?orderNo=` 查询接口 |
| 6 | require_email 后端未强制 | 前端强制，后端可绕过 |
| 7 | 前端自动识别输入类型 | 邮箱会被误判为折扣码 |
| 8 | 查询结果数量 | email 可能对应多笔订单，当前只返回 LIMIT 1 |

## 五、修复后的查询系统完整流程

```
用户访问 /lookup，输入任意以下信息：

① 邮箱 → user@x.com
    → GET /api/orders/lookup?email=user@x.com
    → 后端：SELECT * FROM orders WHERE buyer_email = ?1 ORDER BY created_at DESC
    → 如果找到 1 笔：直接返回
    → 如果找到多笔：返回列表，用户选择其中一笔
    → 如果没找到：404 "未找到订单"

② 订单号 → AB20260526ABCDEF
    → GET /api/orders/lookup?orderNo=AB20260526ABCDEF
    → 后端：SELECT * FROM orders WHERE order_no = ?1
    → 返回订单详情

③ orderToken → （长的无意义字符串）
    → GET /api/orders/lookup?token=xxx
    → 后端：hash 查询，返回订单详情

④ 折扣码 → SAVE20
    → 前端同时要求用户输入 buyerEmail（如果 require_email=true）
    → GET /api/orders/lookup?code=SAVE20&email=user@x.com
    → 后端：
        1. 找到使用该折扣码的订单
        2. 如果 require_email=true：验证 buyer_email = ?email
        3. 如果不匹配：返回 "订单不匹配"
        4. 如果匹配：返回订单详情
```
