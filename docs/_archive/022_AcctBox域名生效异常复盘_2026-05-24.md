# AcctBox 域名生效异常复盘

## 背景

AcctBox 已完成：

```text
Cloudflare Workers Static Assets
Worker API
D1 数据库
远程部署
workers.dev 访问
D1 发卡 smoke
```

随后绑定正式域名：

```text
acctbox.eforge.xyz
```

绑定后出现了长时间验证和多次尝试。本文说明到底是哪一层出了问题、是否走弯路、脚本还有哪些边界。

## 先给结论

没有在 Workers、D1、代码部署、D1 migration、seed、Worker custom domain API 这些核心链路上走错。

当时真正卡住的是：

```text
acctbox.eforge.xyz 默认 DNS/边缘解析路径的 TLS 握手暂态异常。
```

后续用户在浏览器中可以访问，随后命令行也恢复正常：

```text
https://acctbox.eforge.xyz/ -> HTTP/2 200
GET https://acctbox.eforge.xyz/api/health -> ok=true, service=acctbox, storage=d1
BASE_URL=https://acctbox.eforge.xyz npm run verify -> passed
BASE_URL=https://acctbox.eforge.xyz npm run smoke -> passed
```

因此最终判断需要修正为：

```text
Cloudflare 绑定、证书、Worker、D1 都是正常的。
早期 CLI 失败更可能来自域名刚绑定后的生效窗口、边缘路径暂态、或命令行环境与浏览器代理/DNS 路径不一致。
```

证据显示主链路没有错：

```text
1. Worker 已部署成功。
2. workers.dev 地址可访问。
3. D1 /api/health 正常。
4. D1 发卡 smoke 正常。
5. Workers Custom Domain API 显示 acctbox.eforge.xyz 已 enabled。
6. Cloudflare DNS 已生成只读 AAAA 100:: 记录。
7. 强制解析到已验证可用的 Cloudflare 边缘 IP 后，acctbox.eforge.xyz 可访问并能通过 D1 smoke。
```

所以问题不在：

```text
代码
Worker deploy
D1 database_id
D1 migration
D1 seed
Worker service 名称
Workers Custom Domain API
```

当时问题表现为：

```text
默认解析路径 acctbox.eforge.xyz -> 198.18.0.171 的 TLS 握手失败。
```

但该表现已经恢复，不能再把它作为当前故障状态。

## 时间线和证据

### 1. Worker 默认域名可用

验证：

```text
https://acctbox.mailforwdy.workers.dev -> HTTP/2 200
GET /api/health -> ok=true, service=acctbox, storage=d1
```

说明：

```text
Worker、Static Assets、D1 binding、D1 数据库都是可用的。
```

### 2. D1 远程链路可用

远程 D1：

```text
database_name: acctbox-db
database_id: c72de869-1e66-4dfe-81fc-4fdec552aba4
region: WNAM
```

已验证：

```text
remote migration applied
remote seed applied
remote smoke passed
```

说明：

```text
database_id 获取和写入正确。
D1 migration/seed 顺序正确。
D1 发卡业务逻辑可用。
```

### 3. 正式域名绑定成功

绑定命令：

```bash
CF_AUTH_EMAIL="<cloudflare-email>" \
CF_GLOBAL_API_KEY="<global-api-key>" \
CF_WORKER_SERVICE="acctbox" \
CF_CUSTOM_DOMAIN="acctbox.eforge.xyz" \
npm run domain:bind
```

返回：

```text
Bound Workers custom domain: acctbox.eforge.xyz -> acctbox
```

Cloudflare Workers custom domain 查询：

```text
hostname: acctbox.eforge.xyz
service: acctbox
environment: production
enabled: true
cert_id: 020a6877-7526-4c1c-af83-7da62ca57afc
```

Cloudflare DNS 查询：

```text
name: acctbox.eforge.xyz
type: AAAA
content: 100::
proxied: true
meta.read_only: true
```

说明：

```text
Workers Custom Domain 绑定已经成功。
只读 AAAA 100:: 是 Workers Custom Domain 的正常形态。
这不是应该手动改 CNAME 的场景。
```

### 4. 默认访问失败

默认 curl：

```text
https://acctbox.eforge.xyz -> SSL_ERROR_SYSCALL
```

详细 curl：

```text
Host acctbox.eforge.xyz:443 was resolved.
IPv4: 198.18.0.171
Connected to acctbox.eforge.xyz (198.18.0.171) port 443
TLS handshake, Client hello
LibreSSL SSL_connect: SSL_ERROR_SYSCALL
```

说明：

```text
域名解析到了一个 Cloudflare/本地网络路径给出的边缘地址，但 TLS 握手失败。
```

### 5. 强制可用边缘 IP 后成功

对比 `ai.eforge.xyz`：

```text
ai.eforge.xyz -> 198.18.0.131
https://ai.eforge.xyz -> HTTP/2 200
```

强制 `acctbox.eforge.xyz` 使用同一可用边缘 IP：

```bash
rtk curl -sS \
  --resolve acctbox.eforge.xyz:443:198.18.0.131 \
  https://acctbox.eforge.xyz/api/health
```

返回：

```text
ok=true
service=acctbox
storage=d1
```

脚本化验证：

```bash
RESOLVE_IP="198.18.0.131" \
BASE_URL="https://acctbox.eforge.xyz" \
npm run verify
```

返回：

```text
Verify 1/6: https://acctbox.eforge.xyz/ -> HTTP 200
AcctBox verify passed
```

发卡 smoke：

```bash
RESOLVE_IP="198.18.0.131" \
BASE_URL="https://acctbox.eforge.xyz" \
npm run smoke
```

返回：

```text
AcctBox smoke passed: f2018aed-6759-4e80-b480-bd7805e7624c -> pro-demo-002
```

说明：

```text
同一个 hostname，同一个 Worker，同一个 D1，只要换到可用边缘路径就正常。
这证明 Worker/D1/域名绑定本身不是根因。
```

### 6. 浏览器和命令行后来都恢复正常

用户反馈：

```text
浏览器可以访问 https://acctbox.eforge.xyz/
```

随后命令行复测：

```text
rtk curl -sS -I https://acctbox.eforge.xyz/ -> HTTP/2 200
rtk curl -sS https://acctbox.eforge.xyz/api/health -> ok=true, service=acctbox, storage=d1
BASE_URL=https://acctbox.eforge.xyz npm run verify -> passed
BASE_URL=https://acctbox.eforge.xyz npm run smoke -> passed
```

这说明早期失败不是长期配置错误，而是暂态访问路径差异。

需要特别记录：

```text
浏览器和 CLI 不一定走同一条网络路径。
浏览器可能使用系统代理、浏览器代理扩展、DoH、连接复用或不同 DNS 缓存。
CLI 可能不使用浏览器代理，也可能被 sandbox、DNS、网络策略影响。
```

本次检查：

```text
curl --proxy http://127.0.0.1:7890 https://acctbox.eforge.xyz/ -> HTTP/2 200
普通 curl 后续也 -> HTTP/2 200
scutil --proxy -> 当前命令行环境未显示系统代理配置
```

因此“7890 代理”是一个合理怀疑因素，但不是唯一证据。更准确的说法是：

```text
早期 CLI 失败很可能是本地命令行网络路径、DNS/边缘路径、生效窗口之间的暂态差异。
浏览器可访问证明 Cloudflare 侧配置已经成功。
```

## 是否走了弯路

### 没有走错的部分

以下判断是必要且正确的：

```text
1. 先验证 workers.dev。
2. 再验证 /api/health。
3. 再验证 D1 smoke。
4. 再查 Workers custom domains API。
5. 再查 DNS record。
6. 再区分 Workers Custom Domain 和 Pages CNAME。
```

如果不做这些检查，很容易误判为：

```text
代码没部署好
D1 database_id 错
DNS 应该手动改 CNAME
Cloudflare 域名没绑定
```

这些判断都会导致继续走错方向。

### 确实可以改进的部分

之前不够好的地方：

```text
1. D1 create、database_id 写入、migrate、seed、deploy、smoke 一开始是临时命令，不是脚本。
2. Worker custom domain 脚本最早只绑定域名，没有等待 HTTPS 可达。
3. 正式域名失败时，缺少脚本化的 RESOLVE_IP 排障能力。
4. 文档没有立即把“绑定成功但默认边缘路径失败”的情况写成明确分层。
```

现在已经补齐：

```text
acctbox/scripts/deploy-full.mjs
acctbox/scripts/verify-domain.mjs
acctbox/scripts/smoke.mjs 支持 RESOLVE_IP
scripts/cloudflare/workers_custom_domain_bind.mjs 支持绑定后 HTTPS 轮询
```

## 当前脚本是否已经最完美

不是“最完美”，但已经从临时命令升级到了可复用闭环。

现在已经具备：

```text
1. D1 database_id 自动提取和写入。
2. 远程 migration。
3. 可选远程 seed。
4. Worker deploy。
5. 可选 Workers custom domain bind。
6. 绑定后 HTTPS 轮询。
7. workers.dev smoke。
8. 正式域名 verify。
9. RESOLVE_IP 排障。
10. 中文入口注释和文档记录。
```

仍然可以继续增强：

```text
1. deploy-full 可以自动查询 Workers custom domain API 并输出 domain id、cert_id、DNS record id。
2. verify-domain 可以自动对比多个 Cloudflare 边缘 IP，而不是手动传 RESOLVE_IP。
3. smoke 可以支持只读模式，避免每次消耗库存。
4. seed 可以拆成 demo seed 和补库存 seed。
5. 可以增加 scripts/diagnose-domain.mjs，专门输出 API 绑定、DNS 记录、默认解析、HTTPS、workers.dev 对比。
```

是否现在必须做这些增强：

```text
不是必须。
当前主链路已经能部署、绑定、验证、记录故障。
但如果后续要批量做 Worker custom domain，建议优先补 diagnose-domain.mjs 和只读 smoke。
```

## 下次遇到域名不通时的标准判断流程

不要一上来改 DNS，也不要重建 Worker。

顺序必须是：

```text
1. curl workers.dev。
2. curl workers.dev /api/health。
3. 查 Workers custom domains API。
4. 查 Cloudflare DNS record。
5. 确认是否是 read_only AAAA 100::。
6. curl 正式域名。
7. 如果 TLS 失败，记录默认解析 IP。
8. 用已验证可用边缘 IP 做 --resolve 对比。
9. 如果 --resolve 成功，说明 Worker/D1/绑定没错，问题在默认解析/边缘路径。
10. 等待或继续做域名路径专项排查，不要改业务代码。
```

## 最终判断

这次不是 D1 或 Worker 配置错误，也不是 Pages/Workers 流程混淆。

真正的问题是早期验证阶段出现：

```text
Workers Custom Domain 已绑定成功，但 acctbox.eforge.xyz 默认解析到的边缘路径一度 TLS 握手失败。
```

现在已确认：

```text
acctbox.eforge.xyz 默认访问已恢复 HTTP/2 200。
verify 和 smoke 已通过。
```

我们没有在主架构上走错，但前期缺少自动化脚本和分层诊断，导致用了较多手工命令确认问题边界。也需要承认，最初把 CLI 失败描述为“默认解析路径异常”时，还没有把“浏览器代理/DNS 路径与 CLI 不一致”充分纳入判断。

现在已经把临时操作固化为：

```text
npm run deploy:full
npm run verify
npm run smoke
npm run domain:bind
```

并把排障路径写入文档。后续不应再为 D1 create、database_id、remote seed、Worker deploy、custom domain bind 这些环节重复摸索。
