# AI 接管部署、域名、运维最佳实践

日期：2026-05-24

## 先解释清楚：Workers 不是“没部署好”

当前线上地址：

```text
https://gptsession2cpaandsub2api.mailforwdy.workers.dev/
```

已经部署成功，并且可以访问。

“当前正确主线是 Workers，不是 Pages”的意思是：

- Cloudflare 有多个部署产品。
- `*.workers.dev` 是 Workers 的默认域名。
- `*.pages.dev` 是 Pages 的默认域名。
- 通过 Cloudflare API 查询，当前账号下 Pages projects 为空。
- 通过 Cloudflare API 查询，Workers scripts 中存在 `gptsession2cpaandsub2api`。

所以不是说项目没上线，而是说它现在上线在 Workers 产品线上。后续自动更新、域名绑定、运维都应该围绕 Workers 做，不要再按 Pages 的配置项推进。

这条链路已经实测跑通。

### 仍需注意

当前 token 查询以下接口失败：

- Zone DNS records。
- Workers routes。

即使已经为 token 开放了较多权限，这两个接口仍返回认证错误。这通常说明权限没有落到正确资源范围上，例如 token 有 Account 级权限，但没有对应 Zone 的 DNS/Workers Routes 权限；或者 token 资源范围没有包含这些 zone。

结论：

```text
部署能力：基本可接管
域名绑定：已通过 Workers Custom Domains API 接管
DNS 底层记录直读：仍缺权限或接口范围不匹配
```

这是当前项目的正式运维入口。技术规则保持不变：

- 保留 `workers.dev` 作为回退访问地址。

### 第 4 层：DNS 和路由运维

AI 要完整接管域名绑定，需要 Cloudflare token 至少具备：

```text
Account - Workers Scripts: Edit
Account - Workers Builds Configuration: Edit 或同等 Workers CI/CD 权限
Zone - Zone Settings: Read
Zone - DNS: Edit
Zone - Workers Routes: Edit
```

如果只希望 AI 读状态，不允许改 DNS：

```text
Zone - DNS: Read
Zone - Workers Routes: Read
```

当前 token 能读 zones，并且能写入 Workers Custom Domain；但不能读 DNS records/routes。因此对本项目域名绑定已经够用，对完整 DNS 运维还不够。

## 域名绑定的推荐方式

### 方案 A：AI 用 Workers Custom Domains API 绑定域名

这是当前项目已经跑通的方案。

命令模板：

```bash
CLOUDFLARE_API_TOKEN=<token> rtk curl -sS -X PUT "https://api.cloudflare.com/client/v4/accounts/<account_id>/workers/domains" \
  -H "Authorization: Bearer ${CLOUDFLARE_API_TOKEN}" \
  -H "Content-Type: application/json" \
  --data '{"environment":"production","hostname":"ai.eforge.xyz","service":"gptsession2cpaandsub2api","zone_id":"<zone_id>"}'
```

成功响应必须包含：

```text
hostname: ai.eforge.xyz
service: gptsession2cpaandsub2api
environment: production
enabled: true
```

绑定后验证：

```bash
rtk curl -I https://ai.eforge.xyz/
rtk curl -sS https://ai.eforge.xyz/ | rtk rg "custom-domain-smoke"
```

### 方案 B：Dashboard 首次绑定，AI 后续维护

这是 API 不可用或权限不足时的兜底方案。

步骤：

1. 打开 Cloudflare Dashboard。
2. 进入 `Workers & Pages`。
3. 打开 Worker：

```text
gptsession2cpaandsub2api
```

4. 进入 `Settings`。
5. 找到 `Domains & Routes`。
6. 添加 Custom Domain 或 Route。
7. 选择已有 zone，例如：

```text
593206.xyz
eforge.xyz
joinai.dpdns.org
```

8. 绑定一个子域名。
9. 保存后访问测试。

优点：

- 首次配置风险低。
- 不需要一开始给 AI 高权限 DNS token。
- Cloudflare UI 会处理很多边界提示。

缺点：

- 首次动作需要人操作。

### 方案 C：Workers Route

只在需要路径级路由时使用，例如把 `example.com/tool/*` 指到 Worker。

当前项目是完整子域名入口，优先使用 Custom Domain，不使用 Route。

原因：Custom Domain 更简单，证书和 DNS 托管路径更清晰，适合个人创业者快速上线和长期维护。

## 推荐 API Token 策略

不要把所有权限塞进一个长期 token。

即使为了调试临时创建了高权限 token，也建议用完后删除或轮换。高权限 token 一旦出现在聊天、日志、shell history 或 MCP 配置中，就应视为已经泄露。

建议分三个 token：

### 1. Deploy Token

用途：部署 Worker。

权限：

```text
Account - Workers Scripts: Edit
Account - Account Settings: Read
```

使用位置：

- GitHub Actions。
- 本地临时 Wrangler deploy。

### 2. Readonly Ops Token

用途：AI 读取状态、列项目、查日志。

权限：

```text
Account - Workers Scripts: Read
Zone - DNS: Read
Zone - Zone Settings: Read
```

使用位置：

- 日常检查。
- 自动化诊断。

### 3. Domain Ops Token

用途：域名、DNS、routes 变更。

权限：

```text
Zone - DNS: Edit
Zone - Workers Routes: Edit
Zone - Zone Settings: Read
```

使用方式：

- 只在绑定域名或迁移域名时临时启用。
- 用完轮换或删除。

## AI 运维的边界

AI 可以自动做：

- 修改代码。
- 同步文档。
- 提交 Git。
- 推送 GitHub。
- 触发 Cloudflare 自动部署。
- 读取线上响应。
- 读取 Workers 状态。
- Wrangler dry-run。
- Wrangler deploy 兜底。
- 写踩坑记录。

AI 不应该无确认自动做：

- 删除 Worker。
- 删除 zone。
- 修改根域名 DNS。
- 覆盖已有业务域名。
- 关闭安全头。
- 放开 `connect-src`。
- 提交或保存 token。

## 有效部署方案

### 推荐主路径：Workers Builds

当前已经证明：

```text
git push origin main -> Cloudflare Worker 自动更新
```

后续继续使用 Workers Builds 作为主路径。

推荐配置：

```text
Worker: gptsession2cpaandsub2api
Repository: qwdingyu/GPTSession2CPAandSub2API
Branch: main
Deploy command: npx wrangler deploy
Config file: wrangler.jsonc
Static assets: src
```

优点：

- 不需要把 Cloudflare token 放进 GitHub Secrets。
- Cloudflare 自己管理 GitHub 连接和部署权限。
- 每次部署能关联 Git commit。
- AI 只需要负责代码、文档、commit、push 和验证。

### 可控替代：GitHub Actions + Wrangler

如果 Workers Builds 不稳定，才考虑 GitHub Actions。

需要 GitHub Secret：

```text
CLOUDFLARE_API_TOKEN
```

workflow 核心命令：

```bash
npm exec wrangler -- deploy
```

缺点：

- 需要在 GitHub 保存 Cloudflare token。
- secret 权限和轮换要额外维护。
- 对个人项目不是首选。

### 手动兜底：本地 Wrangler

当 GitHub 或 Cloudflare 自动构建异常时使用：

```bash
CLOUDFLARE_API_TOKEN=<token> rtk proxy npx wrangler deploy
```

使用后必须写踩坑记录，说明为什么绕过主路径。

## 域名、HTTPS 和路由

### HTTPS

Cloudflare Workers 的 `workers.dev` 默认已经提供 HTTPS。

绑定自定义域名后，只要域名托管在 Cloudflare zone，Cloudflare 会自动签发和托管 HTTPS 证书。一般不需要自己申请证书。

验收命令：

```bash
rtk curl -I https://ai.eforge.xyz/
```

重点检查：

```text
HTTP/2 200
server: cloudflare
content-security-policy
```

### 选择 Custom Domain 还是 Route

Cloudflare 官方建议：

- 如果 Worker 本身就是应用 origin，优先用 Custom Domain。
- 如果 Worker 是挂在已有网站前面的一段路径或代理逻辑，用 Route。

当前项目是一个独立静态工具，推荐：

```text
Custom Domain
```

例如：

```text
ai.eforge.xyz
```

不建议一开始绑定根域名。

### DNS 记录

如果用 Custom Domain，Cloudflare Dashboard 通常会自动处理所需 DNS/证书流程。

如果用 Route，则必须先有一个 proxied DNS 记录，再把 route pattern 指向 Worker。

示例 route pattern：

```text
tools.example.com/*
```

但当前项目更适合 Custom Domain，不建议用 Route 作为首选。

## 官方 MCP 和开源工具

### Cloudflare 官方 MCP

Cloudflare MCP 相关能力可以作为辅助查询和诊断工具，但不应替代官方文档、Wrangler 配置、GitHub commit 和 curl 验证。

官方仓库：

```text
cloudflare/mcp-server-cloudflare
```

建议用途：

- 查询 Cloudflare 最新文档。
- 查询 Workers、DNS、R2、KV、D1 等资源。
- 辅助生成变更计划。
- 读取配置并做安全审查。

注意事项：

- MCP 使用的 token 权限越大，风险越大。
- 不建议把高权限 token 长期给 MCP。
- 推荐先用 Readonly Ops Token。
- 真正改 DNS/域名时，临时启用 Domain Ops Token。

### Wrangler

Wrangler 是当前最重要的官方 CLI。

适合：

- `wrangler deploy`
- `wrangler deploy --dry-run`
- 查看/管理 Worker。
- 管理 KV/R2/D1 等绑定。

本项目必须保留：

```text
wrangler.jsonc
```

这样 AI、Wrangler、Workers Builds 都有同一个部署配置事实源。

### GitHub CLI

`gh` 负责 GitHub 侧：

- 仓库。
- PR。
- Actions。
- Secrets。
- commit/check 状态。

Cloudflare 不应该取代 GitHub；GitHub 是代码事实源，Cloudflare 是运行平台。

### 开源项目

不建议为当前项目引入第三方开源部署平台。

原因：

- 当前项目是单 HTML 静态工具。
- Wrangler + Workers Builds 已经足够。
- 第三方平台会增加 token 面、权限面和维护成本。
- 个人创业者优先使用官方工具，降低长期运维负担。

## 当前推荐决策

对这个项目，最优方案是：

```text
Workers Builds 做自动部署
Wrangler 做配置事实源和兜底
GitHub 做代码事实源
Workers Custom Domains API 做正式子域名绑定
Cloudflare MCP 做只读诊断和文档查询
高权限 API token 只短期使用，之后轮换
```

这比自己写一堆部署脚本更稳，也比引入第三方自动化平台更符合“小而美瑞士军刀”的原则。
