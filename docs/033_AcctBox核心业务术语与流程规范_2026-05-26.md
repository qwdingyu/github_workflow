## 一、术语铁律

以下术语在本项目中**有且仅有一种含义**，任何人不得用其他名称替代，不得赋予其他含义。

### 1.1 数据实体（对应 DB 表）

| 统一术语 | DB 表名 | 代码变量名 | 含义 | 绝对禁止叫法 |
|---------|---------|-----------|------|------------|
| **商品** | `products` | `product` | 可购买的数字权益，有价格、库存、分类 | 产品、项目 |
| **卡密** | `cards` | `card` | 商品的交付物，一条账号+密码/密钥 | 卡号、密钥、激活码 |
| **订单** | `orders` | `order` | 一次购买行为的完整记录 | 交易、记录 |
| **折扣码** | `coupons` | `coupon` | 价格调节器——调整应付金额（打折/抵扣/免单） | ❌ 禁止叫"兑换码"、"领卡码"、"优惠码" |
| **活动** | `campaigns` | `campaign` | 营销来源追踪标记 | — |
| **推荐码** | `referral_codes` | `referral` | 裂变推荐来源追踪 | — |

### 1.2 订单状态（orders.status）

| 状态值 | 统一叫法 | 含义 | 可发生场景 |
|--------|---------|------|----------|
| `pending` | **待确认** | 订单已创建，等待付款确认或管理员确认 | 线下购买 / 在线支付未付款 |
| `paid` | **已付款** | 付款已确认（在线支付回调或管理员确认），等待发卡 | 在线支付回调后 / 管理员标记 |
| `issued` | **已发卡** | 卡密已分配给订单，交付完成 | 自动发卡 / 管理员确认发卡 |
| `expired` | **已过期** | 订单超时未付款，自动作废 | 超时未付款 |
| `cancelled` | **已取消** | 管理员手动取消 | — |
| `refunded` | **已退款** | 管理员标记退款 | — |

### 1.3 商品发卡模式（products.issue_mode）

| 值 | 统一叫法 | 含义 | 付款后行为 |
|----|---------|------|----------|
| `direct` | **自动发卡** | 付款确认后系统自动分配卡密 | 不需要管理员操作 |
| `manual` | **人工发卡** | 付款确认后需管理员在后台点"确认发卡" | 管理员手动触发 |
| `webhook` | **Webhook 发卡** | 付款确认后通知外部系统 | 外部系统处理 |

### 1.4 支付方式（orders.payment_method）

| 值 | 统一叫法 | 含义 |
|----|---------|------|
| `online` | **在线支付** | 用户扫支付二维码，支付平台回调确认（具体平台由配置决定） |
| `offline` | **线下转账** | 用户向管理员线下转账，管理员确认收款 |
| `""` (空) | **折扣码免单** | 折扣码 100% 抵扣，无需付款 |

> ⚠️ `payment_method` 的值 `online` 是支付平台无关的。具体对接哪个支付平台（虎皮椒、Stripe 等）由后端环境变量和系统配置决定，不在订单记录中体现。

### 1.5 核心禁令

> ⚠️ **"兑换码"这个词在本项目中永久废弃。**

- 之前把 `coupons` 叫"兑换码"导致了严重的概念混乱
- `coupons` 的唯一正确叫法是**折扣码**
- 用户端输入折扣码的 Tab 叫**"折扣码"**，不叫"兑换"
- 折扣码可以是 100% 折扣（免单），但本质仍然是价格调节器，不是"领卡通行证"

> ⚠️ **PayJS 已爆雷，不可使用。文档和代码中不再以 PayJS 为推荐方案。**

- 032 文档（PayJS 推荐方案）已标记废弃
- 代码中 `payjs-sign.ts` / `pay.ts` 中 PayJS 相关逻辑暂时保留但不启用，待替换为新的在线支付平台
- `PAYJS_MCHID` / `PAYJS_KEY` 环境变量保留但不配置，后续替换为新平台的密钥配置

## 二+1、查询系统设计（邮箱为唯一入口）

> **2026-05-26 新增｜此节为铁律**
>
> ⚠️ 废弃 `require_email` 参数，**邮箱强制必填**，作为订单查询的唯一入口。

### 2+1.1 设计原则

用户记不住 orderToken（长 UUID），也记不住订单号（`OXXXXX`）。用户唯一记得的是自己的邮箱。

**邮箱是查询的唯一入口。** 行业最佳实践（Steam、京东卡密、闲鱼）均如此。

### 2+1.2 查询流程

```
用户访问查询页
    → 输入邮箱（唯一入口）
    → 后端返回该邮箱所有订单（倒序，最多 10 笔，不含卡密）
    → 前端展示订单列表（订单号 + 商品名称 + 购买时间 + 状态）
    → 用户点击某笔订单 → 查看卡密详情
```

### 2+1.3 订单列表内的过滤和排序

| 过滤/排序维度 | 实现方式 |
|--------------|---------|
| 按订单号精确过滤 | 顶部搜索框，输入 `OXXXXX` → 前端内存实时筛选 |
| 按商品名称过滤 | 顶部搜索框，输入商品名 → 前端内存实时筛选 |
| 按时间倒序 | 默认，最新购买的在最上面 |

> ⚠️ **过滤是列表内前端操作，不需要新增 API 端点。** 后端一次性返回 10 笔，前端内存过滤。

### 2+1.4 业务边界条件

| 情况 | 行为 |
|------|------|
| `require_email=true` 时期创建的订单 | `buyer_email` 有值，邮箱查询正常返回 |
| `require_email=false` 时期创建的历史订单 | `buyer_email` 可能为空，**这些订单永远无法用邮箱查到**，只能靠 orderToken 人工找回 |
| 邮箱查到 2+ 笔订单 | 返回列表，用户选择其中一笔 |
| 邮箱查到 0 笔订单 | 返回空列表 `[]`（不是 404），前端展示引导文案 |

## 二、当前唯一的业务主线：线下购买

支付通道未打通前，系统只有一条购买路径：

### 线下购买流程

```
用户在商店选商品 → 点击"线下购买" → 创建 pending 订单
    → 系统展示收款码 + 付款备注（订单号后6位）
    → 用户线下转账给管理员
    → 管理员在后台看到 pending 订单 → 确认收款 → 点击"确认发卡"
    → 系统自动分配卡密 → 用户端实时看到卡密
```

### 在线支付流程（支付通道打通后启用）

```
用户在商店选商品 → 点击"立即购买" → 创建 pending 订单
    → 系统展示支付二维码
    → 用户扫码付款
    → 支付平台回调确认付款 → 系统自动发卡（direct 模式）
                              或 等管理员确认发卡（manual 模式）
    → 用户端实时看到卡密
```

> 在线支付的具体平台待选定，不再预绑 PayJS。

### 两条路径的关系

| 维度 | 线下购买（当前启用） | 在线支付（待打通） |
|------|---------------------|-------------------|
| **当前状态** | ✅ 立即实现 | 🔲 支付通道打通后启用 |
| **payment_method** | `offline` | `online` |
| **付款确认方式** | 管理员手动确认 | 支付平台回调自动确认 |
| **前端按钮文字** | "线下购买" | "立即购买" |
| **订单初始状态** | `pending` | `pending` |
| **前端轮询** | ✅ `/api/pay/status/:orderId` | ✅ `/api/pay/status/:orderId` |
| **发卡触发** | 管理员点"确认发卡" | 支付回调 / 管理员确认 |
| **是否需要折扣码** | 可选（独立概念） | 可选（独立概念） |
| **在线支付打通后** | 保留作为备选支付方式 | 作为默认支付方式 |

## 四、折扣码与支付方式的关系（消除最大的混淆源）

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│   折扣码 (coupon) 和 支付方式 (payment_method)          │
│   是两个正交的、独立的维度。                             │
│                                                         │
│   折扣码 = 价格调节器                                   │
│   支付方式 = 付款通道                                   │
│                                                         │
│   任何支付方式都可以叠加任何折扣码。                     │
│                                                         │
│            │ 无折扣码  │ 有折扣码(部分) │ 有折扣码(100%) │
│   ─────────┼──────────┼───────────────┼────────────────│
│   线下转账  │ 付全款   │ 付折扣后金额   │ 免单，无需付款 │
│   在线支付  │ 付全款   │ 付折扣后金额   │ 免单，无需付款 │
│                                                         │
│   100% 折扣码 ≠ "领卡码" ≠ "兑换码"                    │
│   100% 折扣码 = 价格为 0 的折扣码                       │
│   仍然走正常下单流程，只是 payableCents = 0             │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 当前代码中折扣码的参与方式

| 入口 | 折扣码参与 | 代码位置 |
|------|----------|---------|
| `POST /api/orders`（折扣码 Tab） | **必须**——折扣码是创建订单的必要条件 | `orders.ts` → `createOrder()` |
| `POST /api/pay/order`（购买 Tab→在线支付） | **可选**——折扣码可降低支付金额 | `pay.ts` → `quoteCoupon()` |
| `POST /api/pay/offline`（购买 Tab→线下） | **可选**——折扣码可降低应付金额 | 待实现 |

### ⚠️ 当前代码的问题

当前 `POST /api/orders` 把折扣码当作**必填字段**（`couponCode: z.string().trim().min(2)`），这导致：

1. 用户必须输入折扣码才能下单——这是 V1 的遗留设计（当时没有支付能力，折扣码充当"门禁"）
2. V2 有了线下购买和在线支付后，折扣码应该是**可选的**
3. 线下购买路径中，用户选商品→点"线下购买"→创建订单，**不需要折扣码**

**修复方向**：`POST /api/orders` 的 `couponCode` 改为可选；线下购买走 `POST /api/pay/offline`，不需要折扣码。
