| 差异维度 | 说明 |
|---------|------|
| **前端策略** | eshop 用 Vue3+Vite 构建；xtools/vcode 用原生 HTML/JS。管理端三者一致（Vue3+EP CDN） |

## 三、行业最佳实践参考

### 3.1 Monorepo vs Multi-repo vs Template

| 方案 | 代表项目 | 适用场景 | 优缺点 |
|------|---------|---------|--------|
| **Monorepo** (Turborepo/Nx) | Vercel, Supabase | 多包共享、原子变更 | 优：共享代码方便；缺：仓库膨胀、CI 慢 |
| **Multi-repo + npm 包** | Stripe, Twilio | 独立版本、独立部署 | 优：解耦；缺：跨包变更难 |
| **Template + Fork** | Astro themes, Laravel Starter | 快速启动同类产品 | 优：起步快；缺：模板更新难同步 |
| **共享内核 + 插件** (推荐) | WordPress, VS Code | 核心稳定 + 业务灵活 | 优：兼顾复用和独立；缺：需要前期设计 |

### 3.2 Cloudflare 官方推荐模式

根据 Cloudflare 官方文档和社区最佳实践：

1. **Workers + Static Assets 一体化部署**（三者均已采用）
2. **Cache API 优先**：Free 套餐 Cache API 不计入 10 万请求配额，是最关键的优化手段
3. **Isolate 级连接复用**：数据库连接在模块级别缓存，不在每请求创建
4. **Cron Trigger 替代**：Free 不支持 Cron，用 GHA 定时调 API 或惰性清理
5. **Wrangler 配置即代码**：`wrangler.jsonc` / `wrangler.toml` 版本化

### 3.3 SaaS 产品工厂化最佳实践

| 实践 | 来源 | 说明 |
|------|------|------|
| **Core + Plugin 架构** | WordPress / Saleor | 核心提供基础设施（认证、限流、安全），业务以插件形式扩展 |
| **Convention over Configuration** | Rails / Next.js | 约定目录结构和命名，减少配置 |
| **Starter Kit 模式** | Shopify Hydrogen / Medusa.js | 提供可运行的起步模板，开发者只改业务层 |
| **Feature Flag 驱动** | LaunchDarkly / Unleash | 通过开关控制功能启用，一份代码多个产品 |
| **Schema-driven 代码生成** | Prisma / Hasura | 从数据模型生成 API、类型、管理后台 |

## 四、推荐方案：三层架构体系

基于三项目的实际代码分析和行业最佳实践，推荐采用 **"共享内核 + 产品模板 + 业务插件"** 的三层架构：

```
┌──────────────────────────────────────────────────────┐
│                   新项目（如 xshop）                    │
│  ┌────────────────────────────────────────────────┐  │
│  │          Layer 3: 业务插件 (改这里)              │  │
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐          │  │
│  │  │ 商品模块 │ │ 支付模块 │ │ 邮件模块 │  ...     │  │
│  │  └─────────┘ └─────────┘ └─────────┘          │  │
│  └────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────┐  │
│  │          Layer 2: 产品模板 (选一个)              │  │
│  │  ┌──────────┐ ┌──────────┐ ┌──────────┐       │  │
│  │  │ cf-shop  │ │ cf-tools │ │ cf-api   │       │  │
│  │  │ 发卡商城  │ │ 工具集   │ │ API 服务  │       │  │
│  │  └──────────┘ └──────────┘ └──────────┘       │  │
│  └────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────┐  │
│  │          Layer 1: 共享内核 (不动)                │  │
│  │  ┌─────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ │  │
│  │  │http │ │security│ │rate  │ │cache │ │db    │ │  │
│  │  │utils│ │utils  │ │limit │ │api   │ │layer │ │  │
│  │  └─────┘ └──────┘ └──────┘ └──────┘ └──────┘ │  │
│  │  ┌──────────────────────────────────────────┐  │  │
│  │  │ Worker Bootstrap (入口+中间件+路由分发)   │  │  │
│  │  └──────────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### 4.1 Layer 1：共享内核 — `@eforge/cf-core`

**定位**：所有 Cloudflare Workers 项目的基础设施层，以 npm 包（或 monorepo 内部包）形式提供。

**包含模块**：

| 模块 | 来源 | 功能 |
|------|------|------|
| `http` | 三项目 `lib/http.ts` 合并 | `ok()`/`fail()`/`safeJsonBody()`/`maskContact()` |
| `security` | 三项目 `lib/security.ts` 合并 | IP 哈希、timingSafeEqual、Turnstile 验证、安全响应头生成 |
| `rate-limit` | eshop 的 DB 版 + xtools 的 KV 版 | 统一接口，可选存储后端（DB / KV / 内存） |
| `idempotency` | eshop `lib/idempotency.ts` | 原子 UPSERT + 哨兵值 |
| `cache` | eshop `lib/cache.ts` | Workers Cache API 命名空间封装 |
| `db` | 三项目 `db/` 合并 | libSQL 连接工厂 + Isolate 级缓存 + Drizzle 实例管理 |
| `auth` | xtools `lib/auth.ts` 提取 | JWT 签发/验证、PBKDF2 密码哈希（纯 Web Crypto） |
| `crypto` | xtools `lib/crypto.ts` 提取 | AES-256-GCM 加解密 |
| `audit` | 三项目 `audit-service.ts` 合并 | 审计日志写入（fire-and-forget） |
| `config` | 三项目 `system_config` 合并 | 运行时 KV 配置（热生效） |
| `error` | xtools `error-classifier.ts` 提取 | 错误分类 + 指数退避重试 |
| `logger` | vcode `lib/logger.ts` 提取 | 结构化 JSON 日志 |
| `bootstrap` | 三项目 `index.ts` 提取 | Worker 入口模板（路由分发 + CSP + 安全头 + 静态资源优先级） |

**目录结构**：

```
packages/cf-core/
├── package.json
├── tsconfig.json
├── src/
│   ├── index.ts              # 统一导出
│   ├── http.ts
│   ├── security.ts
│   ├── rate-limit.ts
│   ├── idempotency.ts
│   ├── cache.ts
│   ├── db/
│   │   ├── connection.ts     # libSQL 连接工厂
│   │   ├── drizzle.ts        # Drizzle 实例管理
│   │   └── schema.ts         # 公共表定义（system_config, audit_logs, rate_limit_windows, idempotency_keys, api_keys）
│   ├── auth/
│   │   ├── jwt.ts
│   │   ├── password.ts
│   │   └── api-key.ts
│   ├── crypto.ts
│   ├── audit.ts
│   ├── config.ts
│   ├── error.ts
│   ├── logger.ts
│   └── bootstrap.ts          # Worker 入口工厂
└── tests/
```

**分发策略**：

| 阶段 | 方案 | 说明 |
|------|------|------|
| **短期（推荐）** | Git submodule 或 monorepo 内部引用 | 零发布成本，直接引用 |
| **中期** | 私有 npm registry（GitHub Packages） | 版本化，多团队共享 |
| **长期** | 开源 + 社区维护 | 如果生态成熟 |

## 七、Cloudflare Free 套餐下的关键优化策略

基于三项目的实践经验和 eshop 评审报告（文档 045），总结 Free 套餐下的核心优化策略：

### 7.1 请求配额优化（10 万次/天）

| 策略 | 效果 | 实现方式 |
|------|------|---------|
| **Cache API 缓存** | 减少 60-80% 的 API 请求 | `@eforge/cf-core/cache` 封装 |
| **静态资源 Edge Cache** | 减少 80-90% 的静态请求 | `Cache-Control: immutable, max-age=31536000` |
| **SPA 路由优化** | 避免 `run_worker_first` 消耗 | 仅对 `/api/*` 启用 Worker 优先 |
| **Isolate 级连接复用** | 减少 DB 连接开销 | `@eforge/cf-core/db` 自动管理 |
| **批量操作** | 减少请求次数 | 批量生成/批量查询 |

### 7.2 CPU 时间优化（10ms/请求）

| 策略 | 效果 | 实现方式 |
|------|------|---------|
| **Hono 框架** | 冷启动 ~5ms | 已选型 |
| **预计算 CSP** | 减少字符串拼接 | 预生成 admin/non-admin CSP 头 |
| **异步日志** | 不阻塞响应 | fire-and-forget 审计日志 |
| **惰性清理** | 分散清理开销 | 每请求异步清理过期资源 |

### 7.3 Cron 替代方案

| 方案 | 适用场景 | 实现方式 |
|------|---------|---------|
| **GHA 定时调 API** | 定时清理、健康检查 | `.github/workflows/cleanup-schedule.yml` |
| **惰性清理** | 过期订单/凭证/Token | 每请求异步检查并清理 |
| **Lazy Refresh** | Token 保活 | 用户请求时按需刷新 |
| **外部 Cron 服务** | 精确定时任务 | cron-job.org 等免费服务 |

## 九、关键决策点

### 决策 1：Monorepo vs Multi-repo

**推荐：Monorepo（短期）→ Multi-repo + npm 包（中期）**

| 阶段 | 方案 | 理由 |
|------|------|------|
| 短期（当前） | 单仓库内的 `packages/cf-core` + `templates/` | 三项目已在同一仓库，改动成本最低 |
| 中期（5+ 项目） | `@eforge/cf-core` 发布到 GitHub Packages | 版本化管理，多仓库可引用 |
| 长期（10+ 项目） | 考虑 Turborepo 或 Nx | 大规模 monorepo 工具链 |

### 决策 2：前端统一方案

**推荐：保持灵活，不强制统一**

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 简单工具页 | 原生 HTML/JS | 零构建成本，Cache 友好 |
| 复杂交互（商城） | Vue 3 + Vite | 组件化开发效率高 |
| 管理后台 | Vue 3 + Element Plus (CDN) | 三者已统一，无需改变 |

### 决策 3：数据库选型（Turso vs D1）

**推荐：Turso (libSQL) 为主，D1 为备选**

| 维度 | Turso Free | D1 Free |
|------|-----------|---------|
| 存储 | 9 GB/月 | 5 GB |
| 行读取 | 无限制 | 500 万行/天 |
| 行写入 | 无限制（有公平使用政策） | 10 万行/天 |
| 分布式 | ✅ 原生 | ✅ 原生 |
| 备份 | 手动/API | 自动（保留 30 天） |
| 迁移 | libSQL 客户端 | Wrangler D1 CLI |

Turso 的无限制读写在 Free 套餐下优势明显，适合批量产品。D1 可作为极轻量场景的备选。

### 决策 4：现有项目是否迁移

**推荐：渐进式迁移，不急于一次性重构**

| 步骤 | 方式 | 风险 |
|------|------|------|
| 1. 新建项目使用模板 | 直接用 `templates/cf-shop` 等 | 零风险 |
| 2. 新项目共享 `cf-core` | `import { ok, fail } from '@eforge/cf-core'` | 低 |
| 3. 老项目逐步替换 | 按模块替换 `lib/*` 为 `@eforge/cf-core` | 中 |
| 4. 完全统一 | 老项目迁移到模板结构 | 高（谨慎评估） |

## 十、与现有 cf-form-kit 模板的关系

当前已有的 `templates/cf-form-kit` 是一个微型表单模板（D1 + 无前端框架），定位与本文推荐的三个模板不同：

| 模板 | 定位 | 数据库 | 前端 | 复杂度 |
|------|------|-------|------|--------|
| `cf-form-kit` | 表单/信息收集 | D1 | 无框架 | 极低 |
| `cf-shop` | 发卡/电商商城 | Turso | Vue 3 + Vite | 高 |
| `cf-tools` | 在线工具集 | Turso | 原生 HTML/JS | 中 |
| `cf-api` | API 中间层服务 | Turso | 原生 HTML/JS | 中高 |

`cf-form-kit` 可作为第四个模板保留，适用于极轻量场景（调查问卷、信息收集、落地页表单）。建议将 `cf-form-kit` 也迁移使用 `@eforge/cf-core`，使其与主体系保持一致。

## 十二、总结

### 核心发现

1. **三项目技术栈高度一致**（Hono + Turso + Drizzle + TypeScript + Cloudflare Workers），具备标准化的坚实基础
2. **基础设施层代码重复度 >90%**，抽取为共享内核的 ROI 极高
3. **Adapter/Registry 模式** 是三者共同的核心架构模式（支付 Provider、邮箱驱动、SMS 渠道），可统一为插件接口
4. **已有 `cf-form-kit` 模板** 验证了模板化路线的可行性
5. **Free 套餐优化经验** 已在 eshop 评审中沉淀，可复用到所有新产品

### 一句话方案

> **构建 `@eforge/cf-core` 共享内核 + 三个产品模板（cf-shop / cf-tools / cf-api）+ 可插拔插件体系，实现"30 分钟从模板到上线"的批量产品工厂。**
