# AcctBox V2 实施记录与踩坑

⚠️ D1 已取消，项目已完全迁移到 Turso/libsql

## 背景

`acctbox` 按 V2 蓝图开始实施。第一阶段目标不是做大后台，而是把 V1 已验证的发卡链路升级为轻量可维护底座：

```text
TypeScript + Hono + Zod
Drizzle ORM 普通查询
Wrangler ~~D1~~（已取消） migrations
兑换码发卡
订单 token 查询
ADMIN_TOKEN 管理端
卡密导入
manual 确认发卡
永久 smoke 脚本
```

## 业务调整

由于当前没有支付功能，先用“兑换码”代替支付确认：

```text
1. 用户下单必须输入兑换码。
2. 兑换码无效时不创建订单、不扣库存。
3. direct 商品兑换成功后直接展示卡密。
4. manual 商品兑换成功后进入 pending，由管理员确认后发卡。
5. 未配置邮件时，页面和 lookup 接口就是主交付方式。
```

## 产品判断：兑换码是否多余

如果只是一次性交付卡密，兑换码流程确实比管理员直接发卡密多一步。

但 AcctBox 的目标是验证 Web 端完整闭环：

```text
宣传页
商品展示
兑换领取
订单留痕
lookup 补偿查询
管理端维护
后续传播和复购入口
```

因此推荐保留兑换码，但必须做到：

```text
1. 管理端按商品生成兑换码。
2. 用户兑换成功后直接展示卡密。
3. 用户网络中断时可以通过 order_token lookup 查询。
4. 管理员可以在后台查订单和卡密，必要时人工补发。
```

如果项目完全不需要 Web 宣传和查单，才退化为“管理员直接发卡密”。

## UI 调整：用户端和管理端分离

用户反馈截图显示第一版 UI 存在明显问题：

```text
1. 用户需要填联系方式、邮箱、兑换码、活动码、邀请码，流程过重。
2. 普通用户界面出现“管理”，不符合产品边界。
3. 页面文案有开发验证痕迹。
4. 浅色界面和卡片布局缺少数字权益产品的质感。
```

调整后：

```text
1. 用户端只保留兑换码。
2. 普通导航只保留兑换和查询。
3. /admin 独立进入管理端。
4. 查询支持订单 Token 或一次性兑换码。
5. 视觉改为黑色科技感主题。
```

结论：

```text
发卡产品的用户端必须极简。
复杂信息留给管理端，用户只做一件事：输入兑换码并领取。
```

## 追加踩坑：/admin 通过 challenge 后显示首页

### 现象

访问 `https://acctbox.eforge.xyz/admin` 通过 Cloudflare challenge 后，页面显示普通用户首页。

### 判断

这不是域名绑定错误。`curl -I` 显示：

```text
cf-mitigated: challenge
HTTP 403
```

说明 WAF 正在保护 `/admin`，配置层生效。

### 根因

根因是 Cloudflare Static Assets **默认的 `html_handling`** 行为：

```text
assets.html_handling = "auto-trailing-slash"  (默认值)
```

对于 `/admin` 这种无扩展名路径，Cloudflare 自动做 trailing-slash 检查：找不到 `admin.html` 也没有 `admin/index.html`，就 307 到 `/`——**这个过程在 Worker 执行之前就发生了**。

`run_worker_first: true` 不影响此行为，因为 Static Assets 的 HTML 规范化是路由层逻辑，先于 Worker 分流。

此外前端最初也只识别精确 `/admin`，没有覆盖 `/admin/`。

### 修复方案

首次修复（不正确）：
- `run_worker_first: true` → 无效，问题根源不在 Worker 分流

最终正确修复（三管齐下）：

```text
1. html_handling: "none"                        # 禁止静态层做自动 URL 规范化重定向
2. not_found_handling: "single-page-application" # 非资产路径回退到 index.html
3. run_worker_first: ["/admin", "/admin/*", "/lookup", "/order", "/api/*"]
```

| 配置项 | 作用 |
|---|---|
| `html_handling: "none"` | 🔑 **关闭自动 307**，/admin 不再被规范化到 / |
| `not_found_handling: "single-page-application"` | /admin 404 → 返回 /index.html |
| `run_worker_first` | Worker 先执行，做精细路由（API / 后台 / 静态） |

### 误判点

最初以为只靠 `run_worker_first: true` 就能解决。实际 deploy 后：

```bash
curl -sI https://acctbox.mailforwdy.workers.dev/admin
# HTTP/2 307 → /      ← 仍跳转！证明非 run_worker_first 问题
```

说明 `html_handling` 的自动规范化行为**独立于 Worker 路由层**，必须在 assets 配置中显式关闭。

### 为什么这是当前最佳实践

AcctBox 不是纯静态站，而是带后台、~~D1~~（已取消）、兑换码、lookup 的轻量 Worker 应用。对这类项目，路由确定性比少一次 Worker 调用更重要。

局部配置：

```text
run_worker_first: ["/api/*", "/admin", "/admin/*"]
```

在实际部署中仍出现过 `/admin -> 307 -> /`。为了避免下一次项目继续踩同一个坑，带后台/lookup/API 的 Cloudflare Worker + Assets 项目统一采用：

```text
assets.run_worker_first=true
```

然后在 Worker 中显式分流：

```text
/api/* -> Hono API
/admin、/admin/*、/lookup、/order -> /index.html
其他路径 -> ASSETS
```

### 建议

```text
WAF challenge 继续保留。
不要为了解决前端路由问题放松 /admin 防护规则。
不要再用“/admin 返回了 challenge”作为后台可用的完成证据。
```

## Drizzle ORM 边界

执行规则：

```text
能用 ORM 的普通 CRUD，优先使用 drizzle-orm。
涉及 ~~D1~~（已取消）原子发卡的 UPDATE ... RETURNING 保留参数化 raw SQL。
```

原因：

```text

raw SQL 只允许 prepare().bind()，禁止拼接用户输入。
```

## 踩坑：orders.status CHECK 约束

### 背景

V1 `orders.status` 只允许：

```text
issued / sold_out / failed
```

V2 manual 模式需要：

```text
pending / paid / issued / expired / canceled / failed
```

### 现象

管理端 smoke 在创建 manual 订单时返回 HTTP 500。

### 原因

SQLite/D1 无法直接修改已有 CHECK 约束。`0002_v2_core.sql` 虽然添加了字段，但旧 CHECK 仍然存在，插入 `pending` 失败。

### 解决方案

新增正式迁移：

```text
acctbox/migrations/0003_rebuild_orders_status.sql
```

采用“备份子表 -> 重建 orders -> 恢复子表”的方式，避免外键引用导致：

```text
FOREIGN KEY constraint failed
```

### 建议

```text
1. 状态机字段的 CHECK 要谨慎。
2. 线上表改 CHECK，不要写临时 SQL，要写 migration。
3. 被外键引用的表重建时，必须处理子表。
4. 这类脚本必须保留，不能调完就删。
```

## 追加踩坑：ADMIN_TOKEN 不能放 vars

### 背景

为了本地管理端 smoke 方便，曾短暂把开发默认值放入 `wrangler.jsonc` 的 `vars`。

### 现象

远程部署输出里直接出现：

```text
env.ADMIN_TOKEN ("dev-only-change-me")
```

### 原因

`vars` 是普通环境变量，不是 secret。它会进入部署配置，也可能覆盖同名 secret。

### 解决方案

```text
1. 从 wrangler.jsonc 删除 ADMIN_TOKEN。
2. 生产只使用 wrangler secret put ADMIN_TOKEN。
3. 本地需要管理端时，通过 shell 环境变量或未提交的 .dev.vars 临时传入。
```

本地验证管理端推荐命令：

```bash
ADMIN_TOKEN="dev-only-change-me" rtk npm run dev:admin
```

### 建议

```text
任何鉴权 token 都不能进入 wrangler.jsonc、docs、README、seed.sql。
部署日志中看到 token 或默认 token，要立即回滚配置并重新部署。
```

## 追加踩坑：rotate-admin-token.sh 认证失败导致生产环境 ADMIN_TOKEN 未设置

### 背景

生产环境管理端 /admin.html 访问时返回 503 错误：`生产环境必须通过 wrangler secret 配置 ADMIN_TOKEN`。
执行 `bash scripts/rotate-admin-token.sh` 后脚本因 `wrangler whoami` 认证失败而 `exit 1`，ADMIN_TOKEN 从未被推送到 Cloudflare。

### 现象

1. 线上管理端所有 /api/admin/* 接口返回 503：`生产环境必须通过 wrangler secret 配置 ADMIN_TOKEN`
2. 执行 `bash scripts/rotate-admin-token.sh` 输出：`尚未登录 Cloudflare，请先运行 npx wrangler login`
3. CI 部署（GitHub Actions）正常成功，不受影响

### 原因链路

完整错误链路：

```text
1. wrangler.jsonc 中 vars.ADMIN_TOKEN = "dev-only-change-me"（开发默认值）
2. 未通过 wrangler secret put ADMIN_TOKEN 设置过生产值
3. Cloudflare 部署时，secret 不存在 → 使用 vars 中的默认值
4. security.ts requireAdmin() 检测到：
   - expected === "dev-only-change-me"
   - hostname 不是 localhost
   → 返回 503 "生产环境必须通过 wrangler secret 配置 ADMIN_TOKEN"
5. rotate-admin-token.sh 因本地未登录 Cloudflare（wrangler whoami 失败）而 exit 1
6. token 从未生成，从未推送 → 问题持续
```

关键理解：

- `wrangler.jsonc` 的 `vars` 是普通环境变量，**不是加密 secret**
- `wrangler secret` 设置的值**优先级高于 vars**，但必须显式设置
- **从未设置过 secret → Cloudflare 永远使用 vars 中的默认值**
- CI 部署只负责推送代码，不负责设置 secret

### 排查过程

```bash
# 1. 确认线上状态
$ curl -sS https://acctbox.mailforwdy.workers.dev/api/admin/products \
  -H "Authorization: Bearer dev-only-change-me"
# 返回：{"ok":false,"error":"生产环境必须通过 wrangler secret 配置 ADMIN_TOKEN"}
# ↑ 证明线上 ADMIN_TOKEN 值就是 "dev-only-change-me"

# 2. 确认 CI 部署正常
$ git log --oneline -5
# 3 次部署全部成功，CI 没问题

# 3. 确认 rotate 脚本是否执行成功
$ bash scripts/rotate-admin-token.sh
# ❌ 尚未登录 Cloudflare → exit 1
# ↑ 脚本在 whoami 检查时就退出了，token 从未生成
```

### 解决方案

**必须先在本地完成 Cloudflare 认证，再执行轮换脚本：**

方式 1（浏览器登录，推荐）：

```bash
cd acctbox
npx wrangler login        # 浏览器弹出授权页面
bash scripts/rotate-admin-token.sh   # 生成 token 并推送
```

方式 2（API Token）：

```bash
export CLOUDFLARE_API_TOKEN=cfat_xxx  # 从 https://dash.cloudflare.com/profile/api-tokens 创建
bash scripts/rotate-admin-token.sh
```

验证成功：

```bash
# 用新 token 测试
export ADMIN_TOKEN=<新token>
curl -sS https://acctbox.mailforwdy.workers.dev/api/admin/products \
  -H "Authorization: Bearer $ADMIN_TOKEN"
# 应返回：{"ok":true,...}
```

### 铁律级建议

1. **新项目首次部署后，必须立即执行 `wrangler secret put ADMIN_TOKEN`**——这不是可选项，是上线的前置条件
2. **CI 部署只负责推送代码和 D1 migration，不负责设置 secret**——secret 是一次性手动操作
3. **`wrangler.jsonc` 中 `ADMIN_TOKEN: "dev-only-change-me"` 只能用于本地开发**——代码已做保护（非 localhost 拒绝），但不要依赖代码保护，必须设置 secret
4. **执行 rotate 脚本前，先确认 `npx wrangler whoami` 能通过**——否则脚本会静默退出，token 不会推送
5. **secret 设置成功的验证标准**：用新 token 调用 /api/admin 接口返回 200，而非 503/401

## 踩坑：Admin Token 持久化安全漏洞

### 背景

2026-05-25 安全审计发现 Admin 面板的 Token 管理存在严重安全漏洞：

- **Token 存在 sessionStorage**（`app.js` 第 185 行：`sessionStorage.setItem(storedTokenKey, ...)`）
- **自动回填到密码输入框**（第 278 行：`adminTokenInput.value = savedToken`）
- **永不过期**：只要标签页不关，任意重复访问都自动授权
- **无退出机制**：没有 logout button 清除 Token

### 问题代码（已修复）

```javascript
// 原 app.js 中的安全漏洞代码
const storedTokenKey = "acctbox_admin_token";

adminLogin.addEventListener("submit", async (event) => {
  event.preventDefault();
  sessionStorage.setItem(storedTokenKey, adminTokenInput.value); // ← Token 持久化
  ...
});

// 页面加载时从 sessionStorage 回填
const savedToken = sessionStorage.getItem(storedTokenKey);
if (savedToken) {
  adminTokenInput.value = savedToken;  // ← 密码明文暴露
  ...
}
```

### 根因

前端 Vanilla JS 实现中，采用 `sessionStorage` 保存 Token 是设计缺陷。虽然 `sessionStorage` 比 `localStorage` 略有改善（标签页关闭即清除），但：
1. 同浏览器同标签页刷新后 Token 仍然存在
2. Token 明文显示在密码输入框中
3. 无法主动退出

### 修复方案

**前端**：重构为 Vue 3 + Element Plus 单页应用（`public/admin.html`）

| 安全措施 | 实现方式 |
|---|---|
| Token 在内存中 | Vue `ref('')`，不落 sessionStorage/localStorage |
| 刷新需重新登录 | 页面加载时 `token.value` 为空，弹出登录对话框 |
| 30 分钟无操作自动退出 | `inactivityTimer` 定时器清除内存 Token |
| 退出按钮 | `handleLogout()` 清除 `token.value`，显示登录对话框 |
| CSS 全页面滚动 | 不设 table fixed height，避免参考项目中的表内滚动 bug |

**后端**（不变）：
- 继续使用 Bearer Token 鉴权
- 已有操作审计日志（`admin_audit_logs` 表）
- 已有 IP 哈希记录

### 架构变更

| 文件 | 变更 |
|---|---|
| `public/admin.html` | **新建** Vue 3 + Element Plus 单文件 SPA（CDN，无构建步骤） |
| `src/index.ts` | Worker 路由 `/admin` 指向 `admin.html` |
| `public/index.html` | 移除 admin 段（`admin-shell`、`admin-view` 等） |
| `public/app.js` | 移除所有 admin 代码（`adminHeaders`、`loadAdmin`、`showAdmin`、`sessionStorage` 操作） |

### 设计决定

1. **全页面滚动**：表格不设固定高度（`el-table` 不设 `height` 属性），整个页面作为滚动容器。这是从参考项目 `admin.html` 的踩坑经验中吸取的教训——表内滚动在移动端和不同屏幕尺寸下适配困难。
2. **暗色主题**：匹配 AcctBox 现有的 `#05070c` 暗色背景。
3. **CDN 加载**：Vue 3 + Element Plus 通过 unpkg CDN 加载，无构建步骤。`public/` 目录下直接放 SPA 文件，Worker Static Assets 绑定直接服务。
4. **Token 生命周期**：纯内存变量。页面关闭或刷新后 Token 消失，必须重新输入。

### 建议

1. **后续可升级为 JWT**：如果管理端需要更细粒度的权限控制，可以引入签名 Token + TTL，后端校验过期时间。
2. **前端可分离部署**：`public/admin.html` 可以整体迁移到 Vercel，Worker 只保留 `/api/*`。迁移时只需修改 Worker 路由和 CORS 配置。
3. **操作审计**：已经在 admin 路由中植入 `writeAdminAudit` 调用，每次管理操作都会记录到 `admin_audit_logs` 表。

## 踩坑：管理后台 Element Plus 表格列堆叠

### 现象

用户反馈管理后台（`/admin`）的表格"列堆在一起了，变成行了"，即表格列没有正常横向排列，而是纵向堆叠，每列独占一行，完全无法阅读。影响订单管理、商品管理、卡密管理、兑换码管理四张表格。

### 根因

**主要根因（99%）：订单表和商品管理表缺少 `<el-table>` 的 `</el-table>` 闭合标签**

```html
<!-- ❌ 修复前 -->
<div class="table-shell">
  <el-table :data="orders" stripe border ...>
    <el-table-column ... />
    ...
    <el-table-column ...>
      ...
    </el-table-column>
    ← 缺少 </el-table> 闭合标签
  </div>    ← 浏览器自动闭合 <el-table> 在这里
</template>

<!-- ✅ 修复后 -->
<div class="table-shell">
  <el-table :data="orders" stripe border ...>
    <el-table-column ... />
    ...
    <el-table-column ...>
      ...
    </el-table-column>
  </el-table>   ← 补上正确闭合
  </div>
</template>
```

在 Vue 3 的 In-DOM 模板编译中：
1. 浏览器的 HTML 解析器把 `<el-table>` 当作未知元素，在遇到 `</div>` 时自动闭合并将其余内容推为兄弟节点
2. Vue 3 从 DOM 反构模板字符串时得到错误的结构
3. Element Plus 的 Column 组件无法在 Table 的正确作用域内注册
4. 列元素退化为普通块级元素 → 纵向堆叠排列

**次要因素：`table-layout="fixed"` + `min-width` 的组合在窄屏下会加剧问题**

即使标签正确闭合，`table-layout="fixed"` + `style="width:100%"` + 所有列用 `min-width` 的组合如下：

```text
table-layout="fixed" + width:100%
→ 表格强制等于容器宽度
→ 列宽按 min-width 比例分配（不是绝对 min-width）
→ 当容器宽度小于列宽总和时，所有列被等比压缩
→ 压缩到内容无法完整显示，触发换行
→ 但不会堆叠成行，只会显示不完整
```

因此标签缺失是**因**，`fixed` 布局下列被压缩是**火上浇油**。单独修复 `table-layout="auto"` 可以缓解，但只有补上 `</el-table>` 才能根除。

原始代码中还存在一个噪音：
1. 卡密表和兑换码表的 `</el-table>` 是正确的，但订单表和商品管理表缺失
2. `.table-shell` 之前设置了 `overflow: hidden`，进一步切断了滚动

### 排查过程（错误路径，教训）

**第 1 轮：误判为文字颜色问题**

看到用户说"看不到"，AI 先入为主判断是深色模式下文字颜色与背景融为一体。花了一个完整 turn 阅读 Element Plus 深色主题 CSS 变量，查找 `--el-table-text-color`、`--el-bg-color` 等。完全走偏。

**第 2 轮：误判为 overflow:hidden 导致**

读到 `.table-shell { overflow: hidden }` 后判断是滚动被切断。将 `overflow: hidden` 改为 `overflow: auto`。这是部分正确（确实需要滚动），但没有解决列被压缩的根本原因。

**第 3 轮：用 CSS hack 覆盖 Element Plus 行为**

写了 `width: auto !important; min-width: 100% !important;` 覆盖 `el-table` 的 `width:100%`。这破坏了 Element Plus 内部的表头/表体滚动同步机制（`el-table` 的 `fixed` 列依赖精确的宽度计算）。

**第 4 轮：所有列改用固定 width**

把所有 `min-width` 改为 `width`，去掉 `style="width:100%"`。在窄屏下确实不再堆叠，但列宽变成硬编码，无法根据内容自适应，且去掉了 `width:100%` 后表格不再占满容器，窄屏下右侧留白。

**第 5 轮：查官方文档，找到 table-layout="auto" 方案**

最终查阅了 Element Plus 官方文档和最佳实践文章，发现 Element Plus 2.x 提供了 **`table-layout="auto"** 属性。将 `el-table` 改为 `table-layout="auto"` + 列用 `min-width`，看起来宽度恢复正常。但用户反馈"还是堆叠"——因为 `</el-table>` 缺失的问题根本还没动。

**第 6 轮：最终根因——检查 HTML 结构完整性（真正的发现）**

在用户再次反馈"还是不行"后，不再猜测，直接**逐行审查 admin.html 的完整结构**。发现：
- 订单表（L280-312）：`<el-table>` 开始后，最后一个 `</el-table-column>` 后面跟着 `</div>`，**没有 `</el-table>`**
- 商品管理表（L365-388）：同样的模式，**缺少 `</el-table>`**
- 卡密管理表（L401-420）：`</el-table>` 存在 ✅
- 兑换码列表（L429-447）：`</el-table>` 存在 ✅

前 5 轮的所有修改（CSS hack、width/min-width 互换、table-layout 切换）全部打偏，因为**组件压根没正确渲染**。

### 正确方案

**第一步：补全 `</el-table>` 闭合标签（根因修复）**

这是优先级最高的修复。所有 `el-table` 必须有正确的 `</el-table>` 闭合。

**第二步：使用 `table-layout="auto"` 避免窄屏压缩（最佳实践）**

补上闭合标签后，`el-table` 就能正确渲染。但为了获得更好的自适应体验，推荐加上 `table-layout="auto"`：

```html
<!-- 关键：table-layout="auto" + style="width:100%" + 列用 min-width -->
<el-table :data="orders" stripe border table-layout="auto" style="width:100%">
  <el-table-column prop="orderNo" label="订单号" min-width="180" show-overflow-tooltip />
  <el-table-column prop="productTitle" label="商品" min-width="140" show-overflow-tooltip />
  <!-- ... -->
</el-table>
```

CSS 部分：

```css
/* .table-shell 不设 overflow:hidden，让 Element Plus 自己管理滚动 */
.table-shell { width: 100%; border: 1px solid rgba(148,163,184,0.12); border-radius: 8px; }

/* 窄屏下 table-shell 需要 min-width 触发横向滚动 */
@media (max-width: 720px) {
  .table-shell { min-width: 720px; }
}
```

### 为什么这是正确方案

| 组合 | 行为 | 适用场景 |
|------|------|----------|
| `table-layout="fixed"` + `width` | 列宽按固定值分配，总和超出容器时出现滚动 | 列宽已知且不需要自适应 |
| `table-layout="fixed"` + `min-width` + `width:100%` | min-width 被按比例分配到容器宽度，列被压缩 | ❌ 导致列被压缩 |
| `table-layout="auto"` + `min-width` + `style="width:100%"` | 列宽按内容自适应，最小保证 min-width，超出容器时自动出现横向滚动条 | ✅ 最佳实践 |

核心区别：
- `fixed` 布局下，`width:100%` 表示表格宽度 = 容器宽度，所有列必须在容器内分配
- `auto` 布局下，`width:100%` 表示表格最小占满容器，但列可以超出，超出部分自动产生横向滚动

### 一、系统定位

AcctBox 是一个**数字权益发卡平台**，部署在 Cloudflare Workers + D1 上，面向个人开发者/小型商家，提供虚拟商品（账号、卡密、会员等）的兑换交付。

核心闭环：

```text
管理员配置商品 → 导入卡密 → 生成兑换码 → 分发兑换码 → 用户兑换 → 自动/手动发卡 → 用户查询结果
```

### 二、架构师视角

#### 2.1 技术栈评估

| 层级 | 选型 | 评价 |
|------|------|------|
| 运行时 | Cloudflare Workers | ✅ 全球边缘部署，冷启动极快，免费额度充足 |
| 数据库 | Cloudflare D1 (SQLite) | ✅ 与 Workers 深度集成，无需额外运维；⚠️ 单库 10GB 上限，无读副本 |
| 框架 | Hono | ✅ 轻量、类型安全、边缘运行时原生支持 |
| ORM | Drizzle ORM | ✅ 类型安全、轻量；⚠️ 复杂查询仍需 raw SQL（如原子库存扣减） |
| 前端用户端 | 原生 HTML/CSS/JS | ✅ 极致轻量，单文件部署；⚠️ 无 SSR，SEO 靠边 |
| 前端管理端 | Vue 3 + Element Plus (CDN) | ✅ 快速搭建后台；⚠️ 单文件架构，无构建优化，CDN 依赖 |
| 认证 | Bearer Token (ADMIN_TOKEN) | ⚠️ 无 JWT、无 RBAC、无多用户；适合单管理员场景 |

#### 2.2 架构风险

**风险 1：D1 无事务回滚**

D1 目前不支持真正的数据库事务回滚（`batch` 不是原子事务）。当前代码中 `createOrder` 的 direct 模式流程：

```text
1. issueAvailableCard() → 原子 UPDATE RETURNING 扣减库存
2. INSERT INTO orders → 写入订单
3. 如果步骤 2 失败 → releaseIssuedCard() 补偿释放
```

这个补偿模式在极端情况下（Worker 执行超时、D1 写入部分成功）可能丢失卡密。当前通过 `try/catch + releaseIssuedCard` 做了补偿，但不是原子性的。

**建议**：对于 direct 模式，考虑"先创建订单（pending），再扣库存，再更新订单为 issued"的三步走，每步都有明确的状态可以回溯。

**风险 2：单文件 admin.html 架构**

当前 `admin.html` 约 700+ 行，包含完整 Vue 3 应用 + CSS + 模板。优点是部署简单（Workers Static Assets 直接服务），缺点是：
- 无法 tree-shake Element Plus（整个组件库通过 CDN 加载）
- 无 HMR，调试效率低
- 代码维护性随功能增长急剧下降

**建议**：当管理端功能超过 1000 行时，迁移到 Vite + Vue 3 SPA 构建，Worker 只提供 `/api/*`。

**风险 3：CDN 可用性**

Element Plus 和 Vue 3 通过 unpkg.com CDN 加载。如果 CDN 不可用，管理后台完全无法使用。

**建议**：将 `element-plus/dist/index.css`、`element-plus/theme-chalk/dark/css-vars.css`、Vue 3 和 Element Plus JS 下载到 `public/vendor/`，由 Workers Static Assets 本地提供服务。

**风险 4：卡密安全**

当前卡密的 `deliverySecret` 以明文存储在 D1 中。管理端的卡密列表 API（`GET /admin/cards`）直接返回 `deliverySecret`。虽然管理端需要 Bearer Token，但：
- 管理端前端拿到后渲染在 DOM 中
- 导出功能（`GET /admin/orders/export`）CSV 中也包含联系方式脱敏，但卡密本身在订单详情中可见

**建议**：卡密在数据库中加密存储（AES-256-GCM），仅在发卡时解密。密钥通过 `wrangler secret` 注入。

#### 2.3 数据模型评估

当前 11 张表（products, cards, card_batches, orders, order_events, coupons, campaigns, referral_codes, referral_events, request_logs, admin_audit_logs, idempotency_keys, system_config, email_logs），覆盖了完整业务链路。

**冗余表**：
- `campaigns` 和 `referral_codes` 在当前业务中没有管理端入口，仅通过 seed.sql 插入演示数据。如果短期不启用，可以考虑暂时不维护。
- `email_logs` 没有对应的发送逻辑，属于预留表。

**缺失索引**：
- `cards` 表缺少 `(product_id, status, created_at)` 复合索引，`issueAvailableCard` 的子查询 `WHERE product_id = ?2 AND status = 'available' ORDER BY created_at ASC` 会全表扫描。

```sql
-- 建议添加
CREATE INDEX IF NOT EXISTS idx_cards_product_status_created ON cards(product_id, status, created_at);
```

#### 3.2 关键路径风险

**风险 1：兑换码 = 支付的替代品，但不是等价物**

当前兑换码承担了"允许领取"的门禁角色，这在 MVP 阶段合理。但兑换码本质上是**线下分发**——管理员必须手动生成并分发兑换码。这意味着：
- 无法自助购买（用户必须先获得兑换码）
- 无法自动收费（兑换码没有支付语义）
- 兑换码的分发渠道完全依赖外部（微信/邮件/线下）

**建议**：短期（1-2 周）内完成微信/支付宝支付集成，让兑换码退化为"优惠码"角色。

**风险 2：manual 模式的人工瓶颈**

manual 模式下，每个订单都需要管理员手动确认发卡。如果日均订单超过 20 单，人工确认会成为瓶颈。

**建议**：优先推广 direct 模式（自动发卡），manual 模式仅用于高价值/需审核的商品。

### 五、行业顾问视角

#### 5.1 数字权益发卡行业的核心诉求

数字权益（虚拟商品）发卡行业有以下几个关键特征：

1. **库存是核心资产**：卡密一旦泄露或误发，直接等于经济损失。当前系统通过 `UPDATE ... RETURNING` 原子扣减 + `deliverySecret` 分离存储来保护库存，这是正确的。

2. **交付即履约**：与实物电商不同，数字权益的交付是即时的，不存在物流环节。这意味着"支付→发卡"必须是原子的，中间状态越少越好。当前的 `direct` 模式（兑换码→自动发卡）是最佳路径。

3. **售后成本低但纠纷风险高**：用户说"没收到"时，系统必须有完整证据链。当前系统的 `order_events` 审计日志 + `order_token_hash` 查询机制可以应对，但还缺少：
   - 卡密查看时间戳（用户何时首次看到卡密）
   - IP 记录（发卡时的用户 IP）

4. **灰色地带**：数字权益发卡行业容易涉及侵权商品（盗版软件、共享账号等）。系统本身是中性的，但运营者需要注意合规风险。

#### 5.2 合规建议

1. **数据保护**：用户联系方式（`buyerContact`、`buyerEmail`）目前明文存储。如果面向欧盟用户，需符合 GDPR；面向国内用户，需符合《个人信息保护法》。建议加密存储或定期匿名化。
2. **交易凭证**：当前没有发票/收据功能。如果涉及收费，需要提供交易凭证。
3. **退款机制**：当前没有退款流程。`markPaidAndIssue` 只有"确认发卡"，没有"撤回发卡"。建议添加订单取消 + 卡密回收流程。

#### 5.3 商业模式建议

```text
当前：兑换码 → 免费领取 → 适合赠品/活动/内测
短期：+ 支付 → 自助购买 → 适合小规模售卖
中期：+ 多商品分类 + 优惠码体系 → 适合运营推广
长期：+ 多管理员 + 代理商 + 佣金体系 → 适合平台化
```

优先级排序：

```text
P0（1-2 周）：支付集成（微信/支付宝当面付或 Stripe）
P1（2-4 周）：邮件通知 + 卡密加密存储 + 复制按钮
P2（1-2 月）：登录体验优化 + 多管理员 + 库存预警
P3（2-3 月）：商品分类 + SEO 优化 + 代理商体系
```

### 六、资深用户视角

#### 6.1 兑换体验

**正面**：
- 兑换流程极简：输入兑换码 → 一键领取

**正面**：

- Token 查询机制可靠，即使页面关闭也能找回

**负面**：
- manual 模式下用户不知道需要等多久
- 没有网络错误重试提示
- 页面刷新后管理端需要重新输入 Token（没有持久化登录状态）

## 八、补充分析：前端稳定性与核心链路保障

> 基于表格列堆叠踩坑的根因，补充现有分析中缺失的一个关键维度：
> **前端代码的结构健壮性直接影响核心发卡链路的可靠性。**

### 8.1 核心链路的前端依赖关系

AcctBox 的发卡核心链路（管理端部分）：

```text
管理员登录 → 查看商品/库存 → 管理卡密 → 确认发卡
                       ↓                                 
                  表格渲染（依赖 UI 组件正确挂载）          
                  ├─ 订单管理表：查看待确认订单
                  ├─ 商品管理表：编辑商品信息
                  ├─ 卡密管理表：核对卡密内容
                  └─ 兑换码管理表：管理兑换码
```

**任何一个表格渲染失败，这条核心链路就断了**。比如：
- 订单表无法渲染 → admin 无法看到待确认订单 → **manual 模式的卡密永远发不出去**
- 卡密表无法渲染 → admin 无法查看已发卡密 → **用户说"没收到"时无法核实**
- 兑换码表无法渲染 → admin 无法生成兑换码 → **用户没有兑换入口**

这次踩坑证明：**前端的结构错误（缺少 `</el-table>` 闭合标签）可以让整个管理端瘫痪**，而这个问题跟后端逻辑是否正确（Zod 校验、幂等保护、原子扣减）完全无关。

### 8.2 当前 admin.html 的结构风险评估

| 风险项 | 严重度 | 说明 |
|--------|--------|------|
| 单文件 700+ 行 | 🔴 高 | 所有模板/逻辑/CSS 集中在一个 HTML 文件，无结构化分离，手工维护容易遗漏闭合 |
| 无构建验证 | 🔴 高 | 无 Vite/Webpack 编译，标签闭合错误在"运行后"才能发现，没有静态检查 |
| CDN 组件库 | 🟡 中 | Vue 3 + Element Plus 通过 CDN 加载，无 Tree-shaking，无编译时优化 |
| In-DOM 模板编译 | 🟡 中 | Vue 3 的 In-DOM 编译对 HTML 结构敏感，不同于字符串模板编译的错误提示友好 |

**核心教训**：In-DOM 模板编译模式下，`el-table` 未闭合时解析为：

```text
浏览器解析 → <el-table> 当作未知元素 → 遇到 </div> 自动闭合 → DOM 结构错误
Vue 编译 → 从已损坏的 DOM 反构模板字符串 → column 不在 table 作用域内 → 列不渲染
```

这个错误链中，**没有任何一层给出警告或错误提示**（Vue DevTools 也看不到结构问题）。

### 8.3 现有分析中缺失的优化建议

**针对"项目经经理视角"（§3.3 交付质量）的补充：**

原有分析提到"前端质量参差不齐"，但没有给出具体改进方案。补充如下：

```text
前端质量提升措施（按优先级）：
1. ✅  修复已发现的标签闭合问题（已完成）
2. 🔲  建立 admin.html 结构检查清单（每次修改管理端模板时对照）：
       - 每个 <el-table> 必须有对应的 </el-table>
       - 每个 <template> 必须有对应的 </template>
       - 每个 <div> 的缩进层级不超过 6 层
3. 🔲  添加自动化 HTML lint（如 HTMLHint）到 CI 管道
4. 🔲  管理端代码超过 1000 行时迁移到 Vite Vue SPA（编译时检测标签错误）
```

**针对"产品经理视角"（§4.1 管理端旅程）的补充：**

原有分析提到"表格、表单交互仍需打磨"。表格的"打磨"需要分两层：

```text
第一层（结构层）：确保组件正确渲染

  - CSS 只是"装饰" → 结构不对时 CSS 无法修复
  - 本次修复后已解决 ✅

第二层（体验层）：优化列宽、滚动、筛选等
  - table-layout="auto" + min-width → 自适应列宽 ✅ 已应用
  - 窄屏下横向滚动体验 → 用 .table-shell 的 overflow:auto 触发 ✅ 已修复
  - 冻结列（fixed）→ 当前未启用，可考虑在宽表场景使用
```

**针对"架构师视角"（§2.2 架构风险）的补充：**

新增一个架构风险：

```text
风险 5：前端模板缺乏结构验证
严重度：🔴 高
描述：In-DOM 模板的 Vue 应用不会在编译阶段检测标签闭合，错误只能在运行后由用户发现。
      本次表格列堆叠的 5 轮错误修复就是直接后果——因为没有错误提示，每一轮"看起来修好了"
      实际上根因根本没动。
影响：管理端功能完全不可用时，后端逻辑再正确也等于零。
建议：
  短期：每次修改 admin.html 后手动检查 DOM 结构（用浏览器 Element 面板验证组件树）
  中期：CI 增加 HTMLHint 或 html-validate 检查
  长期：迁移到 Vite Vue SPA，利用 Vite 的编译时验证提前发现标签错误
```
