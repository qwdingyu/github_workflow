# AcctBox 核心算法审查与已知限制

> 审查日期：2026-05-27
> 技术栈：Cloudflare Workers + **Turso/libsql**（~~D1 已取消~~）+ Drizzle ORM
> 审查范围：订单创建、支付回调、卡密发放、优惠券核销、库存管理、邮件通知

---

## 一、技术栈纠偏：Turso/libsql ≠ D1

### 1.1 当前架构

项目已**完全迁移到 Turso/libsql**，不再使用 Cloudflare D1：

```
src/db/client.ts    → drizzle-orm/libsql 驱动
src/db/database.ts  → @libsql/client/web 连接 Turso 云端
src/bindings.ts     → TURSO_URL + TURSO_TOKEN（非 D1Database）
src/index.ts        → initDatabase({ TURSO_URL, TURSO_TOKEN })
wrangler.jsonc      → 无 D1 绑定，只有 TURSO 环境变量
```

### 1.2 并发模型差异

| 特性 | ~~D1 (SQLite) 已取消~~ | Turso/libsql (当前使用) |
|------|-------------|------------------------|
| 写入并发 | **单写者模型**，同一时刻只有一个写事务 | **MVCC 多版本并发控制**，支持多写者并行提交 |
| 冲突检测 | 无（串行写入，无冲突可能） | 行级冲突检测，无冲突时并行提交，有冲突时回滚后到先到者 |
| SQLITE_BUSY | 常见（写锁互斥） | **不会出现**（MVCC 消除了全局写锁） |
| 事务隔离 | SERIALIZABLE（串行化） | 快照隔离 + 乐观并发控制 |

**影响**：之前审查中"SQLite 单写者模型天然防并发超兑"的结论**已不成立**。Turso MVCC 允许并发写入，`consumeCoupon` 的条件 UPDATE 在高并发场景下存在**乐观锁冲突**的可能，需要额外的防护措施。

## 三、已知限制与优化建议

### 3.1 🔴 `markPaidAndIssue` 中 coupon 消耗失败不回滚订单

**现状**：
```typescript
// markPaidAndIssue 第 467-473 行
if (order.couponCode) {
  const couponResult = await consumeCoupon(db, order.couponCode);
  if (!couponResult || !couponResult.success) {
    console.warn(`coupon consume failed, manual intervention may be needed`);
    // ⚠️ 不回滚——订单已发卡，回滚会导致用户付款却收不到卡密
  }
}
```

**风险场景**：
1. 用户使用优惠券下单，支付成功
2. 支付回调触发 `markPaidAndIssue`，卡密已发出
3. 此时优惠券已被管理员停用/过期/用完，`consumeCoupon` 失败
4. 用户实际享受了折扣但优惠券未被标记为已使用

**是否需要优化**：**建议优化，但优先级 P2**

**优化方案**：
- 方案 A（推荐）：在 `markPaidAndIssue` 发卡前先 `consumeCoupon`，失败则不发卡。但需考虑 coupon 消耗成功而发卡失败的补偿——此时需回滚 coupon（新增 `rollbackCouponConsume` 函数）
- 方案 B：在管理后台增加"优惠券异常订单"告警视图，自动筛选 `couponCode IS NOT NULL AND couponUsedAt IS NULL` 的已发卡订单，供管理员人工介入
- 方案 C（最小改动）：在 `consumeCoupon` 失败时，向订单写入一条事件日志 `writeOrderEvent(db, orderId, "warn", "优惠券消耗失败")`，方便后续排查

**推荐**：先实施方案 C（5 分钟），再择机实施方案 B。

### 3.2 🔴 Turso MVCC 并发下的优惠券超兑风险

**现状**：
```typescript
// consumeCoupon 使用条件 UPDATE
const result = await db.update(coupons)
  .set({ usedCount: sql`${coupons.usedCount} + 1` })
  .where(and(
    eq(coupons.code, code),
    eq(coupons.active, 1),
    sql`${coupons.usedCount} < ${coupons.maxUses}`,
    // expiresAt 检查已添加
  ))
  .returning({ code: coupons.code });
```

**风险场景**（Turso MVCC）：
1. 事务 T1 和 T2 同时读取 `usedCount = 9, maxUses = 10`
2. T1 和 T2 都通过 `usedCount < maxUses` 检查
3. T1 先提交：`usedCount = 10` ✓
4. T2 提交时，MVCC 检测到同一行有写-写冲突，T2 被回滚 → **安全**
5. 但如果 T1 和 T2 操作**不同行**（不同优惠券代码），MVCC 不会冲突 → **安全，因为每个优惠券是独立行**

**实际风险评估**：
- 同一个优惠券代码的并发消耗：MVCC 行级冲突检测**可以防护**
- 但 MVCC 是**乐观锁**，冲突后会回滚，调用方需要**重试机制**
- 当前代码没有重试逻辑——`consumeCoupon` 返回 `success: false` 后直接 warn

**是否需要优化**：**建议优化，优先级 P2**

**优化方案**：
```typescript
// 方案：添加重试逻辑（最多 3 次）
async function consumeCouponWithRetry(db: DbType, code: string, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    const result = await consumeCoupon(db, code);
    if (result.success) return result;
    // 如果是 MVCC 冲突导致的失败（而非 usedCount >= maxUses），需要重试
    // 但当前无法区分失败原因——需要 consumeCoupon 返回更详细的错误类型
  }
  return { success: false, changes: 0 };
}
```

更好的方案：让 `consumeCoupon` 返回失败原因枚举（`CONFLICT` / `EXHAUSTED` / `EXPIRED` / `INACTIVE`），调用方根据原因决定是否重试。

### 3.3 🟡 `pay/unified` 线上→线下降级时卡密重新锁定

**现状**：
1. 线上支付流程：`lockCardForOrder` 锁定卡密 → 创建订单
2. 线上支付失败，降级为线下支付
3. 释放旧锁定的卡密：`releaseLockedCardByOrder`
4. 重新走线下支付流程：`lockCardForOrder` 再次锁定卡密

**风险**：步骤 3→4 之间，释放的卡密可能被其他请求抢走，导致降级后库存不足。

**实际风险评估**：
- 时间窗口极短（毫秒级）
- 卡密库存通常不会恰好处于临界状态
- 即使被抢走，返回"库存不足"是正确的业务语义

**是否需要优化**：**暂不需要，优先级 P3**

**优化方案**（如需）：
- 降级时不释放旧卡密，直接复用：检查卡密状态仍为 locked 且 orderId 匹配，直接复用
- 但这增加了代码复杂度，且需要处理卡密被其他订单锁定的情况

### 3.4 🟡 Turso MVCC 下 `issueAvailableCard`/`lockCardForOrder` 的并发安全

**现状**：
```typescript
// issueAvailableCard 使用 UPDATE ... WHERE status='available' RETURNING
// lockCardForOrder 使用 UPDATE ... WHERE status='available' OR (status='locked' AND lockedAt < expired) RETURNING
```

**风险场景**（Turso MVCC）：
1. 两个请求同时锁定同一张 available 卡密
2. MVCC 检测到同一行的写-写冲突，后到者被回滚
3. 后到者的 `issueAvailableCard` 返回空数组，认为库存不足
4. 但实际上库存可能充足（只是这张卡密被抢了），应该重试锁定其他卡密

**实际风险评估**：
- 低流量场景：几乎不会触发
- 高并发抢购场景：可能导致"假性库存不足"

**是否需要优化**：**建议优化，优先级 P2**

**优化方案**：
- 方案 A：在 `issueAvailableCard` 内部添加重试逻辑（最多 3 次），每次重试会尝试锁定下一张 available 卡密
- 方案 B：在调用方（`createOrder`、`markPaidAndIssue`）添加重试逻辑
- 方案 C：使用 `SELECT FOR UPDATE`（需确认 Turso/libsql 是否支持）

**推荐**：方案 A，改动最小。

### 3.5 🟢 邮件发送失败不影响业务流程

**现状**：
```typescript
sendEmail(db, env, { ... }).catch((e) => console.warn("[email] failed:", e));
```

**风险**：邮件发送失败时，用户无法收到卡密通知，但卡密已在订单查询页可见。

**是否需要优化**：**暂不需要，优先级 P3**

**优化方案**（如需）：
- 增加邮件重试队列（使用 Cloudflare Queues）
- 在管理后台显示"邮件发送状态"列
- 提供"重新发送邮件"按钮

### 3.6 🟢 管理员手动确认发卡时缺少 coupon 二次校验

**现状**：`markPaidAndIssue` 在发卡后才消耗 coupon，如果 coupon 已失效则仅 warn。

**风险**：管理员可能手动确认一笔使用已过期/已停用优惠券的订单。

**是否需要优化**：**建议优化，优先级 P3**

**优化方案**：在管理后台"确认付款"按钮旁显示 coupon 状态标签（有效/已过期/已停用），管理员可在确认前检查。

## 五、Turso/libsql 迁移后需关注的额外事项

### 5.1 连接管理

- 每个请求都调用 `initDatabase()` 创建新的 libsql client + Drizzle 实例
- Turso HTTP 模式下每次 SQL 都是独立的 HTTP 请求，无连接池开销
- 但如果使用 WebSocket 模式，频繁创建/销毁连接会有性能影响

### 5.2 事务支持

- Turso 云端通过 HTTP API 访问，**不支持多语句事务**
- 当前代码中的 `db.transaction()` 调用需要确认是否被 Turso HTTP 正确支持
- libsql 的 `batch()` 方法可替代部分事务需求

### 5.3 Drizzle ORM 兼容性

- `drizzle-orm/libsql` 驱动完整支持 `UPDATE ... RETURNING`
- `sql` 模板标签可正常使用
- 但部分高级特性（如 `db.transaction()` 的隔离级别设置）可能受限于 Turso HTTP 协议

## 六、结论

本次审查共发现 **4 个已修复的严重 Bug** 和 **6 个已知限制**。

核心结论：
1. **技术栈已迁移到 Turso/libsql**，之前的"SQLite 单写者天然安全"假设不再成立
2. **MVCC 并发模型**提供了行级冲突检测，但需要调用方处理重试
3. 3 个 **P2 级优化**建议在下一个迭代中实施（coupon 消耗闭环、并发重试、卡密锁定重试）
4. 3 个 **P3 级优化**可按需排期
