## 一、决策汇总（已确认）

### 决策 1：废弃 `require_email` 参数

**结论：邮箱强制必填，不留妥协空间。**

`require_email` 这个参数存在以下问题：

| 问题 | 说明 |
|------|------|
| 查询链路永远要打补丁 | 不开邮箱时历史订单 `buyer_email=null`，邮箱查询必须兼容"查不到"的边界 case |
| 后端校验分裂 | 前端读配置控制必填，后端 Zod schema 如果不是 `.nonempty()`，绕过前端就能不填 |
| 历史订单不可溯源 | `buyer_email=null` 的订单，无法通过邮箱找回，只能靠 orderToken |
| 行业无此惯例 | 所有数字商品平台（Steam、京东卡密、闲鱼）都强制邮箱，没有例外 |

**新设计收益：**
- 每一笔订单都可溯源，客服响应速度大幅提升
- 查询链路极简，不需要兼容"没邮箱"状态，代码干净 bug 更少
- 发卡邮件、退款通知都能触达用户

**历史数据处理：**
- `require_email=false` 时期创建的历史订单 → 保留不动，这些订单本来就不支持邮箱查询
- 未来所有新订单 → `buyer_email` 强制非空，后端校验不通过则 400

### 决策 2：下单成功不发送邮件

**行业最佳实践（来自链动小铺、快发卡、幻世发卡等平台）：数字商品即买即得，不发确认邮件。**

- 发卡网均无下单成功邮件
- 页面直接显示 orderNo + orderToken，用户截图保存
- 发邮件会增加运营成本，且可能被视为垃圾邮件

**用户查询卡密的入口：**
1. 下单成功后页面直接显示 orderNo + orderToken（用户截图）
2. 从支付记录里找 orderNo（行业标准链路）
3. 邮箱查询（兜底方案）

### 决策 3：orderNo 查询返回卡密

用户用 orderNo 查询时，需要返回完整卡密。**用户查询的核心诉求就是卡密，其他信息没有价值。**

## 二、查询系统设计（三种入口，按优先级排序）

### 2.1 设计原则

用户记不住 orderToken（长 UUID），也记不住 orderNo（除非从支付记录复制）。用户最可能记住的是自己的邮箱。

**三种入口优先级：**
1. orderNo（行业标准链路，用户从支付记录复制）
2. orderToken（UUID，下单成功时获得）
3. 邮箱（兜底方案，用户记得自己邮箱但忘了 orderNo）

### 2.2 查询流程

```
用户访问查询页
    → 输入内容，前端自动识别类型：
        ├── 包含 `@` → 邮箱查询
        ├── 长度 > 40 → orderToken
        └── 其他 → orderNo 查询（精确匹配）
    → 返回订单详情（含卡密）
    → 邮箱查询时返回列表，用户选择后再查详情（含卡密）
```

### 2.3 订单列表内的过滤和排序（仅邮箱查询场景）

| 过滤/排序维度 | 实现方式 |
|--------------|---------|
| 按订单号精确过滤 | 顶部搜索框，输入 `OXXXXX` → 实时筛选 |
| 按商品名称过滤 | 顶部搜索框，输入商品名 → 实时筛选 |
| 按时间倒序 | 默认，最新购买的在最上面 |

## 三、功能缺口与 Bug

### 问题 1：后端缺失 orderNo 查询接口（功能新增）

**现状**：`GET /api/orders/lookup` 只支持 `token` 和 `code` 两个参数，不支持 `orderNo` 查询。

**修复**：新增 `GET /api/orders/lookup?orderNo=`，按 `order_no` 精确匹配，返回订单详情（**含卡密**）。orderNo 是行业标准查询入口，用户从支付记录复制 orderNo 后直接查询。

**返回结构**：

```json
{
  "order": {
    "orderNo": "OABC123456",
    "status": "issued",
    "productTitle": "商品名称",
    "createdAt": "2026-05-26T10:00:00Z",
    "card": { "accountLabel": "...", "deliverySecret": "..." }
  }
}
```

---

### 问题 2：后端缺失邮箱查询接口（功能新增）

**现状**：`GET /api/orders/lookup` 只支持 `token` 和 `code` 两个参数。

**修复**：新增 `GET /api/orders/lookup?email=`，按 `buyer_email` 倒序返回该邮箱所有订单的简要信息（**不含卡密**），每次最多 10 笔。

**返回结构**：

```json
{
  "orders": [
    {
      "orderNo": "OABC123456",
      "status": "issued",
      "productTitle": "商品名称",
      "createdAt": "2026-05-26T10:00:00Z"
    }
  ],
  "total": 3,
  "hasMore": false
}
```

**修复**：在 `public/app.js` 订单列表展示区域，新增：
- 顶部搜索框（输入订单号或商品名，内存过滤）
- 默认按 `createdAt` 倒序

### 问题 4：查询入口前端自动识别缺失（Bug 修复）

3. 用 `p.title` 替换 `issued.accountLabel`
